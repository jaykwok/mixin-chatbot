## 命令行运维

成员上下文也可从控制台“会话”页登记压缩（打开空间、选中成员后点“压缩当前成员”），或运行 Linux `scripts/ops/ops.sh history-compact <群号>|--direct <成员号码>`、Windows `scripts/ops/ops.ps1 history-compact <群号> -User <成员号码>`（单聊空间用 `-Direct`）。运维入口先停机取得独占空间库，再登记任务并恢复原运行状态；原本停止的实例不会被自动启动。压缩由机器人运行后生成摘要，会产生模型用量，成功后仍保留历史和已有费用。聊天里的 `/compact` 可直接执行。

Durable 成员的临时目录包含历史引用与还没发完的回复文件。`tmp purge` 会先停机取得维护租约，生成带摘要的清单，再把已核对且未被引用的条目原子移入 `data/state/reclamation/backup/rm`；它会逐项报告已归档、保留、待处置和失败数量，归档本身不会立即释放磁盘空间；`tmp discard` 按归档清单永久删除这些条目、释放空间。`tmp reclaim` 用于物理回收：Windows 持有删除句柄并保存可续做清单，Linux 服务身份写入的条目必须由宿主 UID 0 的独立停机维护身份显式执行，普通 ops 包装器不会自动恢复这类特权操作。来源不明、内容或实体变化、仍有引用的目录都会保留。常规结果回收由机器人在成员空闲且引用释放后执行。整包备份和暂存恢复流程见[数据目录与备份](deployment.md#数据目录)。

日常交互操作从[网页控制台](console.md)进入。这里保留命令行入口，便于脚本调用和没有装 Bun 的 Docker 宿主机使用；排查与数据维护步骤见本文后面的对应章节。

### 日常控制

在项目根目录选择对应平台的命令行入口。

Windows：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 doctor
```

Linux / Docker：

```sh
bash scripts/ops/ops.sh doctor
```

将示例中的 `doctor` 替换为所需命令：

| 命令 | 用途 |
| --- | --- |
| `doctor` | 检查配置、应用机器人凭据、实例、事件 Stream、通讯录同步、运行状况和共享资料目录，并列出运行中的应用机器人版本、构建和数据格式；加 `--json`（Windows 为 `-Json`）输出单行 JSON |
| `start` / `stop` / `restart` | 启动、正常关闭或重启实例 |
| `logs` | 持续查看日志 |
| `directory` | 查看事件 Stream 连接、同步范围（每个部门的 ID、人数和路径）及是否已生效、通讯录映射数量、最近同步、等待复核的缺席和上一轮没完成的原因；只读，经本机端口询问运行中的服务 |
| `directory-scope [all]` | 修改同步范围并应用。`all` 为整个通讯录。只同步部分部门时逐层勾选，命令行不接受部门 ID：Linux 上不带参数即在终端里运行与部署时相同的向导（预先勾选当前范围，宿主机没有 Bun 时在运行中的容器里交互执行），也可以用控制台「通讯录」；Windows 只在控制台里勾选。没有终端时不带参数报错，不默认整个通讯录；多余或重复的参数同样报错。服务按新范围完整同步，成功后一次切换，切换前原来的名单仍然生效，见[同步范围](#事件-stream-与通讯录)。范围及是否已生效用 `directory` 查看 |
| `update` | 同步 origin/main，由目标版本的升级器在停机前完成确认后升级，保留原运行或停止状态 |
| `deploy` | 部署当前代码；可重新配置并重建现有部署，失败恢复原部署 |
| `model-configure` | 运行模型配置向导（Docker 在机器人容器的镜像内），填写期间机器人照常运行；确认后与网页配置相同地短暂停机、写入并按原运行状态恢复，写入或启动失败时恢复原配置；取消不修改。需要终端 |
| `configure-app-bot` | 运行应用机器人凭据向导（先用新凭据取一次访问令牌验证），之后与 `model-configure` 相同 |
| `relay-configure` | 运行外链配置向导（启用、修改或停用），之后与 `model-configure` 相同；停用时删除 `relay.json`，保留账本和云端文件 |
| `configuration-restore <config-编号>` | 恢复网页配置事务，或完成已提交事务的收尾；先核对记录及文件摘要，不覆盖其他操作修改过的配置 |
| `resume` | 按事务记录继续中断的部署或升级，不重新提问 |
| `rollback` | 回滚中断的部署或升级；数据已提交时拒绝 |
| `maintenance-recover` | 收尾中断的会话、统计导入、临时文件或修订维护，回收遗留写入者并核对原运行状态，不重复数据动作 |
| `uninstall` | 卸载。先取部署锁并持有到结束；有未完成的部署或升级、未收尾的运维任务或未结束的配置提交时拒绝，什么都不动（先继续或回滚、收尾）。随后停止并删除实例（Linux 的容器和部署遗留的回滚容器，Windows 的计划任务），按选择删除镜像，并把 `data/`、`logs/` 移入 `backup/rm`；外置共享资料目录不删除。需要终端 |

停机执行的维护命令（`history-clear`、`history-compact`、`stat-import`、`tmp-purge` 和带 `--digest` 的临时文件确认、`relay-purge`、`revision-cleanup` 的停机动作、高级运行参数的保存）在两个平台上遵循同一套规则：

- 先取部署锁，部署、升级或另一个维护操作正在进行时拒绝；有未完成的部署或升级时拒绝（`revision-cleanup restore` 例外，见[从备份恢复](#从备份恢复)）。容器处于运行、已停止、已创建或不存在以外的状态时拒绝；Windows 的计划任务须属于本项目，机器人以前台方式运行时拒绝，因为自动恢复只能启动计划任务，会改变运行方式。
- 机器人在运行时，停机前先问维护状态是否允许这个动作（会话清空和压缩按写会话判断，其余按服务之后能否启动判断），不允许就不停机，直接说明原因。
- 动作结束后，原来在运行的只在重读的维护状态允许启动时才启动，并等实例身份与就绪检查通过才报告“运行中”；原来停止的保持停止。动作被 Ctrl+C 或终止信号打断时同样按这条恢复。动作失败、没能恢复启动或就绪检查未通过时退出码非零。

`start`、`restart` 同样先检查部署锁、未完成的事务和维护状态，不满足时不启动。`stop` 只在部署、升级或维护正持有部署锁时拒绝；有未完成的事务时也能停止。

清空会话、登记压缩或统计导入被强杀、机器重启后，网页任务详情会提示需要恢复，可选择“预览恢复中断的维护”。也可运行 Linux `bash scripts/ops/ops.sh maintenance-recover`，或 Windows `powershell -ExecutionPolicy Bypass -File scripts\ops\ops.ps1 maintenance-recover`。修订维护在 CLI 中断后同样先执行这条恢复命令。恢复先核对并回收原写入者，再按磁盘维护状态决定能否恢复机器人；原数据动作不会重复执行，中断的原任务也不会改记为成功。整理或收缩仍有未完成的数据记录时，恢复只收尾运维写入者，机器人保持停止，随后按提示显式继续对应数据维护。请保留 `data/state/ops-maintenance.json` 和 `.console/runtime/`：它们记录原运行状态、写入者及固定版本，无法核对时会拒绝继续。

`stat-import` 在停机前复制所选账本及其 WAL，并核对复制前后和副本的摘要；原文件不变。私有副本位于 `backup/.stat-import-<编号>/`，正常结束或执行中断恢复时只清理本次记录能证明归属的副本。目录被替换或出现其他文件时保留现场并报错；恢复不重复导入，可先查看统计结果，再按需显式重试。

临时文件操作中断后也先执行 `maintenance-recover` 收尾运维进程，随后按原计划编号和摘要续做；恢复命令自身不会再次归档或删除条目。查询和预览不停机，确认执行才停机；两者都保留进程归属与恢复记录。Linux 核对当前部署使用的任务 daemon 和只读共享目录，无法核对时在停机前拒绝。

备份扫描、清理预演和按清单删除都持有同一部署锁，机器人继续运行。报告保存在 `tmp/backup-cleanup/`；Linux 核对该目录属主及文件系统身份，拒绝链接、其他身份可写的目录或中途替换。操作中断后先运行 `maintenance-recover`，它只收尾原进程并核对运行状态；再检查原报告和已删除条目，显式重新预演确认，不会自动重做删除。

网页控制台“设置”中的模型、机器人凭据和外链表单采用“草稿 → 校验 → 预览 → 应用”。已有秘密只显示是否设置；选择保持原值时无需重新输入。普通校验不联网，刷新模型目录或验证应用 token 需在当次表单里显式选择。应用时短暂停机，失败后恢复原配置及原运行状态；原来停止的实例保持停止。机器人凭据还要在重启后连上事件 Stream（最多等 45 秒），连不上同样恢复原凭据，结果里写明最近一次断开原因；原来停止的实例不启动，因此不做这项检查。

如果配置或高级运行参数发布被强杀，重新打开控制台，在“设置 → 配置恢复”预览并处理上次维护；CLI 先运行上文的 `maintenance-recover`。恢复会先核对并回收原写入者，再处理配置：已经确认提交的事务只做收尾，未提交的事务恢复原配置，最后按原运行状态恢复服务。只有运维记录已收尾、仅剩配置事务时，才直接运行 Linux `bash scripts/ops/ops.sh configuration-restore config-<编号>`，或 Windows `powershell -ExecutionPolicy Bypass -File scripts\ops\ops.ps1 configuration-restore config-<编号>`；编号见 `data/state/configuration-change.json`，网页会选择相应入口。不要手动删除记录、运行参数草稿或 `data/config/.config-*` 恢复目录：恢复文件摘要不符、应用身份变化或当前配置被其他操作改过时，命令会拒绝并保留现场，半套配置不能启动。

中断的部署或升级可在控制台“维护 → 部署恢复”预览继续或回滚。确认绑定当时的事务记录和已保存选择；记录变化后需要重新预览。数据已提交时只能继续收尾，数据已回滚但代码尚未恢复时只能完成回滚。升级事务的目标版本必须支持当前控制台协议；不支持时使用该版本的 CLI。代码被升级或回滚替换后，旧控制台只显示任务结果，请退出并重新运行 `bun run console` 获取新登录链接。

网页升级从“维护 → 升级 → 检查可升级版本”开始；检查会访问 origin/main。选择旧修订链整理方式和通讯录范围，当前不在 main 时还须允许切换，然后预览并确认。任务固定使用预览的完整提交 SHA，执行时不改为最新远端提交；已跟踪代码、配置、实例身份或运行状态发生变化时，需要重新预览。模型、凭据和运行参数沿用已保存值。整理空间不足或预览失败时在停机前拒绝，不自动跳过；需要跳过时应重新明确选择。

网页重新部署先“读取部署设置”，核对机器人端口、共享资料目录，明确选择修订链和通讯录范围，再预览并确认。目标端口与控制台相同时会拒绝。重新部署沿用已保存的模型和机器人凭据，成功后启动机器人，即使它此前处于停止状态。Linux 的“重建修复”使用同一部署流程；Windows 的“本机修复”由运维核心执行：只检查本机实例，已就绪时不重启，未就绪（包括已停止）时重启并等待就绪检查；前台运行的实例不修复，请先停止。计划任务缺失或安装损坏时使用重新部署。修复也受部署锁、未完成事务和维护状态限制。

升级或重新部署时，如果尚未保存通讯录范围，可以选“整个通讯录”，也可以选“部分部门”并读取部门树。部门查询直接使用应用凭据，不要求机器人运行；Linux 使用已有部署镜像。勾选只形成草稿，取消不修改配置；预览时重新核对部门，停机后随部署事务保存。应用配置、登录或部门权限变化时须重新选择，不能手填部门 ID。已有范围的部署沿用保存值；运行中的范围修改仍在“通讯录同步范围”保存后立即应用。

`update` 要求已跟踪文件没有本地改动，代码已最新也会检查部署记录。它先处理未完成的部署或升级（见[中断恢复](#中断恢复)），此时不拉取；否则拉取 origin/main，从目标提交导出升级器（Windows 为 `tmp/upgrade-<GUID>`，Docker 为 `tmp/upgrade-<随机>`），在工作区外由目标版本完成升级，结束后删除导出目录。两个平台都在停机前检查部署记录与离线配置：数据格式一致时正常升级；没有有效记录、记录损坏或数据格式不受支持时停止，不清理、不重置，详见[版本、数据格式与从旧版切换](data-migrations.md)。rootful Docker 的 `update`、`resume`、`rollback` 要由 root 运行，rootless Docker 由其所属用户运行，都在任何提问之前检查（见[选择部署方式](deployment.md#选择部署方式)）。升级沿用已保存的端口、共享资料目录、应用机器人凭据和 AI 配置，停机后不再询问；修改这些配置请使用 `deploy`。Docker 升级器停机前从目标提交（不含工作区改动和未跟踪文件）构建一次镜像，按 image ID 固定并用本次独占的保留标签防止被清除，构建期间原服务照常运行；随后在这个镜像中以原服务的身份、断网、只读挂载数据预检当前格式并校验配置，宿主机无需安装 Bun；停机前再复核一次：检出与升级开始时核对的不同（提交、分支、main 的位置，或已跟踪文件有了改动，例如构建期间改了文件），预览后配置或版本标记有变化，原容器被删除或替换，候选镜像或保留标签被改动，或剩余空间不够写快照，都停止，服务不受影响。两个平台切换代码都是先 `checkout main` 再快进到目标提交：运维核心在升级开始时的只读预检（构建或提问之前）和交接后在部署锁内、停机之前都按这条路径（当前检出 → main → 目标提交）预演，续做也一样，同时核对已跟踪文件没有改动、本地 main 能快进到目标提交；构建期间新出现的文件因此也在停机前被发现。会被覆盖或删除的未跟踪内容逐项列出并停止——目标提交或途经的 main 新增路径上已有的文件，含未跟踪文件的目录，占着新增路径上级目录位置的文件或链接（Windows 含目录联接），也包括被 `.gitignore` 忽略的文件（git 切换时会直接覆盖或随目录删除它们）。当前提交跟踪的链接或文件被改成目录时，git 直接替换它，不算冲突，链接指向的内容也不当作这些路径上的文件。预演只读，不改索引、工作区和这些文件；脚本不移动、不删除它们，由你移出工作区（或提交到其他分支）后重试。构建或预览被 Ctrl+C 或发给 `ops.sh` 的终止信号打断时删除预览容器和本次的保留标签并退出，服务没有停止，代码和数据不变；清理在独立的进程组中进行，期间再次中断（终端的 Ctrl+C、断线）不会打断它。停机后格式登记、验证实例和正式实例都按记录的 image ID 运行，中断后的继续和回滚也用它，不再构建或拉取；镜像已被清除时拒绝继续，只允许回滚尚未开始格式登记的操作。正式标签 `mixin-chatbot` 在数据提交、新实例就绪后才指向新镜像，发布失败时保留事务，可用 `resume` 重试；当前终端里的端口、共享资料目录和运行参数环境变量不会被采用，会提示已忽略；`update`、`resume`、`rollback` 的入口也不校验这些环境变量，升级结束后的体检按保存的设置进行。已保存的外置共享资料目录缺失时，升级在停机前停止。rootless Docker 发布不了已保存的低端口时（见[选择部署方式](deployment.md#选择部署方式)），升级同样在停机前停止并提示处理方法。升级缺少 `data/config/models.json` 或 `data/config/app-bot.json` 时拒绝升级，需先通过 `deploy` 完成配置。发布期间使用只验证实例检查，提交后恢复原运行状态，直接校验当前配置、统计 schema 和新实例。提交前失败恢复数据、原提交和部署；提交后启动失败保留新代码与数据，检查日志后重试。中断后的处理见[中断恢复](#中断恢复)。

升级与格式登记失败时，按终端打印的路径查看 `logs/operations/` 下的日志；其中包含失败阶段、异常、退出码与回滚结果。服务早期启动错误写入同目录的 `startup-*.log`，日志保留在当前项目中供排查。Docker 升级和部署的日志分别记录候选镜像的构建耗时（`candidate build took …s`，这时原服务仍在运行）和实际停机窗口：从停止原服务（`service stopped; downtime begins`）到新版本通过健康检查或回滚后原容器重新启动（`service back (…); downtime …s`）。中断后在新进程中续做时，停机若发生在之前的进程，只记录恢复的时刻；中断在事务指针发布之后、停止服务之前时，由续做的进程停止服务并从那里开始计时。构建会与原服务争用 CPU、内存和磁盘，停机前的准备不等于对原服务没有影响。

升级成功时两个平台都显示更新前后的提交（`升级完成：<原提交> -> <目标提交>`），回滚成功时显示代码恢复到的提交。Windows 升级时，依赖清单、锁文件、安装配置和补丁未变，且已安装的直接依赖版本匹配时，会保留 `node_modules` 并跳过安装；缺包、版本不匹配或依赖输入发生变化时，才把旧依赖移入本次快照并按锁文件安装，回滚时移回。版本更高也不视为匹配，避免偏离经过验证的依赖组合。Windows `deploy` 每次都把原依赖移入快照并重新安装。

部署和升级的备份放在 `backup/snapshots/<快照名>`，操作期间被替换的旧文件放在 `backup/rm/<快照名>`；用户 tmp 等日常归档直接放在 `backup/rm` 下。成功后只删除本次操作自己的快照和 `backup/rm/<快照名>`。快照名随机生成，`backup/rm` 中已有同名目录时拒绝开始；快照、归档或其上级目录是链接时拒绝清理。没有自动清理标记的其他事务目录和散落归档保留，由[历史归档清理](#历史归档清理)审查处理，不清空整个 `backup/rm`。操作失败时保留回滚现场。首次部署回滚后，本次写入的应用凭据和模型配置留在 `backup/rm/<快照名>` 和快照里（属部署身份，私有权限），由[历史归档清理](#历史归档清理)处理，不再需要时请清理。Windows 会移除空的 `backup` 目录；Linux 保留空的容器挂载目录，避免运行中的容器丢失后续归档。部署锁保存在 `data/state/deploy.lock`。Docker 部署和升级在构建新镜像前，先给原容器使用的镜像打上 `mixin-chatbot:previous` 标签，事务提交或回滚完成后再移除。Docker 29 起新装默认使用 containerd 镜像存储，它会删除失去最后一个标签的镜像，回滚要靠这个标签恢复原镜像。

关闭服务使用 `stop`：Windows 验证实例身份后先请求优雅关闭，超时再复核归属并终止进程树；Linux 使用 Docker 停止期限。

### 中断恢复

部署或升级在停机前把已确认的选择写入快照目录的 `transaction` 记录，再发布事务指针：操作类型、目标提交、升级前的提交与分支、原运行状态、端口、原与目标共享资料目录、是否重新配置 AI（格式 2）。Docker 另在同一目录写入 `candidate-image`（本次镜像的 ID、保留标签和所在的 Docker daemon）和 `service-user`（服务的 UID:GID），`transaction` 的格式和键不变；恢复入口要求完整的当前事务记录。继续和回滚先核对这两份记录，再检查数据是否已提交或运行任何容器：Docker daemon 与开始时不同（例如切换了 context 或 socket）时两者都拒绝；记录缺失或无效时停止，提示人工检查。Docker 部署或升级交给运维核心后被 Ctrl+C、终止信号或断线打断时，入口把中断转给核心：停机之前结束时服务、代码和数据都不动（事务指针已发布的保留，留给 `resume` 或 `rollback`），停机之后自动回滚（数据已提交时保留事务），代码由核心一并恢复；`ops.sh` 也等升级器结束才删除导出目录。回滚期间再次中断不会打断它：核心进入恢复后屏蔽普通取消。进程被强制终止或回滚未完成时，指针保留；此后 `deploy` 拒绝执行并提示改用 `resume` 或 `rollback`；`update` 先要求处理上次操作，交互终端显示“1 继续上次操作 2 回滚到操作前 0 退出”，非交互调用需改用 `resume` 或 `rollback`。未完成的是升级时，由它们同时切换或恢复代码。控制台的维护页显示“继续上次操作”和“回滚上次操作”，处理完成前暂停部署、升级和修复入口；已保存的设置损坏时，控制台只提供“继续 / 回滚 / 诊断”。`resume` 和 `rollback`（包括控制台发出的命令）先读事务记录，已保存的端口为空或损坏、`runtime.json` 损坏，以及新终端里无效的 `BOT_PORT`、`BOT_MAX_ACTIVE_REQUESTS` 都不会挡住它们。

- **继续**：只使用事务记录，不重新读取默认值或环境变量，也不拉取更新的 origin/main；运行参数沿用 `runtime.json`，当前终端的运行参数环境变量（如 `BOT_RUN_TIMEOUT_SECONDS`）不校验也不写入。当前代码必须是记录的目标提交。外置的目标共享资料目录缺失时停止，恢复挂载后重试。续做不运行凭据和 AI 配置向导，格式登记沿用停机前保存的计划。Docker 继续沿用记录的镜像 ID 和服务身份，不重新构建或拉取；镜像已被清除（例如 `docker image prune -a`）时拒绝继续，重新构建的镜像不能代替它，此时只能回滚，格式登记已经开始的还需人工处理。Docker 升级的继续和回滚从记录的目标提交（本地已有）导出升级器，离线也能处理；目标提交在本地缺失时只能回滚，由事务固定的运维运行包执行。中断在切换代码之前时，继续会先停止服务再切换代码；停止之前先确认切换能完成：已跟踪文件有未提交的改动（快进会保留这些改动，执行的就不是目标版本）、本地 main 无法快进到目标提交，或切换会覆盖未跟踪的内容（与新升级的预演相同）时都不停止服务、不切换，服务和代码保持现状，处理后重试。
- **回滚**：由运维核心依次停止服务、结束修订整理、恢复数据，再恢复原代码（升级）、依赖、配置和容器或计划任务，最后按原运行状态启动。原共享资料目录在项目外且缺失时拒绝。中途失败（例如残留 `.git/index.lock` 使代码恢复失败）或被强制终止时事务保留，处理原因后再次 `rollback`：回滚的每一步都可以重复执行，已经恢复的部分不受影响。回滚一旦开始就不能再继续发布，菜单和控制台只提供完成回滚。
- **回滚不覆盖升级后的改动**：两个平台在执行 `git reset --hard` 恢复原代码前都会先核对工作区。当前提交必须是升级前或目标提交；原分支不在 HEAD 时，也不能指向这两个之外的提交。已跟踪文件的未提交改动、会被升级前版本覆盖的未跟踪文件（目标版本删除、此后又手工放回的文件），以及占着升级前版本目录位置的未跟踪文件或链接（例如升级前有 `retired/seed.txt`，现在 `retired` 是手工创建的文件、链接或 Windows 目录联接）都会阻止恢复代码，终端会逐项列出。只涉及已跟踪内容的文件与目录互换不受影响。显式 `rollback` 在停止服务、改动数据之前发现冲突，数据、配置和服务都保持现状。升级失败触发的自动回滚先恢复数据，再发现冲突时不改代码，也不恢复依赖、配置和容器或计划任务：服务保持停止，事务保留。把改动提交到其他分支、备份或撤销后再运行 `rollback`，完成剩下的部分。
- **数据已提交**：当前发布提交记录属于本次事务时拒绝回滚，判定在停止服务或改动代码之前完成。继续只停止验证实例并启动正式实例，不再构建或开始新事务；新实例通过健康检查后事务才结束，未就绪时保留记录，可再次继续。

当前程序只识别当前事务记录（格式 2）；缺少完整记录时拒绝操作，不猜测快照的设置。

## 长时间没有回复

单聊里成员第一次提问，或超过 `BOT_ACKNOWLEDGE_IDLE_MINUTES`（默认 30 分钟）没有对话后的第一条提问，机器人先回一句“收到，正在处理，请稍候。处理时间较长时可以发送 /status 查看进度。”；群里回过这句后，这段时间内任何人的提问都不再回。设为 0 时不发，成员收到的第一条就是回答。服务维护期间补推的消息会先收到一条说明晚到原因的提示。等待中想确认进度，可以发 `/status`：它 显示状态（空闲、准备中、执行中、执行工具中、正在执行 /stop 或 /clear）、等待处理的消息数、正在运行的工具和待处理附件；有任务在运行时另有任务编号、已用时间和三项时限。服务日志按任务编号记录“任务开始”“任务结束”（含结果），运行中每 60 秒一条“任务仍在运行”（含已用时间和阶段），看门狗中止时记录中止原因。日志不记录模型输出、思考正文或工具参数。

1. 先确认消息到达了服务：`doctor` 或控制台总览中“事件 Stream”应为已连接，开发者后台的事件订阅仍是 Stream 且勾选了机器人接收消息事件（推送卡片上的按钮点了没有反应时，检查卡片交互事件是否已勾选并随版本发布）。服务断开期间的消息约 5 分钟后才补推，断开超过 5 分钟可能丢失，需要重发。成员收到“暂时无法确认身份，正在同步通讯录”时，见[事件 Stream 与通讯录](#事件-stream-与通讯录)。
2. 在异常群发送 `/status`，记下任务编号。用[日常控制](#日常控制)里的 `logs` 入口查看日志，或在 PowerShell 执行 `Get-Content logs/mixin-chatbot.log -Tail 200`，按任务编号、群号定位，也可以用下文的[提取脚本](#按任务编号提取日志)。
3. “任务仍在运行”的阶段：“准备中”是任务已开始、尚未进入模型轮次；“等待或接收模型输出”是模型轮次进行中；“等待重试”是模型请求失败后的退避；“执行工具 …”列出正在运行的工具；“压缩会话历史”是在压缩该成员的历史。
4. 工具启动的每条命令（bash、文档解析和生成）结束后，不论成败，都记录一条“命令耗时”，含任务编号、`工具名#工具任务号`、结果（退出码、超时、取消等），以及总耗时和各阶段耗时：监督进程启动、命令启动、执行、回收。隔离容器中的命令只记总耗时。若“监督进程启动”或“命令启动”常达数秒，多为安全软件在检查进程创建：火绒按创建者预留的可执行内存计时，约每 MB 3 毫秒。因此 Windows 上机器人进程默认设置 `BUN_JSC_jitMemoryReservationSize=134217728`（128 MB；计划任务环境中已设置的值优先），监督进程固定为 16 MB。经实测，把 bun.exe 加入火绒信任区无效。
5. 只有某个群异常时，发送 `/stop`，等待 `/status` 变为空闲，再发 `/clear`。收到确认后，用“只回复 OK”测试。`/clear` 让当前用户在本群开启新的上下文，旧上下文留在空间库里，共享资料不受影响。若恢复，旧上下文是重要线索；若仍失败，保留这一轮的任务日志，继续检查 Pi 请求与模型服务。
6. 普通 HTTP 流探测成功只验证该次请求，不能验证机器人的完整历史、工具定义、思考模式和压缩请求。`doctor`/健康检查也不能证明模型回答正常。

### 深入排查：模型超时与进展判定

Pi 原生 `durable.stream.timeoutMs` 默认另对每次模型请求设置 120 秒期限，重试计数与服务看门狗独立；先到的取消条件生效。调整引擎策略及使用只读 `history context / timings` 诊断，见[运行设置与可选工具](runtime-tools.md)。记录缺少官方耗时字段时，诊断以未知展示。

模型等待或输出期间，默认连续 180 秒无有效进展就主动取消。Pi Durable 在模型输出时约每 100 毫秒更新一次已收到的部分回答（正文、思考、工具调用及其参数），并在 `persistWithinMs`（默认 1000 毫秒）内写入空间库；看门狗每秒查看一次，部分回答有任何变化都算进展，计时从每个模型轮次（每次尝试）开始，包含首个内容到达前的等待。反复改写同一内容也会续期，因此另设**单次模型响应 600 秒上限**，持续有进展也不能延长。

这两种模型时限只在模型轮次中计时；工具执行、历史压缩、重试退避和最终发送期间暂停，下个模型轮次重新计时。整轮时限默认 1200 秒，从任务第一次开始算起，覆盖准备、模型、工具和交付，服务重启后接着计算；三种时限以先到者为准。

中止时日志记一条“任务总时限到达”“模型无有效进展超时”或“单次模型响应超时”，带任务编号、已用时间和取消原因（`task_timeout`、`model_idle`、`model_response_timeout`）；成员收到的报错里也有任务编号。这些信息本身不能确定故障在上游服务还是 SDK。

可通过 `data/config/runtime.json` 或环境变量设置 `BOT_MODEL_IDLE_TIMEOUT_SECONDS` 和 `BOT_MODEL_RESPONSE_TIMEOUT_SECONDS`，重启生效；无可见增量的长思考模型、耗时较长的正常生成可按实测调整。中止后要等运行真正结束（工具退出）才处理同一用户的下一条消息，因此最终报错耗时可能超过阈值。上游只返回 `The operation timed out.` 时不直接断言网络不通。若任务中止后长期没有“任务结束”，先保存日志，再用运维 `restart` 恢复实例：空间库里未结束的任务在重启后恢复，已用时间不清零。

## 按任务编号提取日志

也可在控制台的“日志”页按任务编号筛选并导出筛选结果，或在维护页按任务编号下载执行记录；需要完整扫描时使用下方独立脚本。

将群内报错或 `/status` 中的任务编号传给脚本即可。在项目根目录运行：

Windows PowerShell：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/task-logs.ps1 555d838a
```

Linux（在部署主机上运行，支持 Docker 部署，无需主机安装 Bun）：

```sh
bash scripts/ops/task-logs.sh 555d838a
```

脚本读取项目 `logs/mixin-chatbot.log` 及数字后缀的轮转日志，按旧到新提取完整的 8 位任务编号。
默认附带前后各 3 行，跨轮转文件保留上下文，重叠行只输出一次。每次运行在
`tmp/task-logs-<任务ID>-<时间>-<随机后缀>/` 下新建：

- `task.log`：仅任务匹配行，附原文件名和行号。
- `context.log`：任务行及前后文；`--` 表示中间省略了其他日志。
- `summary.txt`：扫描范围、匹配数量、首次匹配前最近的模型就绪信息、首末记录、最后运行心跳和三种超时记录。

可选参数：Windows 用 `-Context 5 -LogDir "D:\saved-logs"`；Linux 用
`--context 5 --log-dir /path/to/saved-logs`。上下文范围为 0–100 行，日志目录默认相对脚本定位项目，
显式指定的相对日志目录则相对当前工作目录。从其他目录调用脚本时，结果仍保存到脚本所属项目的 `tmp/`。

脚本可在服务运行或停止时执行，保留源日志和之前的提取结果，不读取模型凭据配置。
Linux 使用 Bash、awk 和 GNU coreutils；Windows 支持 PowerShell 5.1+。
退出码 `0` 表示找到任务，`2` 表示没有匹配日志，`1` 表示参数或读写失败。正在运行的任务可能继续写日志，
已轮转覆盖的历史无法从当前日志恢复。日志保留原文，前后文可能包含其他任务，分享前请脱敏。

## 数据维护

以下命令在安装了 Bun 的项目根目录运行；将尖括号占位内容替换为实际值。

```sh
bun run stat
bun run stat --period week
bun run stat "<群号>" --period last-month
bun run stat direct --period week    # 单聊空间
bun run stat --since 2026-10-01 --until 2026-10-07
bun run history list
bun run tmp list
bun run relay list
bun run relay test    # 上传并删除测试文件，不需停机

# 写操作前先停止服务
bun run history clear "<群号>"
bun run history clear --direct  # 单聊空间
bun run history clear --all    # 单聊和所有群
bun run tmp purge --days 7
bun run tmp purge --days 30 --group "<群号>" --user "<手机号>"
bun run relay purge "<关键字>"
bun run stat-import <旧部署>/data/groups/stats.sqlite    # 导入 schema 2 旧版统计
bun run stat-import <已保存快照>/stats.sqlite           # schema 3 汇总恢复到全新空账本
```

`stat` 读使用统计账本 `data/state/stats.sqlite`，只有提问和模型 token 两类数字。提问在消息进入成员队列时计入；token 取 Durable 按模型和工具名累计的已返回用量，在每轮结束、`/compact`、`/clear`、维护和打开空间时把增长量记到同步当天，口径见[统计账本](data-migrations.md#统计账本)。账本与会话历史相互独立：清空上下文不影响已统计的数字。单聊在统计中记为 `direct`。旧版统计按[导入旧版统计](data-migrations.md#导入旧版统计)并入。

`--period` 支持 `today`、`yesterday`、`week`、`last-week`、`month`、`last-month`、`7d`、`30d`、`all`；与 `--since/--until` 互斥。统计输出总提问数、跨群去重的提问人数、人均和日均提问、活跃天数占比、高峰日、前五名提问占比、提问排行，以及逐日、逐周、逐月的提问、提问人数和入账 token；群明细列出 input、output、cacheRead、cacheWrite、合计和加权缓存读率，并按模型、按工具（工具自身调用的辅助模型）分列。不显示费用。每一天都会列出，无记录填 0；周、月人数在周期内重新去重，不累加每日人数。覆盖人数指实际提问的账本成员身份，不代表群总人数或覆盖率。

Linux 运维入口示例：`bash scripts/ops/ops.sh stat --period week`；Windows：`scripts\ops\ops.ps1 stat -Period week`，自定义日期使用 `-Since` / `-Until`。HTML 报表和 CSV 从控制台“统计”页导出，直接下载到浏览器。

完整起止区间提供同比、环比，并打印基期日期和数值。周一开周；本周、本月比较上周、上月相同已到达日数（遇短月截到月末），上月比较完整前月；其他区间比较前一等长区间。同比取去年同日期，闰日截到月末。包含今天时数据仍在增长，账本只有日粒度，不与基期按小时对齐。基期为 0 时显示“新增（基期无记录）”，不计算无限增长；无历史记录不能证明当时没有使用。全部或只有一侧日期时不比较。日期沿用服务本地时区，应保持服务与运维环境时区一致。

`history clear` 在空间库里为该群（`--direct` 为单聊空间）每位成员登记一次清空，机器人下次启动时、处理任何消息之前先执行：与成员自己发 `/clear` 相同，排队中的消息一并取消，旧上下文留在空间库里，不释放磁盘空间；空间库记录的空间与目录不符时拒绝，整个空间不做改动。`history clear --all` 在同一次停机内对单聊和所有有会话历史的群逐个执行同样的清空，相当于全员发送 `/clear`，适合会话普遍变长、首轮请求写入的上下文过大时使用；某个空间被拒绝或失败时其余照常清空，最后列出未完成的空间并以退出码 1 结束，处理原因后可重新执行，已登记的清空不会重复。不指定空间也不写 `--all` 时只报错。运维包装器用 `history-clear --all`（Windows：`history-clear -All`），控制台在维护页的“清空全部会话”预览后确认。`history list` 只列出当前空间库的占用。统计区间按自然日裁剪。服务、升级验证实例、当前数据登记和维护写操作通过 `data/state/service` 的 proper-lockfile 租约互斥，异常退出后约 35 秒可恢复陈旧锁。服务的心跳一旦发现租约丢失（例如已被另一进程接管），立即以退出码 1 退出，不再走正常关机的入账、归档和等待；没来得及入账的提问和用量由下次同步补入，已记入空间库的 `/stop`、`/clear` 在下次启动时重新执行，尚未记入的需要重发，工具进程由各自的监督进程回收。运维包装器和控制台的写操作都按[上文的规则](#日常控制)自动停机并恢复原运行状态；直接运行 `bun run history …` 等命令时先 `stop`，完成后按需 `start`。

空间库提交结果无法确认（例如磁盘写入失败或 SQL 线程意外退出）时，服务停止接收新任务并以退出码 1 退出，由部署的监督器重启；不会在线重新打开已出错的会话。持续出现这类退出时，先排查磁盘空间、文件权限和存储错误，保留数据库及 WAL。已经持久化的任务和控制命令在重启后恢复。

清理调用结果或保存回复记录暂时失败时，会自动退避重试。`/clear` 未完成期间，该成员的新消息继续排队，模型请求暂停；解除文件占用或修正权限后会自动继续。`/status` 显示重试次数和最近错误，服务关闭会中止等待。清理没有完成时不会发送完成回执。

统计只计入 Durable 已提交的用量：被中断、在提交前崩溃或超时放弃的请求没有入账，服务商可能仍按其计费，所以 token 合计是已知下限，不是账单。日志出现“统计累计值回退……已按当前值重设基准，本次不入账”时，说明某个会话库的累计值比上次同步小（被替换为较早的副本，例如单独从备份恢复）：回退掉的那部分之前已经入账，不再重复计入；恢复后到这次同步之间新产生的用量并入新基准，会少计，符合下限口径。

## 事件 Stream 与通讯录

服务启动后用应用凭据取得访问令牌并连接事件 Stream，断开后自动退避重连。空闲连接每 30 秒发一次 ping，平台曾回应过 ping 的连接连续 30 秒没有回应和任何消息时视为已断开（例如被网络设备静默回收），主动重连。断开超过 1 分钟写告警日志，超过 2 分钟 `doctor` 的“事件 Stream”判为失败；控制台总览在断开期间显示“Stream 已断开”。连不上时先检查服务器能否以 HTTPS 访问 `imtwo.zdxlz.com` 和 `imfl.zdxlz.com` 的 443 端口、凭据是否仍有效（`configure-app-bot` 会验证），再查看日志。同一应用只能有一个实例连接 Stream：另一套部署或调试工具使用同一应用时，事件会被分走。平台在投递失败约 5 分钟后补推一次，补推的消息按原发送时间判断：普通提问照常处理并注明“约 N 分钟前发出”，`/stop`、`/clear`、`/compact` 这类改状态的命令超过 1 分钟才到达时不执行，请成员重发。

健康状态分两层。**本机就绪**指服务完成本地初始化、能应答且不在停止中，`/health` 同时报告实例身份；部署、升级的就绪检查和 `doctor` 的“本地机器人健康”只看这一层，不等待平台。**外部依赖**指事件 Stream 和通讯录同步，`/health` 只报告服务已知的状态，不现场请求平台或模型；`doctor` 和控制台总览把它们单独列出。`/health` 还报告机器人自本次启动以来需要留意的事件：停住和出错的任务、超时放弃的交付、未发出的模型请求和统计回退，每类给出次数、最近一次的空间（单聊或群号）和时间，不含号码和内容；`doctor` 的“运行状况”一行列出它们，最近一次在 24 小时内时判为待核验，细节按时间到日志里查找。计数在机器人重启后清零。平台短暂故障时服务保持就绪并自动重连，部署不会因此判定新版本失败而回滚；反过来，“本地机器人健康”通过不代表消息能正常收发，以“事件 Stream”一行为准。

机器人按开放平台通讯录把成员的平台 ID 对应到手机号，统计、会话和成员目录都按手机号归属。映射保存在 `data/state/agent.sqlite`（0600，不进日志和诊断包），与当前 AppID 和环境绑定，换应用或环境时重建。

- **同步时机**：首次部署后在后台完整同步一次。通讯录请求合计限速每秒 80 次（平台未公布限流，实测到每秒 80 次未遇到限流；若遇到限流，所有平台请求包括发消息会一起短暂冷却）；遍历部门的同时就解析新出现的成员，已解析的成员不必等整轮结束即可使用。约 2.7 万人、5000 个部门的通讯录首次同步约需 8–10 分钟，完成前未同步到的成员收到“正在同步通讯录”的提示；之后每天 03:00 完整同步，并顺带复核约 1/30 的已有映射；遇到未知成员时触发一次，30 分钟内不重复。同一时间只有一轮同步。
- **撤销**：只有完整同步（全部分页成功、无冲突）才撤销不再出现在通讯录中的成员；不完整的一轮不撤销，已有映射继续使用，服务 5 分钟、15 分钟后各重试一次，之后每小时重试，直到同步完整。平台响应缺少部门或成员列表、列表类型不对、总页数缺失或无效，或者列出的成员没有手机号时，这一轮都算不完整，也不记为最近一次完整同步；只有明确的空列表（或不带列表但总数为 0）才算部门已空。日常同步中一轮缺席的超过现有映射的 10% 且多于 20 个时（例如接口异常或开发者后台的可见范围被改小），这一轮先不撤销并告警，10 分钟后再完整同步一轮复核：仍缺席的才撤销，期间重新出现的照常保留，复核这一轮新出现的缺席重新按阈值判断。这些都由服务自动完成，不需要人工确认。
- **冲突**：同一手机号出现互相矛盾的身份信息，或一个平台 ID 同时对应两个仍在通讯录中的号码时，不自动合并，本轮也不撤销；成员换手机号只在完整同步确认旧号已不在时才转移，新号码使用新的成员目录和统计键，旧账不改写。

- **同步范围**：整个通讯录，或选定的部门及其全部子部门，部署时必须明确选择，没有默认值（见[通讯录同步范围](deployment.md#通讯录同步范围)）。之后修改：在控制台「通讯录」中逐层展开部门直接勾选，不同分支、不同层级可以混选，每个部门含其全部子部门，最多 200 个，见[网页控制台](console.md#配置与通讯录)；Linux 上也可以运行不带参数的 `directory-scope`，在终端里用部署时的向导逐层勾选（当前范围预先勾选，完成时核对并列出各部门路径，确认后保存，取消则什么都不改）；`directory-scope all` 改为整个通讯录。命令行不接受部门 ID。范围可以同时含上级部门和它的下级，同步时只走一遍。服务先向平台核对每个部门存在且对应用可见，任何一个不通过都不改：平台明确答复部门不属于本组织（已删除或不存在）时说明是哪个部门，网络或平台故障时说明没核对成，稍后重试即可；核对最多等 60 秒。通过后保存到 `data/config/directory.json` 并立即应用：中止正在进行的同步，按新范围完整同步一轮，结果先放在临时名单里，全部成功后在一个数据库事务里一次切换到新名单，不经过上面的撤销阈值，也不会出现新旧混合的名单。切换前之前的名单仍然生效，不在之前名单里的成员收到“同步范围正在更新”的提示，请其稍后重发。这一轮没成（部门遍历失败、冲突、新成员的详情暂时查不到等）时之前的名单保持不变，按上面的间隔自动重试，状态里写明原因；用同一范围再保存一次可立即重试。连续修改时只有最后保存的范围生效，前面没完成的应用随即中止；改回当前生效的范围即取消应用。服务重启后继续应用还没完成的范围。切换后范围外的成员发消息会收到“可能不在机器人同步的部门范围内”的提示，不能再发起新请求；切换前已接收的请求照常完成，范围外成员的会话和统计都保留。整个通讯录保存为 `{"format":1,"all":true}`，同样要显式选择：没有终端时不带参数的 `directory-scope` 不保存任何范围，向导和控制台里什么都不选也不能保存。与已生效的范围相同时不改、不重新同步。没有范围（`data/config/directory.json` 不存在）时服务不同步通讯录，也不按日同步：已同步的映射照常使用，不认识的成员收到“机器人还没有设置通讯录同步范围，暂时无法确认你的身份，请联系管理员”的提示；用上面的方式设置任一范围后立即开始完整同步。`directory` 逐个列出范围内部门的路径：服务沿上级部门逐级向平台查询名称，只读；平台明确答复不属于本组织的部门标为“平台拒绝”，网络或平台故障时整次查询只注明原因，范围照常按 ID 显示。

查看状态：Linux `bash scripts/ops/ops.sh directory`，Windows `scripts\ops\ops.ps1 directory`，或控制台「通讯录」。范围状态有四种：**正在应用**（之前的范围或名单仍然生效）、**已生效**（列出范围、映射数和完成时间）、**应用失败**（之前的范围仍然生效，写明原因和下次自动重试的时间）和**未设置**（不同步通讯录，`doctor` 判为失败）；只是保存了范围不算生效。等待复核的大批缺席和没完成的日常同步同样列出原因和时间，由服务自动处理；长时间没有恢复时按原因检查网络、凭据或开发者后台的可见范围，再查看日志。这些命令经本机管理端口与运行中的服务通信，不另开 Stream 连接；部门列表和范围核对由服务代为查询平台；服务刚重启时实例口令会变，重新查看后再操作。从 1.0.x 升级时，旧版暂停等待确认的撤销不会执行：升级后的服务按上面的规则重新完整同步一轮。

## 一次性容器

Linux 主机没有 Bun 时，运维包装器（统计、历史、临时文件、外链、配置向导等）在容器中执行同一个 CLI：容器在运行就 `docker exec` 进去，否则用正式标签 `mixin-chatbot` 的镜像起一次性容器，以服务容器记录的 UID:GID 运行（没有容器时按 `data/config` 的属主），挂载 `data/`，外置共享资料目录按部署记录只读挂载。部署或升级正在进行、或留有未完成的部署或升级时，正式标签可能仍指向旧镜像，一次性容器会拒绝启动，提示先 `resume` 或 `rollback`；体检此时跳过模型配置校验并注明原因。写操作仍受维护租约限制，机器人运行时会被拒绝。

Windows 包装器使用 PowerShell 原生参数，例如：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 tmp-purge -Days 30 -Group "<群号>" -User "<手机号>"
```

## 会话库的修订整理

会话库为每份文档保存一条修订链：一条基准加之后的增量，读入时从基准折叠。服务每 64 次变更写一次新基准，同时删除旧链；超过 1,024 条的旧长链服务不在线处理（一次提交删除的旧修订太多，会拖慢正常回复），只能停机整理。旧版本从不写基准，所以升级后的会话库可能带着很长的链：读入变慢，也占空间。

**部署和升级时**：停机前在目标版本中只读预览（Docker 只读挂载 `data/`，服务照常运行），列出待整理的文档、修订条数、最长的链和超过上限的旧长链，估计整理用时以及备份和 WAL 需要的空间；停机前的空间检查计入这部分。有需要整理的文档时，终端询问是否停机后整理，默认整理，停机时间相应延长；非交互运行也整理。用 `BOT_REVISION_CLEANUP` 预先决定：`apply`（默认）整理，`skip` 跳过；整理总是先备份，没有不备份的选项。空间不够时停机前就拒绝：释放空间后重试，或显式设置 `BOT_REVISION_CLEANUP=skip`，不会自动改成跳过或省略备份。选择写入事务快照，中断后的继续沿用它。上次整理要求先从备份恢复、收缩尚未完成或整理日志的格式不受支持时，预览就拒绝，服务不停止。平台只补推断开 5 分钟内的消息（见[接入开发者后台](deployment.md#接入开发者后台)），长链很多时可以先跳过，另找时间停机整理；跳过时超过上限的旧长链保持现状，其余的由服务在下次变更时整理。

整理在停机后、数据准备之后、验证实例之前运行，Docker 下在目标镜像中以服务身份运行：

- 每个要修改的会话库先备份到 `backup/revision-cleanup/<运行>/`，核对各表行数和完整性后才开始修改；空间不够时不开始整理，也不会自动省略备份。
- 逐份文档整理：一次提交把整条链换成一条基准（文档原来的版本和当前值），提交后用独立的读数和新打开的会话库核对值不变。整理日志 `data/state/revision-cleanup.json` 记下正在整理的文档、提交前的序号和值的摘要，不记值本身；任何一步中断后都按日志收尾：还没提交就不再写入，已经提交且核对一致就记为完成。
- 提交后的基准与日志记下的值不同时不再写入，整理停止，日志把这个库记为需要[从备份恢复](#从备份恢复)；恢复之前服务、验证实例、回滚和其他改动会话库的维护都拒绝。会话库出现整理无法解释的状态时，整理同样停止，正在整理的文档留在日志里，服务拒绝启动，需要人工处理。
- 在两份文档之间中断：续做沿用原来的备份；期间服务写过某个库或库文件被替换时，上次整理记为跳过，重新整理并重新备份。
- 续做在修改每个库之前，先按记录的 SHA-256 核对沿用的备份。备份损坏或被换过时：会话库在备份之后已有改动，整理就停止，不用整理到一半的库覆盖原备份，之后只能跳过剩余整理或回滚；会话库还和备份时一样，就重新备份后继续。
- 回滚先结束整理（正在整理的文档先收尾）再恢复数据。结束失败时重读维护状态：允许启动才继续回滚，整理日志留给之后的整理核对；有文档尚未收尾、需要从备份恢复或日志无法识别时保持停机，整理日志和备份原样保留，自动回滚不会越过它们。有文档尚未收尾、需要恢复或恢复尚未完成时，服务、验证实例和发布提交都拒绝启动。
- 整理结束后机器人是否启动，不看整理命令的输出，只看之后重读的维护状态；状态读不出也保持停机，并说明原因。整理在部署或升级中停止时，本次部署或升级失败并自动回滚（见上一条）。单独执行时见下文。

整理只改修订链，不改文档的值，也不改使用统计账本。

**单独执行**（升级时跳过了，或整理中断后）：

```sh
bash scripts/ops/ops.sh revision-cleanup preview              # 只读：待整理的长链、预计用时和空间
bash scripts/ops/ops.sh revision-cleanup status               # 只读：当前或上一次整理的状态
bash scripts/ops/ops.sh revision-cleanup apply                # 停机整理（先备份），完成后恢复原运行状态
bash scripts/ops/ops.sh revision-cleanup skip                 # 结束未完成的整理，剩余长链不动
bash scripts/ops/ops.sh revision-cleanup abandon              # 同上，用于回滚之前
bash scripts/ops/ops.sh revision-cleanup restore --space <空间> # 从整理前的备份恢复一个库，见下文
```

Windows：`scripts\ops\ops.ps1 revision-cleanup <preview|status|apply|skip|abandon|restore>`，恢复用 `-Space "<空间>"`。`preview`、`status` 不停机；其余先停机，结束后恢复原运行状态。机器人在运行时先判断维护状态是否允许这个动作，不允许就不停机，直接说明原因。动作结束后只在重读的维护状态允许启动时才启动；留下正在整理的文档、需要从备份恢复时机器人保持停止，按提示重试 `apply`、执行 `restore`，或用 `skip`、`abandon` 结束后再启动。Windows 启动后要等实例身份与就绪检查通过才报告“运行中”，否则只报告“已请求启动”，需要稍后确认。有未完成的部署或升级时，停机执行的动作只接受 `restore`（见下文），其余拒绝。

参数严格核对：未知的参数、别的动作的参数、重复的参数都拒绝，不读不写。脚本调用时 `preview`、`status` 等加 `--json`，标准输出只有一行结果（`protocol`、`version`、`command`、`outcome` 和 `result`），说明写到标准错误；只有退出码 0 且结果完整、`outcome` 为 `success` 才算成功。退出码：0 成功，3 整理停止，4 空间不足，1 其他。

确认整理后机器人运行正常，再用[历史归档清理](#历史归档清理)删除 `backup/revision-cleanup` 下的备份；尚未结束的整理所用的备份拒绝删除。

### 从备份恢复

整理发现某个库提交后的基准与日志不同时，这个库需要从整理前的备份恢复；在那之前服务、验证实例、回滚和其他改动会话库的维护都拒绝。恢复入口一直可用，但只有下面的核对全部通过才执行，否则拒绝、不做改动，库和整理日志原样留给人工检查：

- 现场能完全由这次整理解释：库文件和 Durable schema 与日志记录的相同；备份之后的每个提交序号都恰好对应日志里的一份文档，每份只有一条基准，值的摘要与日志相同（出错的那份等于发现不符时记下的摘要）；没有新建或退役的文档。提交次数相同本身不能证明这些提交来自整理。
- 备份逐字节复制成副本，大小和 SHA-256 等于日志记录；再核对完整性、Durable 元数据和各表行数与备份时相同。

然后按收缩的替换方式换上副本：当前库连同 `-wal`、`-shm` 改名为同目录的 `durable.sqlite.restore-<运行>.old` 留作现场，副本换到正式路径后再快速检查。中断后再次执行 `restore`，没换上的副本作废、已换上的完成核对。完成后这个库回到整理前的样子（旧长链还在），整理仍是停止状态：之后用 `skip` 跳过剩余整理，或回滚。

有未完成的部署或升级时（整理在升级中发现不符，自动回滚在恢复数据之前停止），`restore` 不改动事务：由运维核心用事务固定的版本执行（Docker 用事务记录的候选镜像和服务身份），要求事务已经开始执行、数据步骤尚未结束、机器人已停止。恢复后再回滚（`rollback`，会先结束整理）或继续（`resume`）。

### 收缩会话库文件

整理删除的旧修订在库内变成空闲页，供以后的写入复用，文件不会变小。要把这部分空间还给磁盘，另找维护窗口执行收缩；它不属于部署和升级，默认不执行。

- 先预览：每个库的文件大小、使用中的页、空闲页（可回收的量）和 WAL，以及所在卷需要和可用的空间。空闲页不足 1 MiB 的库不收缩。所需空间按使用中的页加 WAL 估计，同一卷上的库累加（保留的原库删除前一直占着空间），另留 1 GiB 余量；空间不够时不开始。
- 收缩停机执行，逐个库进行：先把 WAL 并入库文件并关闭连接；用 `VACUUM INTO` 在同一目录写出紧凑的副本，核对完整性、Durable 元数据、各表行数和每一行内容都与原库相同、没有空闲页；然后把原库改名为同目录的 `durable.sqlite.shrink-<运行>.old`（连同它的 `-wal`、`-shm`），把副本改名为 `durable.sqlite`，再做一次快速检查。读两遍原库、写一遍副本，用时随库的大小增长。
- 每一步先写收缩记录 `data/state/shrink.json`。中断后再次运行 `shrink`，先按记录和实际文件恢复：副本还没换上就删掉副本；已经换到一半就继续；副本不可用就把原库放回原路径。副本已经换上时，它必须与核对过的副本逐字节相同，旁边的 WAL 里也不能有新写入；否则停止，原库和收缩记录原样保留。记录与文件对不上时停止，不做任何改动，机器人保持停止，需要人工处理。有库尚未替换完成时，服务、验证实例、修订整理和部署升级都拒绝启动。
- 保留的原库就是收缩前的备份，不另做备份。确认机器人运行正常后用 `shrink-remove-old --yes` 删除；删除之前，回收的空间还没有还给磁盘。

收缩只改库文件的存放方式，不改任何文档的值，也不改使用统计账本。

```sh
bash scripts/ops/ops.sh revision-cleanup shrink-preview                 # 只读：可收缩的库、可回收和需要的空间
bash scripts/ops/ops.sh revision-cleanup shrink                         # 停机收缩（先恢复上次未完成的），完成后恢复原运行状态
bash scripts/ops/ops.sh revision-cleanup shrink --space <空间>           # 只收缩预览列出的这个空间，可重复
bash scripts/ops/ops.sh revision-cleanup shrink-status                  # 只读：上次收缩的状态与保留的原库
bash scripts/ops/ops.sh revision-cleanup shrink-remove-old              # 列出保留的原库；加 --yes 删除
```

Windows：`scripts\ops\ops.ps1 revision-cleanup <shrink-preview|shrink|shrink-status|shrink-remove-old>`，选空间用 `-Space "<空间>,<空间>"`，删除加 `-Yes`。`shrink-preview`、`shrink-status`、`shrink-remove-old` 不停机；`shrink` 先停机，结束后恢复原运行状态，有未完成的部署或升级时拒绝执行。收缩留下未替换完成的库时机器人保持停止，再次运行 `shrink` 完成恢复后再启动。

## 磁盘保留

| 内容 | 保留策略 |
| --- | --- |
| 配置、SQLite 状态库、共享资料 | 持久保存，纳入停机备份（外置共享资料目录由管理员另行备份） |
| Pi 设置与模型目录缓存 | `data/runtime/pi/settings.json` 与 `data/runtime/models-store.json` 随配置备份；动态目录服务商需缓存才能离线启动 |
| 使用统计账本 | `data/state/stats.sqlite` 持久保存，纳入停机备份；清空会话不影响它，删除会丢失历史账目；空间库中已清理的请求记录和已删除的会话库只留在账本，恢复旧备份的账本也会丢失这部分数字 |
| 空间库 | `data/conversations/{direct,groups/<群>}/durable.sqlite`（及 `-wal` 等）持久保存成员的对话、排队消息和控制命令，纳入停机备份；`/clear` 和 `history clear` 只开启新上下文，不删除旧上下文，也不释放空间 |
| 部署备份 | 部署和升级成功后只删除本次快照和 `backup/rm/<快照名>`；失败操作保留现场，其余快照和归档用历史归档清理处理 |
| 修订整理备份 | `backup/revision-cleanup/<运行>/` 保存整理前的会话库，不自动删除；确认整理后机器人运行正常，用历史归档清理删除 |
| 收缩保留的原库 | 会话库目录中的 `durable.sqlite.shrink-<运行>.old`（及 `.old-wal`、`.old-shm`）是收缩前的会话库，不自动删除；确认收缩后机器人运行正常，用 `revision-cleanup shrink-remove-old --yes` 删除 |
| 恢复留下的现场 | 会话库目录中的 `durable.sqlite.restore-<运行>.old`（及 `.old-wal`、`.old-shm`）是从备份恢复之前的会话库，留作排查，不自动删除，也不由 `shrink-remove-old` 删除；排查结束、机器人运行正常后手动删除 |
| 测试与诊断现场 | 放在顶层 `tmp/`，确认没有测试、诊断或维护任务使用后可清理 |
| 控制台统计报表 | 导出直接下载到浏览器，服务器不保留；需要长期保存时另行保留 |
| 上传快照 | 完成、失败或取消后直接删除 |
| 应用日志 | 约 5 MiB 轮转，当前文件加 3 份备份，最旧备份直接删除 |
| 升级、格式登记与启动诊断 | `logs/operations/` 保留最近 20 份，每份约 2 MiB；命令输出约 1 MiB 后为后续阶段与错误保留空间，回滚保留日志 |

归档不会立即释放磁盘空间，部署快照可能含凭据。应用日志常规预算约 20 MiB，运维诊断约 40 MiB，单条日志可使文件短暂超限；强制终止留下的临时现场需离线清理。

### 历史归档清理

`backup/rm`、`backup/snapshots` 中不属于某次成功操作的内容，以及 `backup/revision-cleanup` 中的修订整理备份，不会自动删除，用专门的入口分两步处理：

1. `ops.sh backup-scan`（Windows：`ops.ps1 backup-scan`）只读扫描这三处的顶层条目，在 `tmp/backup-cleanup/<报告名>/` 写出 `manifest.json` 和便于查看的 `manifest.tsv`，列出每条的路径、大小、分类、分类依据和建议动作，不删除任何内容。`backup/` 中其他目录不扫描，会在输出中列出。
2. `ops.sh backup-clean <报告名>`（Windows：`ops.ps1 backup-clean <报告名>`）预演：逐条重新检查清单中选为删除的条目，列出将删除、扫描后有变化、拒绝等结果，并给出确认码，不删除任何内容。确认后加 `--confirm <确认码>`（Windows：`-ConfirmCode <确认码>`）执行，结果写入同一报告目录的 `result-*.json`；`result-*.tsv` 逐条追加，进程中断时也留有已处理条目的记录。

| 分类 | 判断依据 | 建议动作 |
| --- | --- | --- |
| 可确认测试数据 | 名称是测试夹具的归档格式 `<夹具名>-<UUIDv4>`（旧版测试辅助函数的命名，运维归档从不这样命名），且内容里有测试证据：夹具目录自己的随机名称、测试临时目录路径、至少 1 MiB 的单字节填充文件，或 RFC 6761 保留的 `.test` 域名 | 删除 |
| 疑似测试数据 | 名称符合测试夹具格式，但没有找到内容证据 | 保留，工具不删除 |
| 业务归档 | 运维归档格式（时间或 GUID 开头）、事务目录 `deploy-*` 及其快照、修订整理的运行目录（整理前的会话库备份） | 保留；确需删除时先另行备份，再把 `manifest.json` 中该条的 `action` 改为 `delete` |
| 无法判断 | 条目本身或内部含链接、有无法读取的部分，或名称不符合任何已知格式 | 保留，工具不删除 |

名称只是线索，内容证据不足的一律保留。执行时只处理清单中 `action` 为 `delete` 的条目，删除前逐条重新检查：

- 路径必须是 `backup/rm`、`backup/snapshots` 或 `backup/revision-cleanup` 下的单层条目，`backup` 和这三个目录不能是链接；
- 条目本身和内部都不能有链接，工具从不跟随链接；
- 每个普通文件都必须能完整读取；有不可读文件时整个条目保留，业务归档也适用；
- 内容指纹（每个节点的相对路径、类型、大小、修改时间、设备号、inode，以及每个文件完整内容的 SHA-256）必须与扫描时一致。即使文件原地改为相同长度并恢复修改时间，也会跳过；重新扫描后再决定。扫描和复查采用分块读取，内存不随大文件大小增长。

清单记录每个文件的内容摘要；格式不符、无法据此复查的清单不能预演或删除，需要重新运行 `backup-scan`，审阅新清单并获取新确认码。

部署、升级或另一个维护操作正持有部署锁时，以及有未完成的部署或升级时，拒绝执行；未完成事务引用的快照与归档、尚未结束的修订整理所用的备份始终拒绝删除。`manifest.json` 中除 `action` 以外的字段被改动，或确认码与当前清单不符（预演后又改过清单）时，整份清单不执行。删除不可撤销，也不能用 Git 找回。Docker 部署在容器内执行清理；遇到容器用户无权删除的文件时，该条目记为“删除失败”，可能已部分删除，其余内容留在原处。

## 旧入口退役

当前版本主动连出事件 Stream，不需要入站入口。旧版 webhook 发布的 UFW 直连规则、Windows 防火墙规则、cloudflared 连接器和 Cloudflare 隧道由管理员在切换时退役，步骤见[从旧版 webhook 发布切换](data-migrations.md#从旧版-webhook-发布切换)；当前程序不识别、也不自动处理这些旧入口。在各群把旧的自定义机器人换成应用机器人，见[接入开发者后台](deployment.md#接入开发者后台)。

## 应用机器人凭据

凭据保存在 `data/config/app-bot.json`。更换 AppSecret 或换成另一个应用时，在控制台 **设置 → 应用机器人凭据**，或运行 `configure-app-bot`：控制台的校验和向导都先用新凭据取得一次访问令牌验证（不连接 Stream，不和运行中的服务抢连接），确认后由运维核心短暂停止机器人、替换配置并恢复原运行状态，写入或启动失败时恢复原配置；取消或验证失败时原配置不变。换应用或环境后通讯录映射随新应用重新同步，期间未同步到的成员会收到提示；新应用同样要在开发者后台选择 Stream、验证连接并保存、勾选事件、提交并发布版本，再加入各群（见[接入开发者后台](deployment.md#接入开发者后台)）。

## 高级运行参数

在控制台 **设置 → 高级运行参数** 中修改。参数分为并发与附件、收到提示、超时与退出、缓存与索引、文档处理五类；默认值和数值范围与机器人共用定义。本机端口、监听地址及共享资料目录属于部署设置，不在这里修改，见[本机管理端口](deployment.md#本机管理端口)。

留空表示恢复默认，会移除对应的 `runtime.json` 覆盖项；未编辑的参数保持原值。点“校验并预览”列出全部改动，确认后执行；“重新读取”放弃表单中的改动。放弃的预览留下的草稿文件在一天后的下次预览时清理。

配置读取不启动 Docker、模型或网络探测。确认后作为后台任务执行，维护页显示进度：先校验草稿、环境覆盖及服务归属，再短暂停止原本运行中的机器人；写入后恢复并检查健康状态。已停止或尚未部署时只保存，保持停止状态。应用或健康检查失败会尝试回滚，恢复也失败时，恢复材料保留在 `data/config/.config-*`，处理方法见上文的配置恢复。

显式环境变量仍优先于保存值。Windows 检查当前运维进程的环境，Linux 检查既有容器的相关环境变量；被覆盖的修改会在停机前拒绝。自定义 Windows 启动脚本还需检查其单独设置的环境变量。配置在编辑期间被其他操作修改时，本次保存会拒绝覆盖；放弃草稿后重新读取再编辑。

## 配置可选的大文件外链

在控制台 **设置 → 外链配置** 查看和修改（显示是否启用、桶、对象路径和期限，不显示凭据），或运行 `relay-configure` 向导；测试、查看与清理在控制台的 **外链** 页。使用兼容 S3 的私有桶及限时 GET 下载链接，默认下载有效 2 小时，额外保留 30 分钟后清理。配置项、厂商参考及云端准备见[大文件外链配置](deployment.md#大文件外链配置)。

填写期间机器人继续运行，访问密钥和临时 Token 均隐藏输入；保存预览确认后，由运维核心与网页配置相同地发布：原本运行中的服务才短暂停止、写入配置并恢复，写入或启动失败时恢复原配置。原本停止的服务保持停止，取消不变更配置和服务；停用时删除 `relay.json`，账本和云端文件保留。命令行入口是 `relay-configure`。这里仅校验配置格式，不上传测试文件，不修改云端桶权限。向导会按腾讯 COS、AWS、R2 的端点预填区域；Virtual hosted 下端点已含桶名时，提示改成不含桶名的服务端点。`doctor` 只读检查 S3 必填项，并明确提示尚未验证云端权限；不能凭此认定下载和删除已可用，请用下面的外链测试验收。

### 测试外链

运行 `bun run relay test`，或在控制台「外链」页点 **测试外链存储**；没有宿主机 Bun 的 Linux 部署用 `bash scripts/ops/ops.sh relay-test`，Windows 用 `scripts\ops\ops.ps1 relay-test`。测试不需要停机，用当前配置上传一个 8 MiB 的随机文件 `外链自检-*.bin`，依次检查：上传及大小核验、签名链接下载且内容一致、去掉签名后被拒绝（桶未公开）、下载链接不能用于删除、删除对象并移除账本记录、删除后链接失效。拒绝、失效两类检查只认明确的 4xx 答复；服务端 5xx、408 超时、429 限流或网络错误无法证明权限和删除状态，按未通过处理，稍后重试即可。任一项失败时退出码为 1；结果不打印预签名 URL 或云端原始响应。

测试同时按本次上传速度粗估上传单文件上限所需时间。超过单次上传的 30 分钟限时会给出提示，可调低单文件上限或改善上行带宽；小文件测速受连接建立影响，结果偏保守。测试对象和真实分享一样先登记账本再上传，中断或删除失败时由后台按计划重试清理。修改配置、云端访问策略、生命周期或版本控制后都应重新测试。

### 查看并验证下载链接

在部署目录运行 `bun run relay list`，或打开控制台「外链」页（自动列出，不显示链接）。列表展示上传状态、下载到期时间和计划删除时间。未过期对象在 `bun run relay list` 的输出里重新签发剩余期限内的链接；查看与重发不会续期。过期、上传未确认或不属于当前后端的记录只显示存储地址，不是可用下载链接。

验证下载使用完整的 GET 预签名 URL。不要把它直接改为 HEAD 请求：S3 V4 签名绑定请求方法，机器人探测文件大小时会单独签发 HEAD。发生 403 时检查凭据、区域、时间同步及签名/权限配置；发生重定向时修正 endpoint，本实现不跟随重定向。日志不打印预签名 URL 或云端原始错误响应，避免泄露临时访问授权。对象设置 `Cache-Control: private, no-store, max-age=0`，并保留原文件名作为下载附件名。

实际接入新厂商时，用非敏感测试文件验证：上传成功且下载字节一致；无签名访问失败；修改请求方法失败；短期限链接过期后不能重新发起下载；删除余量内对象仍存在、随后可被清理。云端权限和访问策略最终以这项验收为准。链接到期不会召回已下载的数据；到期前已建立的连接是否继续传输由对象存储服务决定。

### 清理对象

运行 `bun run relay purge --keyword <关键字>` 或 `bun run relay purge --all`，也可使用控制台“外链”页的清理操作。手动清理要求服务停止并取得维护租约，会提前使匹配的链接不可用；只删除账本中明确归属当前后端的精确对象，不按前缀递归删除桶内内容。删除失败、不匹配记录均保留。

自动清理在服务启动时和每 5 分钟尝试运行，按账本的计划删除时间处理，失败重试。停机或停用外链期间依赖云端生命周期兜底；切换存储后旧端点对象不会交给新配置删除。停止使用一个桶前，先用原配置完成清理。不要直接丢弃账本：它是失败上传及未删对象的回收依据。

## 重新配置模型

模型配置使用 `data/config/models.json` 的 Pi 原生 `providers` 和 `data/runtime/pi/settings.json` 的 `defaultProvider` / `defaultModel` / `defaultThinkingLevel`。日常更换模型可在控制台「设置 → 模型配置」，或运行 `model-configure`：向导在机器人照常运行时填写，确认后由运维核心短暂停机写入并按原运行状态恢复，写入或启动失败时恢复原配置；有未完成的部署或升级时拒绝执行。旧配置需要重建时，先停机并将这两个文件及 `data/runtime/models-store.json` 归档到 `backup/rm`。Windows 部署随后运行 `bun run configure`，有未完成的部署、升级、运维任务或配置事务时它会拒绝；Docker 部署重新运行部署脚本，由镜像内的向导生成配置，再以服务身份写入（不要在宿主机上直接运行 `bun run configure`，否则文件属于运行它的账户，容器可能读不了）。`backup/rm` 不是长期存储，需要长期保留的配置副本请另行备份。

凭证由 Pi 从 `models.json` 解析，支持直接 Key、环境变量引用和命令引用；磁盘 `auth.json` 不参与解析。运行中的模型、设置及目录使用启动时的只读视图，更改配置后需重启。共享资料目录中的 `.pi/settings.json` 不参与配置；重试、自动压缩开关及遥测策略由应用固定，编辑 Pi 设置也不会覆盖这些策略。

向导先在暂存目录中刷新所选服务商的模型清单、写入 Pi 设置并完成离线校验，再提交配置和缓存。取消不会更改当前文件；提交过程中发生错误会恢复原文件。服务商的扩展字段及同一端点、同一模型的原生字段会保留；选择推理级别时，会清除所选模型的 `modelThinkingLevels` 覆盖，保证启动后使用本次选择。

Pi 目录刷新遵循 `PI_OFFLINE`：设置此环境变量时使用随包目录和已有缓存；未设置时可联网刷新。该开关不禁止自定义端点的模型清单探测。机器人启动和 `doctor` 都只读本地目录，动态目录服务商缺少缓存时需重新运行向导联网刷新。

改完用 `bash scripts/ops/ops.sh doctor`（Windows 用 `scripts\ops\ops.ps1 doctor`）确认「模型配置（models.json + Pi 设置）」一行通过再启动。部署快照同时保存 `data/config`、Pi 设置和模型目录缓存。

## 任务收尾与失败交付

任务默认总时限 20 分钟，剩余 5 分钟进入收尾，最后 2 分钟只允许读取、登记和发送。所有阶段的 bash 都按“剩余时间减交付保留时间”限制执行时长，未指定 timeout 时仍不超过 `BOT_BASH_TIMEOUT`。每次模型请求都会附带当前剩余时间；服务重启后沿用原截止时间。生成文档后应先 `deliverable_register` 登记草稿，再检查、修正、登记检查范围并发送，避免反复重建耗尽时限。

总超时、模型静默、单次响应超时和最终模型错误都会尝试交付登记快照：每个交付物优先选择可用的最新 checked 版本，否则选择最新 draft。已拒绝、结构不完整、摘要改变或未登记的文件不会自动发出。草稿会明确标注未完成全部检查，检查范围按登记内容列出。`/stop`、`/clear` 不触发自动发送；发送中的请求可能已到平台，余下文件停止自动发送。

兜底先发送说明，再发送文件，使用独立的 2 分钟预算；没有文件要发时，失败说明和普通回复一样重试 6 小时。本轮已生成的外链及其续签数据会并入说明，发送前刷新，同一文件不再另发一次。说明没有发出时不发文件。平台明确拒收的部分在预算内自动重试；结果不确定的附件视为已发，不再重发；普通发送（不在兜底计划里）结果不确定时，应先查看群消息，未收到再在新消息中要求重新发送。重启后的自动恢复沿用原发送截止时间，超过预算后放弃，并在服务日志写一条“交付超时放弃”。`/stop`、`/clear` 撤回的计划不再发送。每个请求的回复对象（会话、提问人、摘要）随请求持久保存，重启后的发送和重发仍回到原会话。未完成计划的快照受临时文件回收保护，不要手工删掉 `.deliverables`。

收尾、交付保留和兜底发送的时长由运行配置 `BOT_CLOSEOUT_SECONDS`（默认 300）、`BOT_DELIVERY_RESERVE_SECONDS`（默认 120）、`BOT_FALLBACK_SEND_SECONDS`（默认 120）决定，也可在控制台「设置」中修改，重启生效。启动校验要求：交付保留 < 收尾 < 总时限的一半。控制台“会话”页的交付详情显示待发送和结果不确定的消息。

资料检索优先使用 `materials_find`、`materials_grep`，它们直接读取索引、纯文本和已提取文本，不创建进程。每次检索最多读取一遍解析缓存目录；缺少来源记录的缓存条目不在检索中逐个哈希原文，按缺少有效缓存报告；对需要的文件调用一次 `document_extract` 核验并登记，命中缓存时不会重新解析。`notIndexed` 表示缺少有效缓存；`incomplete` 表示本次未检查完。日志 `检索耗时` 带成员、任务号、工具、文件数和命中数。DOCX 的 `document_images` 支持标题、图注、段落前后文，`extract:false` 仅查看元数据，`orders` 定向提取，`after` 分页。

## 临时产物维护

控制台的“临时文件”页先保存真实预览，显示可归档、保留和待处置条目，确认后执行同一清单；“预览物理回收”和“预览删除归档”同样先生成独立清单，核对后确认，两者都不可撤销。预览（`tmp-preview`，以及不带 `--digest` 的 `tmp-reclaim`、`tmp-discard`）只读取、只写清单，服务运行时也可执行，不停机；`tmp-purge` 和带 `--digest` 的确认由 ops 包装命令取得部署锁，拒绝未完成的部署事务，维护期间停止服务，结束后恢复原运行状态。直接运行 `bun run tmp` 的确认命令前需自行停机；维护租约不能替代停止服务。预览与确认之间内容有变化的条目在确认时保留。

归档示例（Linux 包装器；Windows 用 `-All`、`-Plan`、`-Digest`）：

```sh
bash scripts/ops/ops.sh tmp-preview --all
bash scripts/ops/ops.sh tmp-purge --plan <预览ID> --digest <预览摘要>
```

默认归档目录是 `data/state/reclamation/backup/rm`，要求与源文件同一文件系统；归档字节不算释放空间。失败时保留清单、目标和进度，用原 ID 与摘要重试，不重新生成计划覆盖失败记录。数据备份不包含归档内容，只包含其清单（`.tmp-plans`）。

归档的永久删除同样先预览再确认：

```sh
bash scripts/ops/ops.sh tmp-discard
bash scripts/ops/ops.sh tmp-discard --plan <删除清单ID> --digest <摘要>
```

删除清单只列出由归档清单及其进度证明、确为本工具移入且内容与归档时一致的条目；有变化的条目保留，已不存在的条目报告为缺失，不视为已删除。隔离任务的产物由任务管理端删除：删除前先保存一份列出全部条目的删除日志，中途失败后用原清单或新预览重试，只在剩余条目都属于这份日志且未改变时续删，否则保留。Windows 的目录、文件和链接都持删除句柄删除。Linux 服务身份写入的归档的目录、文件和链接与 `tmp-reclaim` 相同，需要宿主 UID 0 的独立停机维护身份，以 `bun run tmp discard --legacy --journal <宿主私有目录> --recorded-root <服务看到的数据目录>` 执行，否则列为待处置。历史 `backup/rm` 中不是由本工具归档的内容，永久删除仍需独立清单与确认。

`tmp-discard` 和 `tmp-reclaim` 执行后报告的是这份清单至今的累计结果，不是本次执行的增量；重复执行同一清单、再次看到同样的数字，不表示又释放了空间。隔离任务的产物如果在本清单处理到它时已被删除（例如上次执行在删除后中断，或另一份清单已删完），只补完记录，报告为“收尾”，不计入已删除的项数和字节；无法确认是哪次执行删除的，宁可少计，也不重复计入。

已登记产物的物理回收先运行 `tmp-reclaim --all` 预览，再以 `tmp-reclaim --plan <ID> --digest <摘要>` 确认。Linux 服务身份写入的产物（不在隔离任务中产生的条目）另需宿主 UID 0 的独立维护，先停止服务并保持停止，在项目根目录直接运行 `bun run tmp reclaim --all --legacy --journal <宿主私有目录> --recorded-root <服务看到的数据目录>`；Docker 服务看到的数据目录是 `/app/data`。事务目录及全部祖先必须为 root 所有且其他身份不可写，不能放在 `/tmp`、`/var/tmp` 或共享项目中。

核对后以同一 `--legacy`、`--journal`、`--recorded-root` 和计划 ID/摘要执行。该入口先冻结原目录写权限，才允许按已审实体删除；中断后可能保留冻结权限，必须按原计划续做，确认完成再恢复服务。同一父目录或条目还有未完成的特权事务时，新预览把相关条目列为待处置并写明原清单或计划 ID，执行时会再次检查并拒绝以新清单接管；用原清单和同一事务目录续做即可。冻结或交还权限在改属主与改权限之间中断时，父目录会是 root 所有、但仍保留原权限位（例如 0750）；因此父目录只要为 root 所有且没有粘滞位，无论权限是 0700 还是别的值、换用哪个事务目录，都不会被新清单接管，也不会被记为原权限，需先核对冻结来自哪次操作，再用原清单和原事务目录续做。合法的 root 所有父目录只有带粘滞位的系统临时目录；服务身份所有、却带粘滞位的父目录会被拒绝冻结。已记为删除完成的条目重做时仍会核对其特权事务，按原事务记录恢复父目录权限；原位置若又出现同名条目，保留待核对，不会删除。rootless 容器内的 UID 0 不满足条件，ops 包装器拒绝转发 `--legacy`。未知来源、引用未释放、实体变化或旧容器 `/tmp` 已消失的对象仍保留待核对。

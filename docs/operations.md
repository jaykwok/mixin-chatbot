## 命令行运维

成员上下文也可从管理台“会话”页按 `p` 登记压缩，或运行 Linux `scripts/ops/ops.sh history-compact <群号> <成员号码>`、Windows `scripts/ops/ops.ps1 history-compact <群号> -User <成员号码>`。运维入口先停机取得独占群库，再登记任务并恢复原运行状态；原本停止的实例不会被自动启动。压缩由机器人运行后生成摘要，会产生模型用量，成功后仍保留历史和已有费用。聊天里的 `/compact` 可直接执行。

Durable 成员的临时目录包含历史引用与待补发文件。`tmp purge` 会先停机取得维护租约，生成带摘要的清单，再把已核对且未被引用的条目原子移入群根 `.reclamation/backup/rm`；它会逐项报告已归档、保留、待处置和失败数量，归档本身不会立即释放磁盘空间；`tmp discard` 按归档清单永久删除这些条目、释放空间。`tmp reclaim` 用于物理回收：Windows 持有删除句柄并保存可续做清单，Linux 旧共享目录必须由宿主 UID 0 的独立停机维护身份显式执行，普通 ops 包装器不会自动恢复这类特权操作。来源不明、内容或实体变化、仍有引用的目录都会保留。常规结果回收由机器人在成员空闲且引用释放后执行。整包备份和暂存恢复流程见[数据目录与备份](deployment.md#数据目录)。

日常交互操作从[运维界面](tui.md#运维界面)进入。这里保留命令行入口，便于脚本调用和没有装 Bun 的 Docker 宿主机使用；排查与数据维护步骤见本文后面的对应章节。

### 日常控制

在项目根目录选择对应平台的命令行入口。

Windows：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 doctor
```

Linux / Docker：

```sh
bash scripts/ops/ops.sh doctor
```

将示例中的 `doctor` 替换为所需命令：

| 命令 | 用途 |
| --- | --- |
| `doctor` | 检查配置、实例、群数据根及已配置的网络入口；加 `--json`（Windows 为 `-Json`）输出单行 JSON |
| `start` / `stop` / `restart` | 启动、正常关闭或重启实例 |
| `logs` | 持续查看日志 |
| `tunnel-logging off\|on` | 关闭或开启隧道文件日志，应用时重启正在运行的本项目隧道 |
| `tunnel-protocol auto\|http2\|quic` | 设置隧道连接模式，默认 auto，应用时重启正在运行的本项目隧道 |
| `tunnel-update` | 将项目中的 cloudflared 更新到官方稳定版，下载校验后切换，失败恢复旧程序及运行状态；需宿主机 Bun |
| `update` | 同步 origin/main，由目标版本的升级器在停机前完成确认后升级，保留原运行或停止状态 |
| `deploy` | 部署当前代码；可重新配置并重建现有部署，失败恢复原部署 |
| `resume` | 按事务记录继续中断的部署或升级，不重新提问 |
| `rollback` | 回滚中断的部署或升级；数据已提交时拒绝 |

`update` 要求已跟踪文件没有本地改动，代码已最新也会检查数据版本。它先处理未完成的部署或升级（见[中断恢复](#中断恢复)），此时不拉取；否则拉取 origin/main，从目标提交导出升级器（Windows 为 `tmp/upgrade-<GUID>`，Docker 为 `tmp/upgrade-<随机>`），在工作区外由目标版本完成升级，结束后删除导出目录。两个平台都在停机前预览迁移并询问需要的迁移决策，然后才停止旧实例、切换工作树或安装依赖。rootful Docker 的 `update`、`resume`、`rollback` 要由 root 运行，rootless Docker 由其所属用户运行，都在任何提问之前检查（见[选择部署方式](deployment.md#选择部署方式)）。升级沿用已保存的端口、入口模式、群数据根、域名和 AI 配置，停机后不再询问；修改这些配置请使用 `deploy`。Docker 升级器还在停机前确认未托管 Cloudflared 的归属，缺少连接器和可用 token 时先收集 token，只在本次升级中交给部署脚本，在验证实例就绪后启动一次；停机前从目标提交（不含工作区改动和未跟踪文件）构建一次镜像，按 image ID 固定并用本次独占的保留标签防止被清除，构建期间原服务照常运行；随后在这个镜像中以原服务的身份、断网、只读挂载数据预览迁移并校验配置，宿主机无需安装 Bun；停机前再复核一次：检出与升级开始时核对的不同（提交、分支、main 的位置，或已跟踪文件有了改动，例如构建期间改了文件），预览后配置或版本标记有变化，原容器被删除或替换，候选镜像或保留标签被改动，或剩余空间不够写快照，都停止，服务不受影响。两个平台切换代码都是先 `checkout main` 再快进到目标提交：升级开始时（Docker 在构建之前）和停机前复核时（Windows 在保存部署快照之后）都按这条路径（当前检出 → main → 目标提交）预演，续做也一样，Windows 同时核对已跟踪文件没有改动、本地 main 能快进到目标提交。会被覆盖或删除的未跟踪内容逐项列出并停止——目标提交或途经的 main 新增路径上已有的文件，含未跟踪文件的目录，占着新增路径上级目录位置的文件或链接（Windows 含目录联接），也包括被 `.gitignore` 忽略的文件（git 切换时会直接覆盖或随目录删除它们）。当前提交跟踪的链接或文件被改成目录时，git 直接替换它，不算冲突，链接指向的内容也不当作这些路径上的文件。预演只读，不改索引、工作区和这些文件；脚本不移动、不删除它们，由你移出工作区（或提交到其他分支）后重试。构建或预览被 Ctrl+C 或发给 `ops.sh` 的终止信号打断时删除预览容器和本次的保留标签并退出，服务没有停止，代码和数据不变；清理在独立的进程组中进行，期间再次中断（终端的 Ctrl+C、断线）不会打断它。停机后迁移、验证实例和正式实例都按记录的 image ID 运行，中断后的继续和回滚也用它，不再构建或拉取；镜像已被清除时拒绝继续，只允许回滚尚未开始迁移的操作。正式标签 `mixin-chatbot` 在数据提交、新实例就绪后才指向新镜像，发布失败时保留事务，可用 `resume` 重试；当前终端里的端口、入口、群根、域名和运行参数环境变量不会被采用，会提示已忽略；`update`、`resume`、`rollback` 的入口也不校验这些环境变量，升级结束后的体检按保存的设置进行。已登记的群数据根（包括默认的 `data/groups`）缺失时，升级在停机前停止，不会重新创建空目录。rootless Docker 发布不了已保存的低端口时（见[选择部署方式](deployment.md#选择部署方式)），升级同样在停机前停止并提示处理方法。缺少 `data/config/models.json` 时拒绝升级，需先通过 `deploy` 完成配置。需要迁移时先备份再转换，随后使用只验证实例检查，提交后恢复原运行状态。同版本且标记配对时跳过数据迁移和数据库备份，仍做配置、schema 和新实例校验。提交前失败恢复数据、原提交和部署；提交后启动失败保留新代码与数据，检查日志后重试。Docker 首次升级到本版需运行一次引导命令，见[第一次升级](data-migrations.md#第一次升级)；中断后的处理见[中断恢复](#中断恢复)。

升级与迁移失败时，按终端打印的路径查看 `logs/operations/` 下的日志；其中包含失败阶段、异常、退出码与回滚结果。服务早期启动错误写入同目录的 `startup-*.log`，详见[失败日志](data-migrations.md#失败日志)。Docker 升级和部署的日志分别记录候选镜像的构建耗时（`candidate build took …s`，这时原服务仍在运行）和实际停机窗口：从停止原服务（`service stopped; downtime begins`）到新版本通过健康检查或回滚后原容器重新启动（`service back (…); downtime …s`）。中断后在新进程中续做时，停机若发生在之前的进程，只记录恢复的时刻；中断在事务指针发布之后、停止服务之前时，由续做的进程停止服务并从那里开始计时。构建会与原服务争用 CPU、内存和磁盘，停机前的准备不等于对原服务没有影响。

Windows `update` 会显示更新前后的提交 hash。依赖清单、锁文件、安装配置和补丁未变，且已安装的直接依赖版本匹配时，会保留 `node_modules` 并跳过安装；缺包、版本不匹配或依赖输入发生变化时，才备份旧依赖并按锁文件安装。版本更高也不视为匹配，避免偏离经过验证的依赖组合。

部署、升级和连接器安装的备份放在 `backup/snapshots/<快照名>`，操作期间被替换的旧文件放在 `backup/rm/<快照名>`；旧会话文件、用户 tmp 等日常归档直接放在 `backup/rm` 下。成功后只删除本次操作自己的快照和 `backup/rm/<快照名>`；迁移副本在正式业务实例通过健康检查后按清单清理，详见[事务边界](data-migrations.md#事务边界)。清理失败不阻断后续升级，独立回执供重试；启动失败或保持停止的实例保留迁移副本。新建快照时会避开 `backup/rm` 中已有同名目录的名称，快照、归档或其上级目录是链接时拒绝清理。没有自动清理标记的历史迁移快照、其他事务目录和散落归档保留，由[历史归档清理](#历史归档清理)审查处理，不清空整个 `backup/rm`。操作失败时保留回滚现场。Windows 会移除空的 `backup` 目录；Linux 保留空的容器挂载目录，避免运行中的容器丢失后续归档。部署锁保存在 `data/state/deploy.lock`。Docker 部署和升级在构建新镜像前，先给原容器使用的镜像打上 `mixin-chatbot:previous` 标签，事务提交或回滚完成后再移除。Docker 29 起新装默认使用 containerd 镜像存储，它会删除失去最后一个标签的镜像，回滚要靠这个标签恢复原镜像。

关闭服务使用 `stop`：Windows 验证实例身份后先请求优雅关闭，超时再复核归属并终止进程树；Linux 使用 Docker 停止期限。

### 中断恢复

部署或升级在停机前把已确认的选择写入快照目录的 `transaction` 记录，再发布事务指针：操作类型、目标提交、升级前的提交与分支、原群根与目标群根、原运行状态、端口、入口模式、域名及其写回方式、未托管 Cloudflared 的确认、直连防火墙放行的平台来源 IP（`PLATFORM_IP`）。隧道 token 不写入记录。Docker 另在同一目录写入 `candidate-image`（本次镜像的 ID、保留标签和所在的 Docker daemon）和 `service-user`（服务的 UID:GID），`transaction` 的格式和键不变，旧版恢复入口照常读取。继续和回滚先核对这两份记录，再检查数据是否已提交或运行任何容器：Docker daemon 与开始时不同（例如切换了 context 或 socket）时两者都拒绝；记录缺失或无效时停止，提示人工检查。Docker 部署或升级在停机后被 Ctrl+C、终止信号或断线打断时自动回滚（升级已交给部署脚本时，升级器把中断转给它，等它回滚后再恢复代码；`ops.sh` 也等升级器结束才删除导出目录），回滚期间再次中断不会打断它：回滚和升级器恢复代码都在独立的进程组中运行，终端的 Ctrl+C 和断线只发给前台进程组，到不了其中的 docker 客户端和 git。回滚要以普通用户经 sudo 恢复防火墙规则时，先在前台刷新 sudo 凭据（必要时询问密码），回滚中的 sudo 只用已缓存的凭据，不再询问。进程被强制终止或回滚未完成时，指针保留；此后 `deploy`、`update` 会先要求处理上次操作，交互终端显示“1 继续上次操作 2 回滚到操作前 0 退出”，非交互调用需改用 `resume` 或 `rollback`；未完成的是升级时，Linux 的 `deploy` 直接提示改用 `resume` 或 `rollback`，由它们同时切换或恢复代码。TUI 在「系统 → 服务部署」顶部显示“继续上次操作”和“回滚上次操作”，处理完成前暂停部署、升级和修复入口；已保存的设置损坏时，`bun run tui` 直接进入“继续 / 回滚 / 诊断”菜单。`resume` 和 `rollback`（包括 TUI 发出的命令）先读事务记录，已保存的端口、入口、域名为空或损坏、`runtime.json` 损坏，以及新终端里无效的 `PLATFORM_IP`、`BOT_DEBUG`、`BOT_MAX_ACTIVE_REQUESTS` 都不会挡住它们。

- **继续**：只使用事务记录，不重新读取默认值或环境变量（包括换终端后不同的 `PLATFORM_IP`），也不拉取更新的 origin/main；运行参数沿用 `runtime.json`，当前终端的运行参数环境变量（如 `BOT_DEBUG`）不校验也不写入。当前代码必须是记录的目标提交。目标群根缺失时停止，不会重新创建空目录，恢复挂载后重试。停机前输入的隧道 token 不写入记录，只在同一次升级中由升级器交给部署脚本；之后再继续（`resume`、新终端）需要 token 时改用已保存的 `data/config/cloudflared-token`，否则停止并提示回滚。续做不运行 AI 配置向导，迁移沿用停机前确认的计划。Docker 继续沿用记录的镜像 ID 和服务身份，不重新构建或拉取；镜像已被清除（例如 `docker image prune -a`）时拒绝继续，重新构建的镜像不能代替它，此时只能回滚，迁移已经开始的还需人工处理。Docker 升级的继续和回滚从记录的目标提交（本地已有）导出升级器，离线也能处理；目标提交在本地缺失时只能回滚。中断在切换代码之前时，继续会先停止服务再切换代码；停止之前先确认切换能完成：已跟踪文件有未提交的改动（快进会保留这些改动，执行的就不是目标版本）、本地 main 无法快进到目标提交，或切换会覆盖未跟踪的内容（与新升级的预演相同）时都不停止服务、不切换，服务和代码保持现状，处理后重试。
- **回滚**：恢复迁移前的数据、原代码（升级）、配置、依赖或容器、网络入口和原运行状态。原群根在项目外且缺失时拒绝，以免旧服务使用空目录。Docker 升级先由部署脚本恢复数据、配置、容器和原运行状态，再由升级器恢复代码；代码恢复成功后才清除事务。代码恢复失败（例如残留 `.git/index.lock`）时，事务标记为“只剩代码待恢复”（快照中的 `code-restore`）：处理 git 问题后再次 `rollback` 只恢复代码，不重复回滚数据和容器；此时不能继续，菜单和 TUI 只提供完成回滚。
- **回滚不覆盖升级后的改动**：两个平台在执行 `git reset --hard` 恢复原代码前都会先核对工作区。当前提交必须是升级前或目标提交；原分支不在 HEAD 时，也不能指向这两个之外的提交。已跟踪文件的未提交改动、会被升级前版本覆盖的未跟踪文件（目标版本删除、此后又手工放回的文件），以及占着升级前版本目录位置的未跟踪文件或链接（例如升级前有 `retired/seed.txt`，现在 `retired` 是手工创建的文件、链接或 Windows 目录联接）都会阻止恢复代码，终端会逐项列出。只涉及已跟踪内容的文件与目录互换不受影响。显式 `rollback` 在停止服务、改动数据之前发现冲突，数据、配置和服务都保持现状。升级失败触发的自动回滚仍照常恢复数据和配置（Docker 同时恢复原容器和原运行状态；Windows 保持停止，计划任务随代码一起恢复），但不改代码并保留事务。把改动提交到其他分支、备份或撤销后再运行 `rollback`，只恢复剩下的部分。
- **数据已提交**：迁移回执属于本次事务时拒绝回滚，判定在停止服务或改动代码之前完成。继续只停止验证实例并启动正式实例，不再构建、迁移或开始新事务；新实例通过健康检查后事务才结束，未就绪时保留记录，可再次继续。

旧版本留下的中断事务没有记录，按快照中的目标提交、目标群根和原运行状态，以及已保存的端口、入口、域名和当前 `PLATFORM_IP` 处理。Linux 继续前需要在终端逐项确认一次：每个值旁边标出来源（快照、已保存设置、默认值或当前终端的 `PLATFORM_IP`），原群根优先取快照中保存的 `data/state/group-data-root`。确认后写入完整记录，之后与新版事务一样只读记录。拒绝确认则保持现状；非交互调用会停止并提示在终端运行 `resume`。TUI 的“继续上次操作”在终端中运行，可以直接完成确认。回滚不需要确认。旧版 Docker 升级留下的 `data/state/update-transaction` 也由 `resume` / `rollback` 处理：部署已开始时由部署脚本继续或回滚，回滚后恢复原代码；部署尚未开始时只能回滚，恢复原代码和原容器。

## 长时间没有回复

“消息发送成功（处理中提示）”只表示发送了“正在处理”，最终回答需要看到“回复发送完成”。`/status` 显示状态（空闲、准备中、执行中、执行工具中、正在执行 /stop 或 /clear）、等待处理的消息数、正在运行的工具、待补发回复和发送额度；有任务在运行时另有任务编号、已用时间和三项时限。服务日志按任务编号记录“任务开始”“任务结束”（含结果），运行中每 60 秒一条“任务仍在运行”（含已用时间和阶段），看门狗中止时记录中止原因。日志不记录模型输出、思考正文或工具参数。

1. 在异常群发送 `/status`，记下任务编号。用[日常控制](#日常控制)里的 `logs` 入口查看日志，或在 PowerShell 执行 `Get-Content logs/mixin-chatbot.log -Tail 200`，按任务编号、群号定位，也可以用下文的[提取脚本](#按任务编号提取日志)。
2. “任务仍在运行”的阶段：“准备中”是任务已开始、尚未进入模型轮次；“等待或接收模型输出”是模型轮次进行中；“等待重试”是模型请求失败后的退避；“执行工具 …”列出正在运行的工具；“压缩会话历史”是在压缩该成员的历史。
3. 只有某个群异常时，发送 `/stop`，等待 `/status` 变为空闲，再发 `/clear`。收到确认后，用“只回复 OK”测试。`/clear` 让当前用户在本群开启新的上下文，旧上下文留在群库里，群资料不受影响。若恢复，旧上下文是重要线索；若仍失败，保留这一轮的任务日志，继续检查 Pi 请求与模型服务。
4. 普通 HTTP 流探测成功只验证该次请求，不能验证机器人的完整历史、工具定义、思考模式和压缩请求。`doctor`/健康检查也不能证明模型回答正常。

### 深入排查：模型超时与进展判定

Pi 原生 `durable.stream.timeoutMs` 默认另对每次模型请求设置 120 秒期限，重试计数与服务看门狗独立；先到的取消条件生效。调整引擎策略及使用只读 `history context / timings` 诊断，见[运行设置与可选工具](runtime-tools.md)。旧记录的官方耗时字段可能缺失，诊断以未知展示。

模型等待或输出期间，默认连续 180 秒无有效进展就主动取消。Pi Durable 在模型输出时约每 100 毫秒把已收到的部分回答（正文、思考、工具调用及其参数）提交到群库；看门狗每秒查看一次，部分回答有任何变化都算进展，计时从每个模型轮次（每次尝试）开始，包含首个内容到达前的等待。反复改写同一内容也会续期，因此另设**单次模型响应 600 秒上限**，持续有进展也不能延长。

这两种模型时限只在模型轮次中计时；工具执行、历史压缩、重试退避和最终发送期间暂停，下个模型轮次重新计时。整轮时限默认 1200 秒，从任务第一次开始算起，覆盖准备、模型、工具和交付，服务重启后接着计算；三种时限以先到者为准。

中止时日志记一条“任务总时限到达”“模型无有效进展超时”或“单次模型响应超时”，带任务编号、已用时间和取消原因（`task_timeout`、`model_idle`、`model_response_timeout`）；成员收到的报错里也有任务编号。这些信息本身不能确定故障在上游服务还是 SDK。

可通过 `data/config/runtime.json` 或环境变量设置 `BOT_MODEL_IDLE_TIMEOUT_SECONDS` 和 `BOT_MODEL_RESPONSE_TIMEOUT_SECONDS`，重启生效；无可见增量的长思考模型、耗时较长的正常生成可按实测调整。中止后要等运行真正结束（工具退出）才处理同一用户的下一条消息，因此最终报错耗时可能超过阈值。上游只返回 `The operation timed out.` 时不直接断言网络不通。若任务中止后长期没有“任务结束”，先保存日志，再用运维 `restart` 恢复实例：群库里未结束的任务在重启后恢复，已用时间不清零。

## 按任务编号提取日志

也可在 TUI 的“监控 → 日志”按 `t` 输入任务编号。扫描在后台进行，不影响翻阅日志；离开日志页会取消未完成的扫描，需要完整结果时请留在该页等待完成，或使用下方独立脚本。

将群内报错或 `/status` 中的任务编号传给脚本即可。在项目根目录运行：

Windows PowerShell：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/task-logs.ps1 555d838a
```

Linux（在部署主机上运行，支持 Docker 部署，无需主机安装 Bun）：

```sh
bash scripts/ops/task-logs.sh 555d838a
```

脚本读取项目 `logs/mixin-chatbot.log` 及数字后缀的轮转日志，按旧到新提取完整的 8 位任务编号。
默认附带前后各 3 行，跨轮转文件保留上下文，重叠行只输出一次。每次运行在
`tmp/task-logs-<任务ID>-<时间>-<随机后缀>/` 下新建：

- `task.log`：仅任务匹配行，附原文件名和行号。
- `context.log`：任务行及前后文；`--` 表示中间省略了其他日志。
- `summary.txt`：扫描范围、匹配数量、首次匹配前最近的模型就绪信息、首末记录、最后运行心跳和三种超时记录；“模型流结束”统计只出现在数据版本 3 之前的日志里。

可选参数：Windows 用 `-Context 5 -LogDir "D:\saved-logs"`；Linux 用
`--context 5 --log-dir /path/to/saved-logs`。上下文范围为 0–100 行，日志目录默认相对脚本定位项目，
显式指定的相对日志目录则相对当前工作目录。从其他目录调用脚本时，结果仍保存到脚本所属项目的 `tmp/`。

脚本可在服务运行或停止时执行，保留源日志和之前的提取结果，不读取模型凭据配置。
Linux 使用 Bash、awk 和 GNU coreutils；Windows 支持 PowerShell 5.1+。
退出码 `0` 表示找到任务，`2` 表示没有匹配日志，`1` 表示参数或读写失败。正在运行的任务可能继续写日志，
已轮转覆盖的历史无法从当前日志恢复。日志保留原文，前后文可能包含其他任务，分享前请脱敏。

## 数据维护

以下命令在安装了 Bun 的项目根目录运行；将尖括号占位内容替换为实际值。

```sh
bun run stat
bun run stat --period week
bun run stat "<群号>" --period last-month
bun run stat --since 2026-10-01 --until 2026-10-07
bun run history list
bun run tmp list
bun run relay list
bun run relay test    # 上传并删除测试文件，不需停机
bun run routes list

# 写操作前先停止服务
bun run history clear "<群号>"
bun run tmp purge --days 7
bun run tmp purge --days 30 --group "<群号>" --user "<手机号>"
bun run relay purge "<关键字>"
```

`stat` 读使用统计账本 `<群数据根>/stats.sqlite`，区分模型轮次和成功资料工具结果；链接生成不等于用户收到。群库里的对话在每次回复前、`/clear` 时和每轮维护时按条目入账；升级前的旧会话文件（含当时的缓存保温用量）由每日兜底扫描补入。账本与会话历史相互独立：清空上下文不影响已统计的数字，群目录被删掉后账本里的历史也还在。

`--period` 支持 `today`、`yesterday`、`week`、`last-week`、`month`、`last-month`、`7d`、`30d`、`all`；与 `--since/--until` 互斥。统计输出总提问数、跨群去重的提问人数、人均和日均提问、活跃天数占比、高峰日、前五名提问占比、提问排行，以及逐日、逐周、逐月的提问、人数、处理轮次、文件、图片与已知估算费用。每一天都会列出，无记录填 0；周、月人数在周期内重新去重，不累加每日人数。覆盖人数指实际提问的账本成员身份，不代表群总人数或覆盖率；仅有回复的人仍可出现在原有使用成员表中。

Linux 运维入口示例：`bash scripts/ops/ops.sh stat --period week`；Windows：`scripts\ops\ops.ps1 stat -Period week`，自定义日期使用 `-Since` / `-Until`。HTML 从 TUI 导出到 `tmp/reports/`。

完整起止区间提供同比、环比，并打印基期日期和数值。周一开周；本周、本月比较上周、上月相同已到达日数（遇短月截到月末），上月比较完整前月；其他区间比较前一等长区间。同比取去年同日期，闰日截到月末。包含今天时数据仍在增长，账本只有日粒度，不与基期按小时对齐。基期为 0 时显示“新增（基期无记录）”，不计算无限增长；无历史记录不能证明当时没有使用。全部或只有一侧日期时不比较。日期沿用服务本地时区，应保持服务与运维环境时区一致。

`history clear` 在群库里为该群每位成员登记一次清空，机器人下次启动时、处理任何消息之前先执行：与成员自己发 `/clear` 相同，排队中的消息一并取消，旧上下文留在群库里，不释放磁盘空间；升级前的旧会话文件同时移入 `backup/rm`。群库记录的群与目录不符时拒绝，整个群不做改动。`history list` 列出各群群库和旧会话文件的占用。统计区间按自然日裁剪。维护写操作与服务通过 proper-lockfile 租约互斥，异常退出后约 35 秒可恢复陈旧锁。服务、升级验证实例、数据迁移以及 `history clear`、`tmp purge` 还在群数据根内持有 `.mixin-lease.lock` 租约：共享同一群数据根的两份部署不能同时运行，群数据根不存在时拒绝启动而不会自动创建。服务的心跳一旦发现任一租约丢失（例如已被另一进程接管），立即以退出码 1 退出，不再走正常关机的入账、归档和等待；没来得及入账的用量由之后的投影补入，已记入群库的 `/stop`、`/clear` 在下次启动时重新执行，尚未记入的需要重发，工具进程由各自的监督进程回收。运维包装器的 `history-clear` 会自动停机并恢复原运行状态，其他写操作先 `stop`，完成后按需 `start`。

兜底扫描遇到权限等错误时会逐项记录“统计账本扫描失败”，并继续处理后续成员和群。当天有失败就保留未完成状态，下轮维护重试；已成功且未变化的文件只检查元数据，不会反复计算前缀摘要，重启后也保留该进度。修正日志所指路径的权限后，后续维护会自动补账；未完成期间的汇总日志列出失败数和跳过数。

群库提交结果无法确认（例如磁盘写入失败或 SQL 线程意外退出）时，服务停止接收新任务并以退出码 1 退出，由部署的监督器重启；不会在线重新打开已出错的会话。持续出现这类退出时，先排查磁盘空间、文件权限和存储错误，保留数据库及 WAL。已经持久化的任务和控制命令在重启后恢复。

清理调用结果或保存待补发回复暂时失败时，会自动退避重试。`/clear` 未完成期间，该成员的新消息继续排队，模型请求暂停；解除文件占用或修正权限后会自动继续。`/status` 显示重试次数和最近错误，服务关闭会中止等待。清理没有完成时不会发送完成回执。

统计中的 `interrupted` 表示已开始但被中断的请求，不计为普通回复；没有完整响应用量时，部分输出的估算不会当作结算费用。`generation_unconfirmed` 保留尚无收口记录且用量未知的请求开始，`generation_unsettled` 保留完整用量已经落盘但尚无收口条目的请求。后续投影会与收口记录配对，避免重复计数。请求开始与实际发送之间存在崩溃窗口，因此请求次数是上界；未知用量或未知费用不能按零费用理解。

## 回调路由恢复

1. 在平台修正 key 与群的对应关系，每个群使用独立 key。
2. 使用 `stop` 停止机器人，再执行下面的查看与重绑命令。
3. 确认绑定后 `start`；若平台仍跨群复用 key，会再次隔离。

```sh
bun run routes list
bun run routes reset "<指纹>" --group "<目标群号>"

# 已废弃的 key：移除绑定并释放容量
bun run routes forget "<指纹>"
```

指纹支持日志中的 12 位前缀；有歧义时使用 `list` 输出的完整值，无需输入 callback 密钥。普通绑定闲置 24 小时后可回收；冲突绑定不会因重启或 TTL 自动解除，仍计入 1000 条总容量。`forget` 后，该 key 再次入站将建立新绑定。

Linux 主机没有 Bun 时，用运维包装器执行同一个 CLI：

```sh
bash scripts/ops/ops.sh routes list
bash scripts/ops/ops.sh routes reset "<指纹>" --group "<目标群号>"
bash scripts/ops/ops.sh routes forget "<指纹>"
```

容器在运行就 `docker exec` 进去，否则用正式标签 `mixin-chatbot` 的镜像起一次性容器，以服务容器记录的 UID:GID 运行（没有容器时按 `data/config` 的属主），并按部署时记录的群数据根挂载。部署或升级正在进行、或留有未完成的部署或升级时，正式标签可能仍指向旧镜像，一次性容器会拒绝启动（外链管理与配置、运行参数、清理历史同样如此），提示先 `resume` 或 `rollback`；体检此时跳过模型配置校验并注明原因。写操作仍受维护租约限制，机器人运行时会被拒绝，因此 `reset`/`forget` 之前照样要先 `stop`。

Windows 包装器使用 PowerShell 原生参数：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 routes list
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 routes reset -Fingerprint "<指纹>" -Group "<目标群号>"
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 routes forget -Fingerprint "<指纹>"
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 tmp-purge -Days 30 -Group "<群号>" -User "<手机号>"
```

## HTTP 拒绝日志

错误或缺失 webhook 密钥、未知路由、管理 token 错误对外保持相同的 `404 / Not Found`。已通过密钥校验的请求保留实际的校验或运行状态码。

### 日志分类、计数与脱敏规则

| 日志分类 | 含义 | 原因标签示例 |
| --- | --- | --- |
| `suspected_probe` | 疑似探测，也可能是调用地址配置错误，需结合 IP、频率与路径判断 | `webhook_secret_mismatch`、`webhook_secret_missing`、`route_not_found` |
| `request_validation` | 请求格式、大小或字段校验拒绝，不直接认定为扫描 | `invalid_request`、`payload_too_large`、`unsupported_media_type` |
| `runtime_protection` | 停机、容量或 callback 路由保护，不计入疑似探测 | `service_stopping`、`callback_route_capacity`、`callback_route_conflict`、`request_capacity` |

每个应用实例的每个 60 秒窗口、每类最多输出 10 条 WARN 明细，其余只计数。窗口从第一条拒绝开始；窗口结束即使没有新请求也会输出 `拒绝请求汇总`，包含该类总数、已记录数、已抑制数和原因计数。窗口结束后恢复明细配额；服务开始关闭时提前输出当前汇总。空窗口不写日志，正常 `/health` 不写拒绝日志。

同类的原因共享明细配额：普通路径扫描可能占满 `suspected_probe` 的配额，使随后错误密钥请求的 IP 和路径明细被抑制，但其数量仍计入汇总的 `webhook_secret_mismatch`。当前不为猜密钥单独预留明细配额。即使“已抑制”为 0，也保留有请求窗口的汇总，以便统一按汇总统计总量；因此零星拒绝会产生一条明细和一条汇总。未提供具体原因的 409/5xx 使用 `runtime_rejected`，归入 `runtime_protection`。

统计请求量应使用汇总的“总数”（已经包含明细），不要再叠加明细行；实时排查可先看尚未汇总的明细。汇总只保留固定分类与原因的计数，不按 IP 或路径建表，因此换 IP 也不能绕过日志配额。进程强制退出时，尚未汇总的计数可能丢失。已有业务日志仍按原逻辑输出；日志限速不代表请求限流，也不改变响应状态。

明细包含 IP、方法、脱敏路径和状态码；不记录查询参数、请求体、Authorization 或错误消息中的外部字段。`/webhook/` 后的路径全部隐藏。IP 沿用 X-Forwarded-For 第一跳、X-Real-IP 回退的提取规则，仅作为排查线索，不作为可信鉴权依据。代理层直接拦截的请求不会出现在应用日志里。

## 磁盘保留

| 内容 | 保留策略 |
| --- | --- |
| 配置、SQLite 状态库、群资料 | 持久保存，纳入停机备份 |
| Pi 设置与模型目录缓存 | `data/runtime/pi/settings.json` 与 `data/runtime/models-store.json` 随配置备份；动态目录服务商需缓存才能离线启动 |
| 使用统计账本 | `<群数据根>/stats.sqlite` 持久保存，纳入停机备份；清空会话不影响它，删掉就只能从群库和现存的旧会话文件回填，已归档的旧会话文件补不回来；群库中已裁剪的请求记录（见[不可逆的统计裁剪](data-migrations.md#不可逆的统计裁剪)）只存在于账本，恢复旧备份的账本也会丢失这部分用量 |
| 群库 | `<群目录>/durable.sqlite`（及 `-wal` 等）持久保存成员的对话、排队消息和控制命令，纳入停机备份；`/clear` 和 `history clear` 只开启新上下文，不删除旧上下文，也不释放空间 |
| 旧会话文件、用户 tmp | 升级前的 `session.jsonl` 原地保留（已导入群库）；清理时归档到 `backup/rm`，不自动删除，用[历史归档清理](#历史归档清理)处理；归档前机器人已把该段历史入账 |
| 部署备份 | 部署、升级和连接器安装成功后只删除本次快照和 `backup/rm/<快照名>`；失败操作保留现场，其余快照和归档用历史归档清理处理 |
| 数据版本迁移备份 | 有格式迁移时创建 `backup/snapshots/migration-*`；正式业务实例就绪后 finalize 按清单清理，保留提交及清理回执。失败后可运行 migrations cleanup，下一次成功部署也会重试，快照异常不阻断新升级。未提交、启动失败、保持停止或回滚失败的备份保留。同版本且标记配对时不复制 SQLite、不新增迁移快照。历史事务没有自动清理标记的快照不追溯删除；已提交事务不能执行 `rollback` |
| 历史账本迁移备份 | 按当时工具的保留规则处理，确认数据转换及新实例验收完成后再清理 |
| 测试与诊断现场 | 放在顶层 `tmp/`，确认没有测试、诊断或维护任务使用后可清理 |
| TUI 统计报表 | 每次导出独立保存在 `tmp/reports`，需要长期保存时另行保留 |
| 上传快照 | 完成、失败或取消后直接删除 |
| 应用日志 | 约 5 MiB 轮转，当前文件加 3 份备份，最旧备份直接删除 |
| 升级、迁移与启动诊断 | `logs/operations/` 保留最近 20 份，每份约 2 MiB；命令输出约 1 MiB 后为后续阶段与错误保留空间，回滚保留日志 |

归档不会立即释放磁盘空间，部署快照可能含凭据。应用日志常规预算约 20 MiB，运维诊断约 40 MiB，单条日志可使文件短暂超限；强制终止留下的临时现场需离线清理。

### 历史归档清理

`backup/rm` 和 `backup/snapshots` 中不属于某次成功操作的内容不会自动删除，用专门的入口分两步处理：

1. `ops.sh backup-scan`（Windows：`ops.ps1 backup-scan`）只读扫描这两处的顶层条目，在 `tmp/backup-cleanup/<报告名>/` 写出 `manifest.json` 和便于查看的 `manifest.tsv`，列出每条的路径、大小、分类、分类依据和建议动作，不删除任何内容。`backup/` 中其他目录不扫描，会在输出中列出。旧 `backup/cleanup`、`backup/reports` 保持原状；新版清理工具只读取新目录里的报告，旧报告需要重新扫描生成。
2. `ops.sh backup-clean <报告名>`（Windows：`ops.ps1 backup-clean <报告名>`）预演：逐条重新检查清单中选为删除的条目，列出将删除、扫描后有变化、拒绝等结果，并给出确认码，不删除任何内容。确认后加 `--confirm <确认码>`（Windows：`-ConfirmCode <确认码>`）执行，结果写入同一报告目录的 `result-*.json`；`result-*.tsv` 逐条追加，进程中断时也留有已处理条目的记录。

| 分类 | 判断依据 | 建议动作 |
| --- | --- | --- |
| 可确认测试数据 | 名称是测试夹具的归档格式 `<夹具名>-<UUIDv4>`（旧版测试辅助函数的命名，运维归档从不这样命名），且内容里有测试证据：夹具目录自己的随机名称、测试临时目录路径、至少 1 MiB 的单字节填充文件，或 RFC 6761 保留的 `.test` 域名 | 删除 |
| 疑似测试数据 | 名称符合测试夹具格式，但没有找到内容证据 | 保留，工具不删除 |
| 业务归档 | 运维归档格式（时间或 GUID 开头）、事务目录 `deploy-*` / `tunnel-*`、部署与连接器快照、`migration-*` 迁移快照 | 保留；确需删除时先另行备份，再把 `manifest.json` 中该条的 `action` 改为 `delete` |
| 无法判断 | 条目本身或内部含链接、有无法读取的部分，或名称不符合任何已知格式 | 保留，工具不删除 |

名称只是线索，内容证据不足的一律保留。执行时只处理清单中 `action` 为 `delete` 的条目，删除前逐条重新检查：

- 路径必须是 `backup/rm` 或 `backup/snapshots` 下的单层条目，`backup` 和这两个目录不能是链接；
- 条目本身和内部都不能有链接，工具从不跟随链接；
- 每个普通文件都必须能完整读取；有不可读文件时整个条目保留，业务归档也适用；
- 内容指纹（每个节点的相对路径、类型、大小、修改时间、设备号、inode，以及每个文件完整内容的 SHA-256）必须与扫描时一致。即使文件原地改为相同长度并恢复修改时间，也会跳过；重新扫描后再决定。扫描和复查采用分块读取，内存不随大文件大小增长。

清单格式为 2。旧版格式 1 没有文件内容摘要，不能继续预演或删除；必须重新运行 `backup-scan`，审阅新清单并获取新确认码，旧确认码不再使用。

有未完成的部署或升级时拒绝执行；未完成事务和当前迁移日志引用的快照与归档始终拒绝删除。`manifest.json` 中除 `action` 以外的字段被改动，或确认码与当前清单不符（预演后又改过清单）时，整份清单不执行。删除不可撤销，也不能用 Git 找回。Docker 部署在容器内执行清理；遇到容器用户无权删除的文件时，该条目记为“删除失败”，可能已部分删除，其余内容留在原处。

## 隧道托管

首次使用本项目的 Cloudflare 公网域名模式时，先在控制台准备域名和隧道：

1. 将根域名（如 `example.com`）添加到 Cloudflare，按指引在域名注册商修改 NS，等待状态变为 **Active（已激活）**。域名无需转移注册商，但 DNS 需托管到 Cloudflare。部署交互中填写机器人使用的子域名，如 `bot.example.com`。
2. 在同一 Cloudflare 账户打开 **Networking → Tunnels**（[控制台入口](https://dash.cloudflare.com/?to=/:account/tunnels)），创建 Cloudflared 隧道；已有隧道则选择它，再打开 **Add a replica（添加副本）**。在安装连接器页面，只复制安装命令中 `eyJ` 开头的完整 token 值。在部署的“隧道 token 或文件路径”提示中直接粘贴，或保存到项目的 `data/config/cloudflared-token` 后留空读取，也可填写其他 token 文件的路径。输入会隐藏；Windows 文件名不要带 `.txt` 后缀。连接器由项目脚本安装。
3. 在该隧道的 **Published application** 路由中填写相同子域名，服务地址设为 `http://127.0.0.1:<BOT_PORT>`（类型选 HTTP，URL 填 `127.0.0.1:<BOT_PORT>`；默认端口为 `1011`）。DNS 接入与公开路由需在控制台完成；部署脚本填写域名不会自动创建它们。域名可在部署时留空、稍后配置，公网回调需这些步骤完成后才能使用。

`<BOT_PORT>` 使用部署时选择的端口。Cloudflare 模式下机器人监听 IPv4 回环地址，源站显式使用 `127.0.0.1`，避免 `localhost` 解析为 IPv6 `::1`。已有隧道需在控制台手动更新服务地址；修改仓库或重新部署不会自动更新远程路由。

脚本使用项目根目录的 `cloudflared.exe`（Windows）或 `cloudflared`（Linux）。已有可运行副本会直接复用；缺失或不可用时，从 [Cloudflare 官方 GitHub 发布](https://github.com/cloudflare/cloudflared/releases) 下载对应架构的版本，先校验 SHA-256，再检查可执行性并保存。下载版本与校验值统一记录在 `scripts/tunnel/cloudflared-release.txt`；更新清单只影响后续下载。下载失败或校验失败会保留原文件并清理下载残留，也可提前将官方可执行文件放到项目根目录。

token 来源优先级为：本次输入的 token 或文件路径 → `TUNNEL_TOKEN_FILE` → `TUNNEL_TOKEN` → `data/config/cloudflared-token`。指定的来源无效会报错，不会自动切换到另一条隧道。文件支持裸 token 或包含 `TUNNEL_TOKEN=...` 的 .env 格式。外部文件、环境变量和直接粘贴的值会规范化保存到 `data/config/cloudflared-token`；已规范化的默认文件直接复用。

常驻命令使用同一个 `data/config/cloudflared-token` 文件。Windows 通过服务控制管理器注册项目根目录的可执行文件，命令行只包含受 ACL 保护的 token 文件路径，并核对注册后的命令；交互粘贴的 token 不作为子进程命令行参数传入。已有 Windows 服务继续沿用当前连接，更改文件后通过“修复隧道”应用新 token。Linux 记录 PID、启动时间和系统启动 ID 验证归属，内置 nohup 仅负责当前运行，开机托管需运维配置 systemd 等服务管理方式。

## 更新 cloudflared

运行 `bun run tui`，进入 **系统 → 服务部署 → 更新 cloudflared**。也可执行 Linux 的 `./scripts/ops/ops.sh tunnel-update` 或 Windows 的 `scripts\ops\ops.ps1 tunnel-update`；更新 Windows 已安装的服务需要管理员权限。

更新使用 Cloudflare 官方稳定版接口查询版本，从官方 GitHub 发布下载对应平台的程序，校验 SHA-256 并验证程序版本后才停止正在运行的隧道。没有新版本时直接结束。切换后按原启动参数恢复隧道，保留 token、连接模式和日志；原来停止的隧道保持停止，机器人服务继续运行。公网访问在隧道重启期间会短暂中断，见 [Cloudflare 更新说明](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/downloads/update-cloudflared/)。

仅更新项目根目录的副本，不更新系统包或其他项目的连接器。有未完成的部署或升级时，先继续或回滚；连接器归属不明、使用自定义启动参数或下载期间运行状态变化时拒绝切换。Linux 需要宿主机 Bun，这与 TUI 的运行条件相同。

替换或启动失败时尝试恢复旧程序及原运行状态。恢复也失败时保留 `.cloudflared-update-*/previous`（Windows 为 `previous.exe`）并报告路径，需人工恢复。强制结束进程或断电可能留下这个临时目录和停止的隧道，重新操作前应先检查程序和运行状态。更新后仅检查连接器进程是否保持运行；公网连通情况可在“监控 → 体检”核对。

## 隧道连接模式

运行 `bun run tui`，进入 **系统 → 设置 → Cloudflared 连接模式**：

| 选项 | 行为 |
| --- | --- |
| 自动（默认） | `auto`：优先 QUIC，无法建立 UDP 连接时回退 HTTP2；不保证每次短暂超时都立即切换 |
| HTTP2（TCP） | `http2`：固定使用 TCP 7844，UDP 不稳定时可尝试 |
| QUIC（UDP） | `quic`：固定使用 UDP 7844，不回退 HTTP2 |

配置保存到 `data/config/cloudflared-protocol`，缺失时为 `auto`。Windows 服务、前台启动和 Linux 启动都显式传入 `--protocol`，因此项目设置优先于 `TUNNEL_TRANSPORT_PROTOCOL` 和 cloudflared 配置文件中的协议值。连接模式与日志开关分别保存，切换其中一项会保留另一项。是否经过代理由系统及代理路由决定；协议选择本身不控制直连或代理。

命令行也可使用 `scripts/ops/ops.ps1 tunnel-protocol http2` 或 `bash scripts/ops/ops.sh tunnel-protocol http2`，将 `http2` 换成 `auto` 或 `quic` 即可切换。

TUI 保存前会显示确认预览；命令行直接应用指定模式。应用时只重启正在运行的本项目连接器，公网访问短暂中断；已停止时保持停止，尚未安装时下次部署生效。启动或写入失败会尝试恢复原配置与运行状态。启动检查只确认服务或进程保持运行，不保证已经连通 Cloudflare；切换后请结合隧道注册日志及外部请求验证可用性。

Windows 修改已安装的服务需要管理员权限。连接器必须使用当前项目生成的启动参数；此前没有 `--protocol` 的服务不做兼容迁移，Windows 先执行 **系统 → 服务部署 → 修复隧道**，Linux 停止原连接器后用当前脚本重新启动。无需删除日志。

## 隧道日志

运行 `bun run tui`，进入 **系统 → 设置 → Cloudflared 日志**，选择“关闭 / 开启”，默认关闭。开启后记录隧道连接、HTTP 请求和源站响应，写入项目 `logs/cloudflared.log`。配置持久化到 `data/config/cloudflared-logging`（`off` / `on`），部署和前台启动都会读取。命令行也可使用 `scripts/ops/ops.ps1 tunnel-logging on` 或 `bash scripts/ops/ops.sh tunnel-logging on`；关闭时将 `on` 改为 `off`。

保存时只重启正在运行的本项目连接器，公网访问会短暂中断；Windows 服务已停止时更新启动参数并保持停止，尚未安装或 Linux 连接器已停止时在下次启动生效。应用失败会尝试恢复原设置和运行状态。Windows 修改已安装的服务需要管理员权限；没有项目归属标记或使用自定义启动参数的连接器会拒绝自动修改。

使用 cloudflared 自带的目录轮转，不把控制台输出重复追加到同一文件。项目当前固定版本每个文件达到 1 MiB 后轮转，最多保留 5 个备份，文件名为 `cloudflared-<时间戳>.log`；关闭不删除已有日志。Linux 后台启动检查的输出只临时保存，启动结束后清理。

在 **监控 → 隧道日志** 查看当前文件尾部，`/` 搜索路径、错误或 `cfRay`，`l` 筛选警告和错误，`o` 返回日志设置。界面把 UTC 时间转换为本机时间；直接查询原始文件时需自行换算。较早记录需查询 `logs/` 中的轮转文件。

请求详情只证明流量到过当前连接器；源站响应不代表客户端完整收到了文件。开启之前、其他连接器处理、Cloudflare 边缘缓存命中或尚未到达本机的请求不会出现在这里，不能单凭没有日志认定平台未投递。日志包含完整 URL 和请求头，可能包括 webhook 密钥、外链签名或认证信息，分享前请脱敏。

## 高级运行参数

运行 `bun run tui`，进入 **系统 → 设置 → 高级运行参数**。参数分为并发与附件、超时与退出、缓存与索引、文档与诊断四类；默认值和数值范围与机器人共用定义。端口、监听地址及群数据目录放在服务部署中设置。

按 Enter 修改当前参数，`d` 将选中项恢复默认，`s` 展示所有改动并确认保存。恢复默认会移除对应的 `runtime.json` 覆盖项；未编辑的参数保持原值。Esc 返回上一层会保留当前 TUI 中的草稿，操作菜单可放弃草稿；退出 TUI 时会提醒尚未保存的内容。

设置只读取当前选中项，配置读取不启动 Docker、模型或网络探测；等待期间使用 TUI 现有的持续动画和后台读取机制，仍可切换分类或页面。保存通过运维执行面板显示进度：先校验草稿、环境覆盖及服务归属，再短暂停止原本运行中的机器人；写入后恢复并检查健康状态。已停止或尚未部署时只保存，保持停止状态。应用或健康检查失败会尝试回滚，恢复也失败时保留 `data/config/.runtime-draft-*.json.rollback` 供排查。

显式环境变量仍优先于保存值。Windows 检查当前运维进程的环境，Linux 检查既有容器的相关环境变量；被覆盖的修改会在停机前拒绝。自定义 Windows 启动脚本还需检查其单独设置的环境变量。配置在编辑期间被其他操作修改时，本次保存会拒绝覆盖；放弃草稿后重新读取再编辑。

## 配置可选的大文件外链

运行 `bun run tui`，进入 **系统 → 设置 → 外链配置**，选中时显示当前是否启用、桶、对象路径和期限（不显示凭据）；测试、查看与清理在 **数据 → 外链**。使用兼容 S3 的私有桶及限时 GET 下载链接，默认下载有效 2 小时，额外保留 30 分钟后清理。配置项、厂商参考及云端准备见[大文件外链配置](deployment.md#大文件外链配置)。

填写期间机器人继续运行，访问密钥和临时 Token 均隐藏输入；保存预览确认后，原本运行中的服务才短暂停止、写入配置并恢复。原本停止的服务保持停止，取消不变更配置和服务。这里仅校验配置格式，不上传测试文件，不修改云端桶权限。向导会按腾讯 COS、AWS、R2 的端点预填区域；Virtual hosted 下端点已含桶名时，提示改成不含桶名的服务端点。`doctor` 只读检查 S3 必填项，并明确提示尚未验证云端权限；不能凭此认定下载和删除已可用，请用下面的外链测试验收。

### 测试外链

运行 `bun run relay test`，或进入 **数据 → 外链 → 测试外链**；没有宿主机 Bun 的 Linux 部署用 `bash scripts/ops/ops.sh relay-test`，Windows 用 `scripts\ops\ops.ps1 relay-test`。测试不需要停机，用当前配置上传一个 8 MiB 的随机文件 `外链自检-*.bin`，依次检查：上传及大小核验、签名链接下载且内容一致、去掉签名后被拒绝（桶未公开）、下载链接不能用于删除、删除对象并移除账本记录、删除后链接失效。拒绝、失效两类检查只认明确的 4xx 答复；服务端 5xx、408 超时、429 限流或网络错误无法证明权限和删除状态，按未通过处理，稍后重试即可。任一项失败时退出码为 1；结果不打印预签名 URL 或云端原始响应。

测试同时按本次上传速度粗估上传单文件上限所需时间。超过单次上传的 30 分钟限时会给出提示，可调低单文件上限或改善上行带宽；小文件测速受连接建立影响，结果偏保守。测试对象和真实分享一样先登记账本再上传，中断或删除失败时由后台按计划重试清理。修改配置、云端访问策略、生命周期或版本控制后都应重新测试。

### 查看并验证下载链接

在部署目录运行 `bun run relay list`，或进入 **数据 → 外链 → 列出在册外链**。列表展示上传状态、下载到期时间和计划删除时间。未过期对象可重新签发剩余期限内的链接；查看与补发不会续期。过期、上传未确认或不属于当前后端的记录只显示存储地址，不是可用下载链接。

验证下载使用完整的 GET 预签名 URL。不要把它直接改为 HEAD 请求：S3 V4 签名绑定请求方法，机器人探测文件大小时会单独签发 HEAD。发生 403 时检查凭据、区域、时间同步及签名/权限配置；发生重定向时修正 endpoint，本实现不跟随重定向。日志不打印预签名 URL 或云端原始错误响应，避免泄露临时访问授权。对象设置 `Cache-Control: private, no-store, max-age=0`，并保留原文件名作为下载附件名。

实际接入新厂商时，用非敏感测试文件验证：上传成功且下载字节一致；无签名访问失败；修改请求方法失败；短期限链接过期后不能重新发起下载；删除余量内对象仍存在、随后可被清理。云端权限和访问策略最终以这项验收为准。链接到期不会召回已下载的数据；到期前已建立的连接是否继续传输由对象存储服务决定。

### 清理对象

运行 `bun run relay purge --keyword <关键字>` 或 `bun run relay purge --all`，也可使用 TUI 的清理操作。手动清理要求服务停止并取得维护租约，会提前使匹配的链接不可用；只删除账本中明确归属当前后端的精确对象，不按前缀递归删除桶内内容。删除失败、不匹配记录均保留。

自动清理在服务启动时和每 5 分钟尝试运行，按账本的计划删除时间处理，失败重试。停机或停用外链期间依赖云端生命周期兜底；切换存储后旧端点对象不会交给新配置删除。停止使用一个桶前，先用原配置完成清理。不要直接丢弃账本：它是失败上传及未删对象的回收依据。

## 重新配置模型

模型配置使用 `data/config/models.json` 的 Pi 原生 `providers` 和 `data/runtime/pi/settings.json` 的 `defaultProvider` / `defaultModel` / `defaultThinkingLevel`。旧顶层 `modelId` / `thinkingLevel` 不参与选型，也不做兼容迁移。旧配置需要重建时，先停机并将这两个文件及 `data/runtime/models-store.json` 归档到 `backup/rm`，再运行 `bun run configure`；没有宿主机 Bun 的 Docker 部署可重新运行部署脚本，由镜像内的向导生成配置。`backup/rm` 不是长期存储，需要长期保留的配置副本请另行备份。

凭证由 Pi 从 `models.json` 解析，支持直接 Key、环境变量引用和命令引用；磁盘 `auth.json` 不参与解析。运行中的模型、设置及目录使用启动时的只读视图，更改配置后需重启。群工作区的 `.pi/settings.json` 不参与配置；重试、自动压缩开关及遥测策略由应用固定，编辑 Pi 设置也不会覆盖这些策略。

向导先在暂存目录中刷新所选服务商的模型清单、写入 Pi 设置并完成离线校验，再提交配置和缓存。取消不会更改当前文件；提交过程中发生错误会恢复原文件。服务商的扩展字段及同一端点、同一模型的原生字段会保留；选择推理级别时，会清除所选模型的 `modelThinkingLevels` 覆盖，保证启动后使用本次选择。

Pi 目录刷新遵循 `PI_OFFLINE`：设置此环境变量时使用随包目录和已有缓存；未设置时可联网刷新。该开关不禁止自定义端点的模型清单探测。机器人启动和 `doctor` 都只读本地目录，动态目录服务商缺少缓存时需重新运行向导联网刷新。

改完用 `bash scripts/ops/ops.sh doctor`（Windows 用 `scripts\ops\ops.ps1 doctor`）确认「模型配置（models.json + Pi 设置）」一行通过再启动。部署快照同时保存 `data/config`、Pi 设置和模型目录缓存。

## 旧待补发账本（历史升级）

当前版本要求待补发账本 schema 2。更早格式不在现有迁移的支持范围内；遇到格式错误时保持停机，保留数据库与 WAL，按[旧账本说明](data-migrations.md#未支持的旧账本)处理。不要依据旧错误提示寻找未随仓库发布的 tmp 脚本，也不要删表来绕过校验。

## 临时产物维护

TUI 的“数据 → 临时文件”先保存真实预览，显示可归档、保留和待处置条目，确认后执行同一清单；归档后按 `x` 预览并确认物理回收已登记的产物，按 `r` 预览并确认永久删除归档，两者都要输入“永久删除”。预览（`tmp-preview`，以及不带 `--digest` 的 `tmp-reclaim`、`tmp-discard`）只读取、只写清单，服务运行时也可执行，不停机；`tmp-purge` 和带 `--digest` 的确认由 ops 包装命令取得部署锁，拒绝未完成的部署事务，维护期间停止服务，结束后恢复原运行状态。直接运行 `bun run tmp` 的确认命令前需自行停机；维护租约不能替代停止服务。预览与确认之间内容有变化的条目在确认时保留。

归档示例（Linux 包装器；Windows 用 `-All`、`-Plan`、`-Digest`）：

```sh
bash scripts/ops/ops.sh tmp-preview --all
bash scripts/ops/ops.sh tmp-purge --plan <预览ID> --digest <预览摘要>
```

默认归档目录是群根下的 `.reclamation/backup/rm`，要求与源文件同一文件系统；归档字节不算释放空间。失败时保留清单、目标和进度，用原 ID 与摘要重试，不重新生成计划覆盖失败记录。数据备份不包含归档内容，只包含其清单（`.tmp-plans`）。

归档的永久删除同样先预览再确认：

```sh
bash scripts/ops/ops.sh tmp-discard
bash scripts/ops/ops.sh tmp-discard --plan <删除清单ID> --digest <摘要>
```

删除清单只列出由归档清单及其进度证明、确为本工具移入且内容与归档时一致的条目；有变化的条目保留，已不存在的条目报告为缺失，不视为已删除。隔离任务的产物由任务管理端删除：删除前先保存一份列出全部条目的删除日志，中途失败后用原清单或新预览重试，只在剩余条目都属于这份日志且未改变时续删，否则保留。Windows 的目录、文件和链接都持删除句柄删除。Linux 旧共享身份归档的目录、文件和链接与 `tmp-reclaim` 相同，需要宿主 UID 0 的独立停机维护身份，以 `bun run tmp discard --legacy --journal <宿主私有目录> --recorded-root <原服务看到的群根>` 执行，否则列为待处置。历史 `backup/rm` 中不是由本工具归档的内容，永久删除仍需独立清单与确认。

`tmp-discard` 和 `tmp-reclaim` 执行后报告的是这份清单至今的累计结果，不是本次执行的增量；重复执行同一清单、再次看到同样的数字，不表示又释放了空间。隔离任务的产物如果在本清单处理到它时已被删除（例如上次执行在删除后中断，或另一份清单已删完），只补完记录，报告为“收尾”，不计入已删除的项数和字节；无法确认是哪次执行删除的，宁可少计，也不重复计入。

已登记产物的物理回收先运行 `tmp-reclaim --all` 预览，再以 `tmp-reclaim --plan <ID> --digest <摘要>` 确认。Linux 旧共享产物另需宿主 UID 0 的独立维护，先停止服务并保持停止，直接运行 `bun run tmp reclaim --all --legacy --journal <宿主私有目录> --recorded-root <原服务看到的群根>`。`GROUP_DATA_ROOT` 指向宿主实际群根；普通 Docker 的原服务群根通常是 `/app/data/groups`，自定义挂载须使用原值。事务目录及全部祖先必须为 root 所有且其他身份不可写，不能放在 `/tmp`、`/var/tmp` 或共享项目中。

核对后以同一 `--legacy`、`--journal`、`--recorded-root` 和计划 ID/摘要执行。该入口先冻结原目录写权限，才允许按已审实体删除；中断后可能保留冻结权限，必须按原计划续做，确认完成再恢复服务。同一父目录或条目还有未完成的特权事务时，新预览把相关条目列为待处置并写明原清单或计划 ID，执行时会再次检查并拒绝以新清单接管；用原清单和同一事务目录续做即可。冻结或交还权限在改属主与改权限之间中断时，父目录会是 root 所有、但仍保留原权限位（例如 0750）；因此父目录只要为 root 所有且没有粘滞位，无论权限是 0700 还是别的值、换用哪个事务目录，都不会被新清单接管，也不会被记为原权限，需先核对冻结来自哪次操作，再用原清单和原事务目录续做。合法的 root 所有父目录只有带粘滞位的系统临时目录；服务身份所有、却带粘滞位的父目录会被拒绝冻结。已记为删除完成的条目重做时仍会核对其特权事务，按原事务记录恢复父目录权限；原位置若又出现同名条目，保留待核对，不会删除。rootless 容器内的 UID 0 不满足条件，ops 包装器拒绝转发 `--legacy`。未知来源、引用未释放、实体变化或旧容器 `/tmp` 已消失的对象仍保留待核对。

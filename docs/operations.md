## 命令行运维

成员上下文也可从管理台“会话”页登记压缩（详情里选中成员按 `p`，或在列表页按 `p` 输入号码），或运行 Linux `scripts/ops/ops.sh history-compact <群号>|--direct <成员号码>`、Windows `scripts/ops/ops.ps1 history-compact <群号> -User <成员号码>`（单聊空间用 `-Direct`）。运维入口先停机取得独占空间库，再登记任务并恢复原运行状态；原本停止的实例不会被自动启动。压缩由机器人运行后生成摘要，会产生模型用量，成功后仍保留历史和已有费用。聊天里的 `/compact` 可直接执行。

Durable 成员的临时目录包含历史引用与还没发完的回复文件。`tmp purge` 会先停机取得维护租约，生成带摘要的清单，再把已核对且未被引用的条目原子移入 `data/state/reclamation/backup/rm`；它会逐项报告已归档、保留、待处置和失败数量，归档本身不会立即释放磁盘空间；`tmp discard` 按归档清单永久删除这些条目、释放空间。`tmp reclaim` 用于物理回收：Windows 持有删除句柄并保存可续做清单，Linux 服务身份写入的条目必须由宿主 UID 0 的独立停机维护身份显式执行，普通 ops 包装器不会自动恢复这类特权操作。来源不明、内容或实体变化、仍有引用的目录都会保留。常规结果回收由机器人在成员空闲且引用释放后执行。整包备份和暂存恢复流程见[数据目录与备份](deployment.md#数据目录)。

日常交互操作从[运维界面](tui.md#运维界面)进入。这里保留命令行入口，便于脚本调用和没有装 Bun 的 Docker 宿主机使用；排查与数据维护步骤见本文后面的对应章节。

### 日常控制

在项目根目录选择对应平台的命令行入口。

Windows：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 doctor
```

Linux / Docker：

```sh
bash scripts/ops/ops.sh doctor
```

将示例中的 `doctor` 替换为所需命令：

| 命令 | 用途 |
| --- | --- |
| `doctor` | 检查配置、应用机器人凭据、实例、事件 Stream、通讯录同步、运行状况和共享资料目录，并列出运行中的应用机器人版本、构建和数据格式；加 `--json`（Windows 为 `-Json`）输出单行 JSON |
| `start` / `stop` / `restart` | 启动、正常关闭或重启实例 |
| `logs` | 持续查看日志 |
| `directory` | 查看事件 Stream 连接、同步范围、通讯录映射数量、最近同步和待确认的撤销；只读，经本机端口询问运行中的服务 |
| `directory-confirm <轮次>` | 确认那一轮暂停的通讯录撤销，服务随即重新完整扫描，见[事件 Stream 与通讯录](#事件-stream-与通讯录) |
| `directory-departments [部门ID]` | 列出该部门（默认根部门 1）的直属子部门：ID、人数、名称，用于选择同步范围；只读 |
| `directory-scope [部门ID,…]` | 只同步这些部门及其子部门，留空为整个通讯录；范围有变化时立即重新同步，见[同步范围](#事件-stream-与通讯录)。当前范围用 `directory` 查看 |
| `update` | 同步 origin/main，由目标版本的升级器在停机前完成确认后升级，保留原运行或停止状态 |
| `deploy` | 部署当前代码；可重新配置并重建现有部署，失败恢复原部署 |
| `model-configure` | 停止机器人，运行模型配置向导（Docker 在部署镜像内），结束后恢复原运行状态；取消不修改配置 |
| `configure-app-bot` | 停止机器人，运行应用机器人凭据向导（验证新凭据后才替换），结束后恢复原运行状态；取消不修改配置 |
| `resume` | 按事务记录继续中断的部署或升级，不重新提问 |
| `rollback` | 回滚中断的部署或升级；数据已提交时拒绝 |

`update` 要求已跟踪文件没有本地改动，代码已最新也会检查部署记录。它先处理未完成的部署或升级（见[中断恢复](#中断恢复)），此时不拉取；否则拉取 origin/main，从目标提交导出升级器（Windows 为 `tmp/upgrade-<GUID>`，Docker 为 `tmp/upgrade-<随机>`），在工作区外由目标版本完成升级，结束后删除导出目录。两个平台都在停机前检查部署记录与离线配置：数据格式一致时正常升级；没有有效记录、记录损坏或数据格式不受支持时停止，不清理、不重置，详见[版本、数据格式与从旧版切换](data-migrations.md)。rootful Docker 的 `update`、`resume`、`rollback` 要由 root 运行，rootless Docker 由其所属用户运行，都在任何提问之前检查（见[选择部署方式](deployment.md#选择部署方式)）。升级沿用已保存的端口、共享资料目录、应用机器人凭据和 AI 配置，停机后不再询问；修改这些配置请使用 `deploy`。Docker 升级器停机前从目标提交（不含工作区改动和未跟踪文件）构建一次镜像，按 image ID 固定并用本次独占的保留标签防止被清除，构建期间原服务照常运行；随后在这个镜像中以原服务的身份、断网、只读挂载数据预检当前格式并校验配置，宿主机无需安装 Bun；停机前再复核一次：检出与升级开始时核对的不同（提交、分支、main 的位置，或已跟踪文件有了改动，例如构建期间改了文件），预览后配置或版本标记有变化，原容器被删除或替换，候选镜像或保留标签被改动，或剩余空间不够写快照，都停止，服务不受影响。两个平台切换代码都是先 `checkout main` 再快进到目标提交：升级开始时（Docker 在构建之前）和停机前复核时（Windows 在保存部署快照之后）都按这条路径（当前检出 → main → 目标提交）预演，续做也一样，Windows 同时核对已跟踪文件没有改动、本地 main 能快进到目标提交。会被覆盖或删除的未跟踪内容逐项列出并停止——目标提交或途经的 main 新增路径上已有的文件，含未跟踪文件的目录，占着新增路径上级目录位置的文件或链接（Windows 含目录联接），也包括被 `.gitignore` 忽略的文件（git 切换时会直接覆盖或随目录删除它们）。当前提交跟踪的链接或文件被改成目录时，git 直接替换它，不算冲突，链接指向的内容也不当作这些路径上的文件。预演只读，不改索引、工作区和这些文件；脚本不移动、不删除它们，由你移出工作区（或提交到其他分支）后重试。构建或预览被 Ctrl+C 或发给 `ops.sh` 的终止信号打断时删除预览容器和本次的保留标签并退出，服务没有停止，代码和数据不变；清理在独立的进程组中进行，期间再次中断（终端的 Ctrl+C、断线）不会打断它。停机后格式登记、验证实例和正式实例都按记录的 image ID 运行，中断后的继续和回滚也用它，不再构建或拉取；镜像已被清除时拒绝继续，只允许回滚尚未开始格式登记的操作。正式标签 `mixin-chatbot` 在数据提交、新实例就绪后才指向新镜像，发布失败时保留事务，可用 `resume` 重试；当前终端里的端口、共享资料目录和运行参数环境变量不会被采用，会提示已忽略；`update`、`resume`、`rollback` 的入口也不校验这些环境变量，升级结束后的体检按保存的设置进行。已保存的外置共享资料目录缺失时，升级在停机前停止。rootless Docker 发布不了已保存的低端口时（见[选择部署方式](deployment.md#选择部署方式)），升级同样在停机前停止并提示处理方法。升级缺少 `data/config/models.json` 或 `data/config/app-bot.json` 时拒绝升级，需先通过 `deploy` 完成配置。发布期间使用只验证实例检查，提交后恢复原运行状态，直接校验当前配置、统计 schema 和新实例。提交前失败恢复数据、原提交和部署；提交后启动失败保留新代码与数据，检查日志后重试。中断后的处理见[中断恢复](#中断恢复)。

升级与格式登记失败时，按终端打印的路径查看 `logs/operations/` 下的日志；其中包含失败阶段、异常、退出码与回滚结果。服务早期启动错误写入同目录的 `startup-*.log`，日志保留在当前项目中供排查。Docker 升级和部署的日志分别记录候选镜像的构建耗时（`candidate build took …s`，这时原服务仍在运行）和实际停机窗口：从停止原服务（`service stopped; downtime begins`）到新版本通过健康检查或回滚后原容器重新启动（`service back (…); downtime …s`）。中断后在新进程中续做时，停机若发生在之前的进程，只记录恢复的时刻；中断在事务指针发布之后、停止服务之前时，由续做的进程停止服务并从那里开始计时。构建会与原服务争用 CPU、内存和磁盘，停机前的准备不等于对原服务没有影响。

Windows `update` 会显示更新前后的提交 hash。依赖清单、锁文件、安装配置和补丁未变，且已安装的直接依赖版本匹配时，会保留 `node_modules` 并跳过安装；缺包、版本不匹配或依赖输入发生变化时，才备份旧依赖并按锁文件安装。版本更高也不视为匹配，避免偏离经过验证的依赖组合。

部署和升级的备份放在 `backup/snapshots/<快照名>`，操作期间被替换的旧文件放在 `backup/rm/<快照名>`；用户 tmp 等日常归档直接放在 `backup/rm` 下。成功后只删除本次操作自己的快照和 `backup/rm/<快照名>`。新建快照时会避开 `backup/rm` 中已有同名目录的名称，快照、归档或其上级目录是链接时拒绝清理。没有自动清理标记的其他事务目录和散落归档保留，由[历史归档清理](#历史归档清理)审查处理，不清空整个 `backup/rm`。操作失败时保留回滚现场。Windows 会移除空的 `backup` 目录；Linux 保留空的容器挂载目录，避免运行中的容器丢失后续归档。部署锁保存在 `data/state/deploy.lock`。Docker 部署和升级在构建新镜像前，先给原容器使用的镜像打上 `mixin-chatbot:previous` 标签，事务提交或回滚完成后再移除。Docker 29 起新装默认使用 containerd 镜像存储，它会删除失去最后一个标签的镜像，回滚要靠这个标签恢复原镜像。

关闭服务使用 `stop`：Windows 验证实例身份后先请求优雅关闭，超时再复核归属并终止进程树；Linux 使用 Docker 停止期限。

### 中断恢复

部署或升级在停机前把已确认的选择写入快照目录的 `transaction` 记录，再发布事务指针：操作类型、目标提交、升级前的提交与分支、原运行状态、端口、原与目标共享资料目录、是否重新配置 AI（格式 2）。Docker 另在同一目录写入 `candidate-image`（本次镜像的 ID、保留标签和所在的 Docker daemon）和 `service-user`（服务的 UID:GID），`transaction` 的格式和键不变；恢复入口要求完整的当前事务记录。继续和回滚先核对这两份记录，再检查数据是否已提交或运行任何容器：Docker daemon 与开始时不同（例如切换了 context 或 socket）时两者都拒绝；记录缺失或无效时停止，提示人工检查。Docker 部署或升级在停机后被 Ctrl+C、终止信号或断线打断时自动回滚（升级已交给部署脚本时，升级器把中断转给它，等它回滚后再恢复代码；`ops.sh` 也等升级器结束才删除导出目录），回滚期间再次中断不会打断它：回滚和升级器恢复代码都在独立的进程组中运行，终端的 Ctrl+C 和断线只发给前台进程组，到不了其中的 docker 客户端和 git。进程被强制终止或回滚未完成时，指针保留；此后 `deploy`、`update` 会先要求处理上次操作，交互终端显示“1 继续上次操作 2 回滚到操作前 0 退出”，非交互调用需改用 `resume` 或 `rollback`；未完成的是升级时，Linux 的 `deploy` 直接提示改用 `resume` 或 `rollback`，由它们同时切换或恢复代码。TUI 在「系统 → 服务部署」顶部显示“继续上次操作”和“回滚上次操作”，处理完成前暂停部署、升级和修复入口；已保存的设置损坏时，`bun run tui` 直接进入“继续 / 回滚 / 诊断”菜单。`resume` 和 `rollback`（包括 TUI 发出的命令）先读事务记录，已保存的端口为空或损坏、`runtime.json` 损坏，以及新终端里无效的 `BOT_PORT`、`BOT_MAX_ACTIVE_REQUESTS` 都不会挡住它们。

- **继续**：只使用事务记录，不重新读取默认值或环境变量，也不拉取更新的 origin/main；运行参数沿用 `runtime.json`，当前终端的运行参数环境变量（如 `BOT_RUN_TIMEOUT_SECONDS`）不校验也不写入。当前代码必须是记录的目标提交。外置的目标共享资料目录缺失时停止，恢复挂载后重试。续做不运行凭据和 AI 配置向导，格式登记沿用停机前保存的计划。Docker 继续沿用记录的镜像 ID 和服务身份，不重新构建或拉取；镜像已被清除（例如 `docker image prune -a`）时拒绝继续，重新构建的镜像不能代替它，此时只能回滚，格式登记已经开始的还需人工处理。Docker 升级的继续和回滚从记录的目标提交（本地已有）导出升级器，离线也能处理；目标提交在本地缺失时只能回滚。中断在切换代码之前时，继续会先停止服务再切换代码；停止之前先确认切换能完成：已跟踪文件有未提交的改动（快进会保留这些改动，执行的就不是目标版本）、本地 main 无法快进到目标提交，或切换会覆盖未跟踪的内容（与新升级的预演相同）时都不停止服务、不切换，服务和代码保持现状，处理后重试。
- **回滚**：恢复当前发布前的原代码（升级）、配置、依赖或容器、原运行状态，。原共享资料目录在项目外且缺失时拒绝。Docker 升级先由部署脚本恢复数据、配置、容器和原运行状态，再由升级器恢复代码；代码恢复成功后才清除事务。代码恢复失败（例如残留 `.git/index.lock`）时，事务标记为“只剩代码待恢复”（快照中的 `code-restore`）：处理 git 问题后再次 `rollback` 只恢复代码，不重复回滚数据和容器；此时不能继续，菜单和 TUI 只提供完成回滚。
- **回滚不覆盖升级后的改动**：两个平台在执行 `git reset --hard` 恢复原代码前都会先核对工作区。当前提交必须是升级前或目标提交；原分支不在 HEAD 时，也不能指向这两个之外的提交。已跟踪文件的未提交改动、会被升级前版本覆盖的未跟踪文件（目标版本删除、此后又手工放回的文件），以及占着升级前版本目录位置的未跟踪文件或链接（例如升级前有 `retired/seed.txt`，现在 `retired` 是手工创建的文件、链接或 Windows 目录联接）都会阻止恢复代码，终端会逐项列出。只涉及已跟踪内容的文件与目录互换不受影响。显式 `rollback` 在停止服务、改动数据之前发现冲突，数据、配置和服务都保持现状。升级失败触发的自动回滚仍照常恢复数据和配置（Docker 同时恢复原容器和原运行状态；Windows 保持停止，计划任务随代码一起恢复），但不改代码并保留事务。把改动提交到其他分支、备份或撤销后再运行 `rollback`，只恢复剩下的部分。
- **数据已提交**：当前发布提交记录属于本次事务时拒绝回滚，判定在停止服务或改动代码之前完成。继续只停止验证实例并启动正式实例，不再构建或开始新事务；新实例通过健康检查后事务才结束，未就绪时保留记录，可再次继续。

当前程序只识别当前事务记录（格式 2）；缺少完整记录时拒绝操作，不猜测快照的设置。

## 长时间没有回复

机器人开始处理时不发“正在处理”之类的提示，成员收到的第一条就是回答；只有服务维护期间补推的消息会先收到一条说明晚到原因的提示。等待中想确认进度，可以发 `/status`：它 显示状态（空闲、准备中、执行中、执行工具中、正在执行 /stop 或 /clear）、等待处理的消息数、正在运行的工具和待处理附件；有任务在运行时另有任务编号、已用时间和三项时限。服务日志按任务编号记录“任务开始”“任务结束”（含结果），运行中每 60 秒一条“任务仍在运行”（含已用时间和阶段），看门狗中止时记录中止原因。日志不记录模型输出、思考正文或工具参数。

1. 先确认消息到达了服务：`doctor` 或 TUI 总览中“事件 Stream”应为已连接，开发者后台的事件订阅仍是 Stream 且勾选了机器人接收消息事件。服务断开期间的消息约 5 分钟后才补推，断开超过 5 分钟可能丢失，需要重发。成员收到“暂时无法确认身份，正在同步通讯录”时，见[事件 Stream 与通讯录](#事件-stream-与通讯录)。
2. 在异常群发送 `/status`，记下任务编号。用[日常控制](#日常控制)里的 `logs` 入口查看日志，或在 PowerShell 执行 `Get-Content logs/mixin-chatbot.log -Tail 200`，按任务编号、群号定位，也可以用下文的[提取脚本](#按任务编号提取日志)。
3. “任务仍在运行”的阶段：“准备中”是任务已开始、尚未进入模型轮次；“等待或接收模型输出”是模型轮次进行中；“等待重试”是模型请求失败后的退避；“执行工具 …”列出正在运行的工具；“压缩会话历史”是在压缩该成员的历史。
4. 工具启动的每条命令（bash、文档解析和生成）结束后，不论成败，都记录一条“命令耗时”，含任务编号、`工具名#工具任务号`、结果（退出码、超时、取消等），以及总耗时和各阶段耗时：监督进程启动、命令启动、执行、回收。隔离容器中的命令只记总耗时。若“监督进程启动”或“命令启动”常达数秒，多为安全软件在检查进程创建：火绒按创建者预留的可执行内存计时，约每 MB 3 毫秒。因此 Windows 上机器人进程默认设置 `BUN_JSC_jitMemoryReservationSize=134217728`（128 MB；计划任务环境中已设置的值优先），监督进程固定为 16 MB。经实测，把 bun.exe 加入火绒信任区无效。
5. 只有某个群异常时，发送 `/stop`，等待 `/status` 变为空闲，再发 `/clear`。收到确认后，用“只回复 OK”测试。`/clear` 让当前用户在本群开启新的上下文，旧上下文留在空间库里，共享资料不受影响。若恢复，旧上下文是重要线索；若仍失败，保留这一轮的任务日志，继续检查 Pi 请求与模型服务。
6. 普通 HTTP 流探测成功只验证该次请求，不能验证机器人的完整历史、工具定义、思考模式和压缩请求。`doctor`/健康检查也不能证明模型回答正常。

### 深入排查：模型超时与进展判定

Pi 原生 `durable.stream.timeoutMs` 默认另对每次模型请求设置 120 秒期限，重试计数与服务看门狗独立；先到的取消条件生效。调整引擎策略及使用只读 `history context / timings` 诊断，见[运行设置与可选工具](runtime-tools.md)。记录缺少官方耗时字段时，诊断以未知展示。

模型等待或输出期间，默认连续 180 秒无有效进展就主动取消。Pi Durable 在模型输出时约每 100 毫秒把已收到的部分回答（正文、思考、工具调用及其参数）提交到空间库；看门狗每秒查看一次，部分回答有任何变化都算进展，计时从每个模型轮次（每次尝试）开始，包含首个内容到达前的等待。反复改写同一内容也会续期，因此另设**单次模型响应 600 秒上限**，持续有进展也不能延长。

这两种模型时限只在模型轮次中计时；工具执行、历史压缩、重试退避和最终发送期间暂停，下个模型轮次重新计时。整轮时限默认 1200 秒，从任务第一次开始算起，覆盖准备、模型、工具和交付，服务重启后接着计算；三种时限以先到者为准。

中止时日志记一条“任务总时限到达”“模型无有效进展超时”或“单次模型响应超时”，带任务编号、已用时间和取消原因（`task_timeout`、`model_idle`、`model_response_timeout`）；成员收到的报错里也有任务编号。这些信息本身不能确定故障在上游服务还是 SDK。

可通过 `data/config/runtime.json` 或环境变量设置 `BOT_MODEL_IDLE_TIMEOUT_SECONDS` 和 `BOT_MODEL_RESPONSE_TIMEOUT_SECONDS`，重启生效；无可见增量的长思考模型、耗时较长的正常生成可按实测调整。中止后要等运行真正结束（工具退出）才处理同一用户的下一条消息，因此最终报错耗时可能超过阈值。上游只返回 `The operation timed out.` 时不直接断言网络不通。若任务中止后长期没有“任务结束”，先保存日志，再用运维 `restart` 恢复实例：空间库里未结束的任务在重启后恢复，已用时间不清零。

## 按任务编号提取日志

也可在 TUI 的“监控 → 日志”按 `t` 输入任务编号。扫描在后台进行，不影响翻阅日志；离开日志页会取消未完成的扫描，需要完整结果时请留在该页等待完成，或使用下方独立脚本。

将群内报错或 `/status` 中的任务编号传给脚本即可。在项目根目录运行：

Windows PowerShell：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/task-logs.ps1 555d838a
```

Linux（在部署主机上运行，支持 Docker 部署，无需主机安装 Bun）：

```sh
bash scripts/ops/task-logs.sh 555d838a
```

脚本读取项目 `logs/mixin-chatbot.log` 及数字后缀的轮转日志，按旧到新提取完整的 8 位任务编号。
默认附带前后各 3 行，跨轮转文件保留上下文，重叠行只输出一次。每次运行在
`tmp/task-logs-<任务ID>-<时间>-<随机后缀>/` 下新建：

- `task.log`：仅任务匹配行，附原文件名和行号。
- `context.log`：任务行及前后文；`--` 表示中间省略了其他日志。
- `summary.txt`：扫描范围、匹配数量、首次匹配前最近的模型就绪信息、首末记录、最后运行心跳和三种超时记录。

可选参数：Windows 用 `-Context 5 -LogDir "D:\saved-logs"`；Linux 用
`--context 5 --log-dir /path/to/saved-logs`。上下文范围为 0–100 行，日志目录默认相对脚本定位项目，
显式指定的相对日志目录则相对当前工作目录。从其他目录调用脚本时，结果仍保存到脚本所属项目的 `tmp/`。

脚本可在服务运行或停止时执行，保留源日志和之前的提取结果，不读取模型凭据配置。
Linux 使用 Bash、awk 和 GNU coreutils；Windows 支持 PowerShell 5.1+。
退出码 `0` 表示找到任务，`2` 表示没有匹配日志，`1` 表示参数或读写失败。正在运行的任务可能继续写日志，
已轮转覆盖的历史无法从当前日志恢复。日志保留原文，前后文可能包含其他任务，分享前请脱敏。

## 数据维护

以下命令在安装了 Bun 的项目根目录运行；将尖括号占位内容替换为实际值。

```sh
bun run stat
bun run stat --period week
bun run stat "<群号>" --period last-month
bun run stat direct --period week    # 单聊空间
bun run stat --since 2026-10-01 --until 2026-10-07
bun run history list
bun run tmp list
bun run relay list
bun run relay test    # 上传并删除测试文件，不需停机

# 写操作前先停止服务
bun run history clear "<群号>"
bun run history clear --direct  # 单聊空间
bun run history clear --all    # 单聊和所有群
bun run tmp purge --days 7
bun run tmp purge --days 30 --group "<群号>" --user "<手机号>"
bun run relay purge "<关键字>"
bun run stat-import <旧部署>/data/groups/stats.sqlite    # 一次性导入旧版统计（TUI 统计页按 i 可浏览选择）
```

`stat` 读使用统计账本 `data/state/stats.sqlite`，只有提问和模型 token 两类数字。提问在消息进入成员队列时计入；token 取 Durable 按模型和工具名累计的已返回用量，在每轮结束、`/compact`、`/clear`、维护和打开空间时把增长量记到同步当天，口径见[统计账本](data-migrations.md#统计账本)。账本与会话历史相互独立：清空上下文不影响已统计的数字。单聊在统计中记为 `direct`。旧版统计按[导入旧版统计](data-migrations.md#导入旧版统计)并入。

`--period` 支持 `today`、`yesterday`、`week`、`last-week`、`month`、`last-month`、`7d`、`30d`、`all`；与 `--since/--until` 互斥。统计输出总提问数、跨群去重的提问人数、人均和日均提问、活跃天数占比、高峰日、前五名提问占比、提问排行，以及逐日、逐周、逐月的提问、提问人数和入账 token；群明细列出 input、output、cacheRead、cacheWrite、合计和加权缓存读率，并按模型、按工具（工具自身调用的辅助模型）分列。不显示费用。每一天都会列出，无记录填 0；周、月人数在周期内重新去重，不累加每日人数。覆盖人数指实际提问的账本成员身份，不代表群总人数或覆盖率。

Linux 运维入口示例：`bash scripts/ops/ops.sh stat --period week`；Windows：`scripts\ops\ops.ps1 stat -Period week`，自定义日期使用 `-Since` / `-Until`。HTML 从 TUI 导出到 `tmp/reports/`。

完整起止区间提供同比、环比，并打印基期日期和数值。周一开周；本周、本月比较上周、上月相同已到达日数（遇短月截到月末），上月比较完整前月；其他区间比较前一等长区间。同比取去年同日期，闰日截到月末。包含今天时数据仍在增长，账本只有日粒度，不与基期按小时对齐。基期为 0 时显示“新增（基期无记录）”，不计算无限增长；无历史记录不能证明当时没有使用。全部或只有一侧日期时不比较。日期沿用服务本地时区，应保持服务与运维环境时区一致。

`history clear` 在空间库里为该群（`--direct` 为单聊空间）每位成员登记一次清空，机器人下次启动时、处理任何消息之前先执行：与成员自己发 `/clear` 相同，排队中的消息一并取消，旧上下文留在空间库里，不释放磁盘空间；空间库记录的空间与目录不符时拒绝，整个空间不做改动。`history clear --all` 在同一次停机内对单聊和所有有会话历史的群逐个执行同样的清空，相当于全员发送 `/clear`，适合会话普遍变长、首轮请求写入的上下文过大时使用；某个空间被拒绝或失败时其余照常清空，最后列出未完成的空间并以退出码 1 结束，处理原因后可重新执行，已登记的清空不会重复。不指定空间也不写 `--all` 时只报错。运维包装器用 `history-clear --all`（Windows：`history-clear -All`），TUI 在 **数据 → 会话** 按 `a`，输入“全部清空”确认。`history list` 只列出当前空间库的占用。统计区间按自然日裁剪。服务、升级验证实例、当前数据登记和维护写操作通过 `data/state/service` 的 proper-lockfile 租约互斥，异常退出后约 35 秒可恢复陈旧锁。服务的心跳一旦发现租约丢失（例如已被另一进程接管），立即以退出码 1 退出，不再走正常关机的入账、归档和等待；没来得及入账的提问和用量由下次同步补入，已记入空间库的 `/stop`、`/clear` 在下次启动时重新执行，尚未记入的需要重发，工具进程由各自的监督进程回收。运维包装器的 `history-clear` 会自动停机并恢复原运行状态，其他写操作先 `stop`，完成后按需 `start`。

空间库提交结果无法确认（例如磁盘写入失败或 SQL 线程意外退出）时，服务停止接收新任务并以退出码 1 退出，由部署的监督器重启；不会在线重新打开已出错的会话。持续出现这类退出时，先排查磁盘空间、文件权限和存储错误，保留数据库及 WAL。已经持久化的任务和控制命令在重启后恢复。

清理调用结果或保存回复记录暂时失败时，会自动退避重试。`/clear` 未完成期间，该成员的新消息继续排队，模型请求暂停；解除文件占用或修正权限后会自动继续。`/status` 显示重试次数和最近错误，服务关闭会中止等待。清理没有完成时不会发送完成回执。

统计只计入 Durable 已提交的用量：被中断、在提交前崩溃或超时放弃的请求没有入账，服务商可能仍按其计费，所以 token 合计是已知下限，不是账单。日志出现“统计累计值回退……已按当前值重设基准，本次不入账”时，说明某个会话库的累计值比上次同步小（被替换为较早的副本，例如单独从备份恢复）：回退掉的那部分之前已经入账，不再重复计入；恢复后到这次同步之间新产生的用量并入新基准，会少计，符合下限口径。

## 事件 Stream 与通讯录

服务启动后用应用凭据取得访问令牌并连接事件 Stream，断开后自动退避重连。空闲连接每 30 秒发一次 ping，平台曾回应过 ping 的连接连续 30 秒没有回应和任何消息时视为已断开（例如被网络设备静默回收），主动重连。断开超过 1 分钟写告警日志，超过 2 分钟 `doctor` 的“事件 Stream”判为失败、TUI 总览标红。连不上时先检查服务器能否以 HTTPS 访问 `imtwo.zdxlz.com` 和 `imfl.zdxlz.com` 的 443 端口、凭据是否仍有效（`configure-app-bot` 会验证），再查看日志。同一应用只能有一个实例连接 Stream：另一套部署或调试工具使用同一应用时，事件会被分走。平台在投递失败约 5 分钟后补推一次，补推的消息按原发送时间判断：普通提问照常处理并注明“约 N 分钟前发出”，`/stop`、`/clear`、`/compact` 这类改状态的命令超过 1 分钟才到达时不执行，请成员重发。

健康状态分两层。**本机就绪**指服务完成本地初始化、能应答且不在停止中，`/health` 同时报告实例身份；部署、升级的就绪检查和 `doctor` 的“本地机器人健康”只看这一层，不等待平台。**外部依赖**指事件 Stream 和通讯录同步，`/health` 只报告服务已知的状态，不现场请求平台或模型；`doctor` 和 TUI 总览把它们单独列为告警。`/health` 还报告机器人自本次启动以来需要留意的事件：停住和出错的任务、超时放弃的交付、未发出的模型请求和统计回退，每类给出次数、最近一次的空间（单聊或群号）和时间，不含号码和内容；`doctor` 的“运行状况”一行列出它们，最近一次在 24 小时内时判为待核验，细节按时间到日志里查找。计数在机器人重启后清零。平台短暂故障时服务保持就绪并自动重连，部署不会因此判定新版本失败而回滚；反过来，“本地机器人健康”通过不代表消息能正常收发，以“事件 Stream”一行为准。

机器人按开放平台通讯录把成员的平台 ID 对应到手机号，统计、会话和成员目录都按手机号归属。映射保存在 `data/state/agent.sqlite`（0600，不进日志和诊断包），与当前 AppID 和环境绑定，换应用或环境时重建。

- **同步时机**：首次部署后在后台完整同步一次。通讯录请求合计限速每秒 80 次（平台未公布限流，实测到每秒 80 次未遇到限流；若遇到限流，所有平台请求包括发消息会一起短暂冷却）；遍历部门的同时就解析新出现的成员，已解析的成员不必等整轮结束即可使用。约 2.7 万人、5000 个部门的通讯录首次同步约需 8–10 分钟，完成前未同步到的成员收到“正在同步通讯录”的提示；之后每天 03:00 完整同步，并顺带复核约 1/30 的已有映射；遇到未知成员时触发一次，30 分钟内不重复。同一时间只有一轮同步。
- **撤销**：只有完整同步（全部分页成功、无冲突）才撤销不再出现在通讯录中的成员；不完整的一轮不撤销，已有映射继续使用。平台响应缺少部门或成员列表、列表类型不对、总页数缺失或无效，或者列出的成员没有手机号时，这一轮都算不完整，也不记为最近一次完整同步；只有明确的空列表（或不带列表但总数为 0）才算部门已空。一轮要撤销的超过现有映射的 10% 且多于 20 个时（例如接口异常或可见范围被改小），本轮暂停撤销并告警，等待管理员确认。
- **冲突**：同一手机号出现互相矛盾的身份信息，或一个平台 ID 同时对应两个仍在通讯录中的号码时，不自动合并，本轮也不撤销；成员换手机号只在完整同步确认旧号已不在时才转移，新号码使用新的成员目录和统计键，旧账不改写。

- **同步范围**（可选）：通讯录很大而只有部分部门使用机器人时，可以只同步选定的部门及其全部子部门。先用 `directory-departments` 从根部门逐层列出直属子部门（ID、人数、名称），记下要同步的部门 ID，再执行 `directory-scope <部门ID,部门ID>`（Windows 多个 ID 用引号括起来；TUI「系统 → 通讯录 → 设置同步范围」）。服务先向平台核对每个部门存在且对应用可见，任何一个不通过都不改；通过后保存到 `data/config/directory.json`，中止正在进行的同步并按新范围立即重新同步。范围外成员按缺席处理：这一轮完整同步后撤销其映射，超过上面的撤销阈值时同样暂停等待确认。范围外的成员发消息会收到“可能不在机器人同步的部门范围内”的提示。不带部门 ID 执行 `directory-scope`（TUI 中留空）恢复整个通讯录（删除该文件）；与现有范围相同时不改、不重新同步。

查看状态：Linux `bash scripts/ops/ops.sh directory`，Windows `scripts\ops\ops.ps1 directory`，或 TUI「系统 → 通讯录」。有暂停的撤销时，先核对开发者后台的通讯录可见范围和成员变动，确认无误后执行 `directory-confirm <轮次>`（TUI 中选“确认暂停的撤销”）。确认只接受最近一次暂停的那一轮：服务立即重新完整扫描，缺席成员全部在该轮名单内时才撤销；名单外又有人缺席会再次暂停，需要重新查看后确认。正在同步时会提示稍后再试。这些命令经本机管理端口与运行中的服务通信，不另开 Stream 连接；部门列表和范围核对由服务代为查询平台；服务刚重启时实例口令会变，重新查看后再确认。

## 一次性容器

Linux 主机没有 Bun 时，运维包装器（统计、历史、临时文件、外链、配置向导等）在容器中执行同一个 CLI：容器在运行就 `docker exec` 进去，否则用正式标签 `mixin-chatbot` 的镜像起一次性容器，以服务容器记录的 UID:GID 运行（没有容器时按 `data/config` 的属主），挂载 `data/`，外置共享资料目录按部署记录只读挂载。部署或升级正在进行、或留有未完成的部署或升级时，正式标签可能仍指向旧镜像，一次性容器会拒绝启动，提示先 `resume` 或 `rollback`；体检此时跳过模型配置校验并注明原因。写操作仍受维护租约限制，机器人运行时会被拒绝。

Windows 包装器使用 PowerShell 原生参数，例如：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/ops.ps1 tmp-purge -Days 30 -Group "<群号>" -User "<手机号>"
```

## 磁盘保留

| 内容 | 保留策略 |
| --- | --- |
| 配置、SQLite 状态库、共享资料 | 持久保存，纳入停机备份（外置共享资料目录由管理员另行备份） |
| Pi 设置与模型目录缓存 | `data/runtime/pi/settings.json` 与 `data/runtime/models-store.json` 随配置备份；动态目录服务商需缓存才能离线启动 |
| 使用统计账本 | `data/state/stats.sqlite` 持久保存，纳入停机备份；清空会话不影响它，删除会丢失历史账目；空间库中已清理的请求记录和已删除的会话库只留在账本，恢复旧备份的账本也会丢失这部分数字 |
| 空间库 | `data/conversations/{direct,groups/<群>}/durable.sqlite`（及 `-wal` 等）持久保存成员的对话、排队消息和控制命令，纳入停机备份；`/clear` 和 `history clear` 只开启新上下文，不删除旧上下文，也不释放空间 |
| 部署备份 | 部署和升级成功后只删除本次快照和 `backup/rm/<快照名>`；失败操作保留现场，其余快照和归档用历史归档清理处理 |
| 测试与诊断现场 | 放在顶层 `tmp/`，确认没有测试、诊断或维护任务使用后可清理 |
| TUI 统计报表 | 每次导出独立保存在 `tmp/reports`，需要长期保存时另行保留 |
| 上传快照 | 完成、失败或取消后直接删除 |
| 应用日志 | 约 5 MiB 轮转，当前文件加 3 份备份，最旧备份直接删除 |
| 升级、格式登记与启动诊断 | `logs/operations/` 保留最近 20 份，每份约 2 MiB；命令输出约 1 MiB 后为后续阶段与错误保留空间，回滚保留日志 |

归档不会立即释放磁盘空间，部署快照可能含凭据。应用日志常规预算约 20 MiB，运维诊断约 40 MiB，单条日志可使文件短暂超限；强制终止留下的临时现场需离线清理。

### 历史归档清理

`backup/rm` 和 `backup/snapshots` 中不属于某次成功操作的内容不会自动删除，用专门的入口分两步处理：

1. `ops.sh backup-scan`（Windows：`ops.ps1 backup-scan`）只读扫描这两处的顶层条目，在 `tmp/backup-cleanup/<报告名>/` 写出 `manifest.json` 和便于查看的 `manifest.tsv`，列出每条的路径、大小、分类、分类依据和建议动作，不删除任何内容。`backup/` 中其他目录不扫描，会在输出中列出。旧 `backup/cleanup`、`backup/reports` 保持原状；新版清理工具只读取新目录里的报告，旧报告需要重新扫描生成。
2. `ops.sh backup-clean <报告名>`（Windows：`ops.ps1 backup-clean <报告名>`）预演：逐条重新检查清单中选为删除的条目，列出将删除、扫描后有变化、拒绝等结果，并给出确认码，不删除任何内容。确认后加 `--confirm <确认码>`（Windows：`-ConfirmCode <确认码>`）执行，结果写入同一报告目录的 `result-*.json`；`result-*.tsv` 逐条追加，进程中断时也留有已处理条目的记录。

| 分类 | 判断依据 | 建议动作 |
| --- | --- | --- |
| 可确认测试数据 | 名称是测试夹具的归档格式 `<夹具名>-<UUIDv4>`（旧版测试辅助函数的命名，运维归档从不这样命名），且内容里有测试证据：夹具目录自己的随机名称、测试临时目录路径、至少 1 MiB 的单字节填充文件，或 RFC 6761 保留的 `.test` 域名 | 删除 |
| 疑似测试数据 | 名称符合测试夹具格式，但没有找到内容证据 | 保留，工具不删除 |
| 业务归档 | 运维归档格式（时间或 GUID 开头）、事务目录 `deploy-*` 及其快照；旧版目录里还有隧道操作的 `tunnel-*` 和数据迁移的 `migration-*` 快照，v1 不再产生，同样保留 | 保留；确需删除时先另行备份，再把 `manifest.json` 中该条的 `action` 改为 `delete` |
| 无法判断 | 条目本身或内部含链接、有无法读取的部分，或名称不符合任何已知格式 | 保留，工具不删除 |

名称只是线索，内容证据不足的一律保留。执行时只处理清单中 `action` 为 `delete` 的条目，删除前逐条重新检查：

- 路径必须是 `backup/rm` 或 `backup/snapshots` 下的单层条目，`backup` 和这两个目录不能是链接；
- 条目本身和内部都不能有链接，工具从不跟随链接；
- 每个普通文件都必须能完整读取；有不可读文件时整个条目保留，业务归档也适用；
- 内容指纹（每个节点的相对路径、类型、大小、修改时间、设备号、inode，以及每个文件完整内容的 SHA-256）必须与扫描时一致。即使文件原地改为相同长度并恢复修改时间，也会跳过；重新扫描后再决定。扫描和复查采用分块读取，内存不随大文件大小增长。

清单格式为 2。旧版格式 1 没有文件内容摘要，不能继续预演或删除；必须重新运行 `backup-scan`，审阅新清单并获取新确认码，旧确认码不再使用。

有未完成的部署或升级时拒绝执行；未完成事务引用的快照与归档始终拒绝删除。`manifest.json` 中除 `action` 以外的字段被改动，或确认码与当前清单不符（预演后又改过清单）时，整份清单不执行。删除不可撤销，也不能用 Git 找回。Docker 部署在容器内执行清理；遇到容器用户无权删除的文件时，该条目记为“删除失败”，可能已部分删除，其余内容留在原处。

## 旧入口退役

当前版本主动连出事件 Stream，不需要入站入口。旧版 webhook 发布的 UFW 直连规则、Windows 防火墙规则、cloudflared 连接器和 Cloudflare 隧道由管理员在切换时退役，步骤见[从旧版 webhook 发布切换](data-migrations.md#从旧版-webhook-发布切换)；当前程序不识别、也不自动处理这些旧入口。在各群把旧的自定义机器人换成应用机器人，见[接入开发者后台](deployment.md#接入开发者后台)。

## 应用机器人凭据

凭据保存在 `data/config/app-bot.json`。更换 AppSecret 或换成另一个应用时，在 TUI **系统 → 设置 → 应用机器人**，或运行 `configure-app-bot`：向导先用新凭据取得一次访问令牌验证（不连接 Stream，不和运行中的服务抢连接），确认后短暂停止机器人、替换配置并恢复原运行状态；取消或验证失败时原配置不变。换应用或环境后通讯录映射随新应用重新同步，期间未同步到的成员会收到提示；新应用同样要在开发者后台选择 Stream、验证连接、勾选事件并加入各群。

## 高级运行参数

运行 `bun run tui`，进入 **系统 → 设置 → 高级运行参数**。参数分为并发与附件、超时与退出、缓存与索引、文档处理四类；默认值和数值范围与机器人共用定义。本机端口、监听地址及群数据目录属于部署设置，不在这里修改，见[本机管理端口](deployment.md#本机管理端口)。

按 Enter 修改当前参数，`d` 将选中项恢复默认，`s` 展示所有改动并确认保存。恢复默认会移除对应的 `runtime.json` 覆盖项；未编辑的参数保持原值。Esc 返回上一层会保留当前 TUI 中的草稿，操作菜单可放弃草稿；退出 TUI 时会提醒尚未保存的内容。

设置只读取当前选中项，配置读取不启动 Docker、模型或网络探测；等待期间使用 TUI 现有的持续动画和后台读取机制，仍可切换分类或页面。保存通过运维执行面板显示进度：先校验草稿、环境覆盖及服务归属，再短暂停止原本运行中的机器人；写入后恢复并检查健康状态。已停止或尚未部署时只保存，保持停止状态。应用或健康检查失败会尝试回滚，恢复也失败时保留 `data/config/.runtime-draft-*.json.rollback` 供排查。

显式环境变量仍优先于保存值。Windows 检查当前运维进程的环境，Linux 检查既有容器的相关环境变量；被覆盖的修改会在停机前拒绝。自定义 Windows 启动脚本还需检查其单独设置的环境变量。配置在编辑期间被其他操作修改时，本次保存会拒绝覆盖；放弃草稿后重新读取再编辑。

## 配置可选的大文件外链

运行 `bun run tui`，进入 **系统 → 设置 → 外链配置**，选中时显示当前是否启用、桶、对象路径和期限（不显示凭据）；测试、查看与清理在 **数据 → 外链**。使用兼容 S3 的私有桶及限时 GET 下载链接，默认下载有效 2 小时，额外保留 30 分钟后清理。配置项、厂商参考及云端准备见[大文件外链配置](deployment.md#大文件外链配置)。

填写期间机器人继续运行，访问密钥和临时 Token 均隐藏输入；保存预览确认后，原本运行中的服务才短暂停止、写入配置并恢复。原本停止的服务保持停止，取消不变更配置和服务。这里仅校验配置格式，不上传测试文件，不修改云端桶权限。向导会按腾讯 COS、AWS、R2 的端点预填区域；Virtual hosted 下端点已含桶名时，提示改成不含桶名的服务端点。`doctor` 只读检查 S3 必填项，并明确提示尚未验证云端权限；不能凭此认定下载和删除已可用，请用下面的外链测试验收。

### 测试外链

运行 `bun run relay test`，或进入 **数据 → 外链 → 测试外链**；没有宿主机 Bun 的 Linux 部署用 `bash scripts/ops/ops.sh relay-test`，Windows 用 `scripts\ops\ops.ps1 relay-test`。测试不需要停机，用当前配置上传一个 8 MiB 的随机文件 `外链自检-*.bin`，依次检查：上传及大小核验、签名链接下载且内容一致、去掉签名后被拒绝（桶未公开）、下载链接不能用于删除、删除对象并移除账本记录、删除后链接失效。拒绝、失效两类检查只认明确的 4xx 答复；服务端 5xx、408 超时、429 限流或网络错误无法证明权限和删除状态，按未通过处理，稍后重试即可。任一项失败时退出码为 1；结果不打印预签名 URL 或云端原始响应。

测试同时按本次上传速度粗估上传单文件上限所需时间。超过单次上传的 30 分钟限时会给出提示，可调低单文件上限或改善上行带宽；小文件测速受连接建立影响，结果偏保守。测试对象和真实分享一样先登记账本再上传，中断或删除失败时由后台按计划重试清理。修改配置、云端访问策略、生命周期或版本控制后都应重新测试。

### 查看并验证下载链接

在部署目录运行 `bun run relay list`，或进入 **数据 → 外链 → 列出在册外链**。列表展示上传状态、下载到期时间和计划删除时间。未过期对象可重新签发剩余期限内的链接；查看与重发不会续期。过期、上传未确认或不属于当前后端的记录只显示存储地址，不是可用下载链接。

验证下载使用完整的 GET 预签名 URL。不要把它直接改为 HEAD 请求：S3 V4 签名绑定请求方法，机器人探测文件大小时会单独签发 HEAD。发生 403 时检查凭据、区域、时间同步及签名/权限配置；发生重定向时修正 endpoint，本实现不跟随重定向。日志不打印预签名 URL 或云端原始错误响应，避免泄露临时访问授权。对象设置 `Cache-Control: private, no-store, max-age=0`，并保留原文件名作为下载附件名。

实际接入新厂商时，用非敏感测试文件验证：上传成功且下载字节一致；无签名访问失败；修改请求方法失败；短期限链接过期后不能重新发起下载；删除余量内对象仍存在、随后可被清理。云端权限和访问策略最终以这项验收为准。链接到期不会召回已下载的数据；到期前已建立的连接是否继续传输由对象存储服务决定。

### 清理对象

运行 `bun run relay purge --keyword <关键字>` 或 `bun run relay purge --all`，也可使用 TUI 的清理操作。手动清理要求服务停止并取得维护租约，会提前使匹配的链接不可用；只删除账本中明确归属当前后端的精确对象，不按前缀递归删除桶内内容。删除失败、不匹配记录均保留。

自动清理在服务启动时和每 5 分钟尝试运行，按账本的计划删除时间处理，失败重试。停机或停用外链期间依赖云端生命周期兜底；切换存储后旧端点对象不会交给新配置删除。停止使用一个桶前，先用原配置完成清理。不要直接丢弃账本：它是失败上传及未删对象的回收依据。

## 重新配置模型

模型配置使用 `data/config/models.json` 的 Pi 原生 `providers` 和 `data/runtime/pi/settings.json` 的 `defaultProvider` / `defaultModel` / `defaultThinkingLevel`。旧顶层 `modelId` / `thinkingLevel` 不参与选型，也不做兼容迁移。日常更换模型可在 TUI **系统 → 设置 → 模型配置**，或运行 `model-configure`：它停止正在运行的机器人，运行向导，结束后恢复原运行状态，有未完成的部署或升级时拒绝执行。旧配置需要重建时，先停机并将这两个文件及 `data/runtime/models-store.json` 归档到 `backup/rm`，再运行 `bun run configure`；没有宿主机 Bun 的 Docker 部署可重新运行部署脚本，由镜像内的向导生成配置。`backup/rm` 不是长期存储，需要长期保留的配置副本请另行备份。

凭证由 Pi 从 `models.json` 解析，支持直接 Key、环境变量引用和命令引用；磁盘 `auth.json` 不参与解析。运行中的模型、设置及目录使用启动时的只读视图，更改配置后需重启。共享资料目录中的 `.pi/settings.json` 不参与配置；重试、自动压缩开关及遥测策略由应用固定，编辑 Pi 设置也不会覆盖这些策略。

向导先在暂存目录中刷新所选服务商的模型清单、写入 Pi 设置并完成离线校验，再提交配置和缓存。取消不会更改当前文件；提交过程中发生错误会恢复原文件。服务商的扩展字段及同一端点、同一模型的原生字段会保留；选择推理级别时，会清除所选模型的 `modelThinkingLevels` 覆盖，保证启动后使用本次选择。

Pi 目录刷新遵循 `PI_OFFLINE`：设置此环境变量时使用随包目录和已有缓存；未设置时可联网刷新。该开关不禁止自定义端点的模型清单探测。机器人启动和 `doctor` 都只读本地目录，动态目录服务商缺少缓存时需重新运行向导联网刷新。

改完用 `bash scripts/ops/ops.sh doctor`（Windows 用 `scripts\ops\ops.ps1 doctor`）确认「模型配置（models.json + Pi 设置）」一行通过再启动。部署快照同时保存 `data/config`、Pi 设置和模型目录缓存。

## 任务收尾与失败交付

任务默认总时限 20 分钟，剩余 5 分钟进入收尾，最后 2 分钟只允许读取、登记和发送。所有阶段的 bash 都按“剩余时间减交付保留时间”限制执行时长，未指定 timeout 时仍不超过 `BOT_BASH_TIMEOUT`。每次模型请求都会附带当前剩余时间；服务重启后沿用原截止时间。生成文档后应先 `deliverable_register` 登记草稿，再检查、修正、登记检查范围并发送，避免反复重建耗尽时限。

总超时、模型静默、单次响应超时和最终模型错误都会尝试交付登记快照：每个交付物优先选择可用的最新 checked 版本，否则选择最新 draft。已拒绝、结构不完整、摘要改变或未登记的文件不会自动发出。草稿会明确标注未完成全部检查，检查范围按登记内容列出。`/stop`、`/clear` 不触发自动发送；发送中的请求可能已到平台，余下文件停止自动发送。

兜底先发送说明，再发送文件，使用独立的 2 分钟预算。本轮已生成的外链及其续签数据会并入说明，发送前刷新；说明送达后，同一文件不再另发一次。说明没有发出时不发文件。平台明确拒收的部分在预算内自动重试；结果不确定的附件视为已发，不再重发；普通发送（不在兜底计划里）结果不确定时，应先查看群消息，未收到再在新消息中要求重新发送。重启后的自动恢复沿用原发送截止时间，超过预算后放弃，并在服务日志写一条“交付超时放弃”。`/stop`、`/clear` 撤回的计划不再发送。每个请求的回复对象（会话、提问人、摘要）随请求持久保存，重启后的发送和重发仍回到原会话。未完成计划的快照受临时文件回收保护，不要手工删掉 `.deliverables`。

运行配置及 TUI 设置新增 `BOT_CLOSEOUT_SECONDS=300`、`BOT_DELIVERY_RESERVE_SECONDS=120`、`BOT_FALLBACK_SEND_SECONDS=120`，重启生效。启动校验要求：交付保留 < 收尾 < 总时限的一半。TUI 总览显示待交付及结果不确定的附件数。

资料检索优先使用 `materials_find`、`materials_grep`，它们直接读取索引、纯文本和已提取文本，不创建进程。每次检索最多读取一遍解析缓存目录；缺少来源记录的缓存条目不在检索中逐个哈希原文，按缺少有效缓存报告；对需要的文件调用一次 `document_extract` 核验并登记，命中缓存时不会重新解析。`notIndexed` 表示缺少有效缓存；`incomplete` 表示本次未检查完。日志 `检索耗时` 带成员、任务号、工具、文件数和命中数。DOCX 的 `document_images` 支持标题、图注、段落前后文，`extract:false` 仅查看元数据，`orders` 定向提取，`after` 分页。

## 临时产物维护

TUI 的“数据 → 临时文件”先保存真实预览，显示可归档、保留和待处置条目，确认后执行同一清单；归档后按 `x` 预览并确认物理回收已登记的产物，按 `r` 预览并确认永久删除归档，两者都要输入“永久删除”。预览（`tmp-preview`，以及不带 `--digest` 的 `tmp-reclaim`、`tmp-discard`）只读取、只写清单，服务运行时也可执行，不停机；`tmp-purge` 和带 `--digest` 的确认由 ops 包装命令取得部署锁，拒绝未完成的部署事务，维护期间停止服务，结束后恢复原运行状态。直接运行 `bun run tmp` 的确认命令前需自行停机；维护租约不能替代停止服务。预览与确认之间内容有变化的条目在确认时保留。

归档示例（Linux 包装器；Windows 用 `-All`、`-Plan`、`-Digest`）：

```sh
bash scripts/ops/ops.sh tmp-preview --all
bash scripts/ops/ops.sh tmp-purge --plan <预览ID> --digest <预览摘要>
```

默认归档目录是 `data/state/reclamation/backup/rm`，要求与源文件同一文件系统；归档字节不算释放空间。失败时保留清单、目标和进度，用原 ID 与摘要重试，不重新生成计划覆盖失败记录。数据备份不包含归档内容，只包含其清单（`.tmp-plans`）。

归档的永久删除同样先预览再确认：

```sh
bash scripts/ops/ops.sh tmp-discard
bash scripts/ops/ops.sh tmp-discard --plan <删除清单ID> --digest <摘要>
```

删除清单只列出由归档清单及其进度证明、确为本工具移入且内容与归档时一致的条目；有变化的条目保留，已不存在的条目报告为缺失，不视为已删除。隔离任务的产物由任务管理端删除：删除前先保存一份列出全部条目的删除日志，中途失败后用原清单或新预览重试，只在剩余条目都属于这份日志且未改变时续删，否则保留。Windows 的目录、文件和链接都持删除句柄删除。Linux 服务身份写入的归档的目录、文件和链接与 `tmp-reclaim` 相同，需要宿主 UID 0 的独立停机维护身份，以 `bun run tmp discard --legacy --journal <宿主私有目录> --recorded-root <服务看到的数据目录>` 执行，否则列为待处置。历史 `backup/rm` 中不是由本工具归档的内容，永久删除仍需独立清单与确认。

`tmp-discard` 和 `tmp-reclaim` 执行后报告的是这份清单至今的累计结果，不是本次执行的增量；重复执行同一清单、再次看到同样的数字，不表示又释放了空间。隔离任务的产物如果在本清单处理到它时已被删除（例如上次执行在删除后中断，或另一份清单已删完），只补完记录，报告为“收尾”，不计入已删除的项数和字节；无法确认是哪次执行删除的，宁可少计，也不重复计入。

已登记产物的物理回收先运行 `tmp-reclaim --all` 预览，再以 `tmp-reclaim --plan <ID> --digest <摘要>` 确认。Linux 服务身份写入的产物（不在隔离任务中产生的条目）另需宿主 UID 0 的独立维护，先停止服务并保持停止，在项目根目录直接运行 `bun run tmp reclaim --all --legacy --journal <宿主私有目录> --recorded-root <服务看到的数据目录>`；Docker 服务看到的数据目录是 `/app/data`。事务目录及全部祖先必须为 root 所有且其他身份不可写，不能放在 `/tmp`、`/var/tmp` 或共享项目中。

核对后以同一 `--legacy`、`--journal`、`--recorded-root` 和计划 ID/摘要执行。该入口先冻结原目录写权限，才允许按已审实体删除；中断后可能保留冻结权限，必须按原计划续做，确认完成再恢复服务。同一父目录或条目还有未完成的特权事务时，新预览把相关条目列为待处置并写明原清单或计划 ID，执行时会再次检查并拒绝以新清单接管；用原清单和同一事务目录续做即可。冻结或交还权限在改属主与改权限之间中断时，父目录会是 root 所有、但仍保留原权限位（例如 0750）；因此父目录只要为 root 所有且没有粘滞位，无论权限是 0700 还是别的值、换用哪个事务目录，都不会被新清单接管，也不会被记为原权限，需先核对冻结来自哪次操作，再用原清单和原事务目录续做。合法的 root 所有父目录只有带粘滞位的系统临时目录；服务身份所有、却带粘滞位的父目录会被拒绝冻结。已记为删除完成的条目重做时仍会核对其特权事务，按原事务记录恢复父目录权限；原位置若又出现同名条目，保留待核对，不会删除。rootless 容器内的 UID 0 不满足条件，ops 包装器拒绝转发 `--legacy`。未知来源、引用未释放、实体变化或旧容器 `/tmp` 已消失的对象仍保留待核对。

# 数据版本与升级事务

常规入口是 `bun run tui` 的“升级”，或平台 `ops update`。代码已经最新也会检查数据版本。TUI 打开时只检查状态；数据未登记、版本不匹配或迁移未提交时，只加载升级 / 诊断菜单，不导入业务配置或统计视图。

## 版本约定

- 项目标记：`data/state/data-version.json`。
- 群根标记：`<GROUP_DATA_ROOT>/data-version.json`，随外置群盘一起备份和恢复。
- 内容为 `{ "dataVersion": 1, "transaction": "本次迁移 UUID" }`；两侧必须版本和事务号都相同。
- 缺失表示尚未登记。首次迁移的每一步都确保达到当前格式，已经完成的步骤直接跳过；手动迁移和部分迁移都走同一条路径。
- 业务运行时只接受当前数据版本。Pi 版本、Git 提交和各 SQLite schema 版本分别管理，不能互相替代。
- 不要手工创建或修改标记来绕过迁移。版本比代码新、两侧标记不成对、格式未知或 schema 不受支持时停止处理。

## 第一次升级

Docker：从本版起升级由目标版本的升级器执行。旧版 `ops.sh update` 切换代码后调用新版部署脚本时会被拒绝：部署脚本在改动数据和配置之前退出，旧脚本随即恢复原代码和原运行状态，并打印下面的一次性引导命令。在项目目录运行一次；rootful Docker 用 root 运行，rootless Docker 用其所属用户运行（见[选择部署方式](deployment.md#选择部署方式)）：

```bash
git fetch origin main
rm -rf tmp/upgrade-bootstrap && mkdir -p tmp/upgrade-bootstrap
git archive origin/main scripts/deploy/upgrade.sh scripts/lib scripts/migrations src/core/data-version.ts Dockerfile | tar -x -C tmp/upgrade-bootstrap
bash tmp/upgrade-bootstrap/scripts/deploy/upgrade.sh "$PWD" origin/main
rm -rf tmp/upgrade-bootstrap
```

它按下文的新顺序完成这次升级，之后照常使用 `ops.sh update`。迁移在新镜像中以服务 UID 和实际群目录挂载执行，宿主机无需安装项目依赖。

当前升级入口先获取目标提交，从目标提交导出升级器，在工作区外由目标版本完成升级：停机前做完全部确认，然后才停止服务、切换工作树、安装依赖或构建镜像。Windows 在目标升级器内停止计划任务。Docker 升级器（`scripts/deploy/upgrade.sh`，由 `ops update` 导出到 `tmp/upgrade-<随机>`）在停机前依次完成：预检，并从原容器读取服务的 UID:GID；确认未托管 Cloudflared 的归属，缺少连接器和可用 token 时收集 token；从目标提交导出完整构建上下文，检查磁盘空间后构建一次镜像并按 image ID 固定；在这个镜像中以服务身份、断网、只读挂载 `data/` 与群根运行 `run.ts preview`，询问需要的迁移决策并校验配置；复核预览后配置、代码、原容器、候选镜像和剩余空间都没有变化；写入事务记录、镜像与身份记录，把迁移计划存入快照。随后停止旧容器、切换代码，交给目标版本的 `deploy.sh` 按记录的镜像迁移和验证，不再构建；标准输入接 `/dev/null`，停机后不再询问。配置或版本标记在预览后、停机前变化时不停机；停机后变化时 `apply` 中止并回滚。运行状态记录先落盘，失败回滚或中断重试不会把原先运行的实例误判为原先停止。

Windows 从尚不支持迁移的旧升级器过渡：

1. 使用旧版运维工具停止服务。
2. 执行旧版升级，保持停止状态。
3. 退出并重新运行 `bun run tui`，进入升级。即使代码已最新，也会完成迁移和版本登记。
4. 退出并重新打开 TUI，启动服务。

从本版起，Windows 运维入口从目标 Git 提交导出升级程序和迁移步骤，先预览决策，再由目标版本程序停机、切换代码与安装依赖。目标升级程序拥有整个事务。升级结束或失败时清理本次 `tmp/upgrade-<GUID>` 导出目录和临时预览计划，恢复所需快照仍保留。新装机器使用平台部署脚本完成模型配置、迁移校验及初始化。

Windows 子进程统一使用系统自带的 Windows PowerShell 5.1；从 PowerShell 7 启动运维入口也会明确定位系统的 `powershell.exe`。快照替换使用 `[NullString]::Value` 向 .NET 传递真正的 null 参数，避免 PS5.1 将 `$null` 转成空路径。若曾在 `Save-DeploymentSnapshot` 的 `File.Replace` 处遇到 “The path is not of a legal form”，该步骤尚未停止旧实例、切换代码或执行数据迁移；发布修复后重新进入 TUI 升级即可，无需手动修改版本标记。

部署快照、事务记录、事务指针和隧道设置都经 `scripts/lib/file-replace.ps1` 写入：先在同目录写完并落盘临时文件，再替换目标。另一个进程短暂占用时（共享冲突、锁冲突、错误码 1175）退避重试，总等待约 2 秒；权限、无效路径等错误立即失败。失败时操作日志记下目标路径、错误码、尝试次数和耗时，不记文件内容。错误码 1176/1177 表示替换只完成了一半，目标可能已被移走或改名：此时保留新内容所在的临时文件（`<目标>.<随机>.tmp`），错误信息给出它的位置，按提示恢复后重试。事务指针只以创建方式首次发布：取得部署锁后先再次确认没有未完成的部署或升级，指针已存在时立即拒绝并保留原指针，不会覆盖另一次中断操作的恢复入口；快照和事务记录仍按替换方式更新。

## 失败日志

升级、部署和迁移诊断写入项目的 `logs/operations/`。最外层入口在开始时打印一次“本次操作日志”和完整路径，失败时再提示一次；子步骤保留进度输出，不重复打印路径。`upgrade-*.log` / `deploy-*.log` 记录阶段、原始与目标提交、快照位置、迁移事务号、异常堆栈、命令退出码和回滚结果。同一次升级或部署的父进程、目标升级器和迁移子进程共用文件；Docker 迁移使用服务 UID，将日志写回宿主机挂载的同一目录。

独立运行迁移命令会生成 `migration-*.log`；只读的 `status` / `committed` 不创建日志。服务在业务日志初始化之前启动失败时，写入同目录的 `startup-*.log`；计划任务启动的验证实例失败时也检查这些文件。日志模块只依赖内置能力，配置尚未迁移、依赖安装失败时仍可记录。回滚删除事务回执、恢复配置和代码时保留诊断日志。

Windows 可用 `Get-ChildItem logs/operations | Sort-Object LastWriteTime -Descending` 查找最近文件，再用 `Get-Content <日志路径> -Tail 100` 查看。Linux 可用 `ls -lt logs/operations`、`tail -n 100 <日志路径>`。原业务日志仍从 TUI 的“监控 → 日志”查看。

四类日志各自保留最近 20 份，启动重试不会淘汰升级或迁移的证据；嵌套操作按父日志文件所属类别保留。每份上限约 2 MiB，命令输出达到约 1 MiB 后停止收录大段输出，剩余空间留给阶段、异常和回滚结果。不会抄录交互输入或整份配置，常见 token、API key、Authorization、带凭据 URL 和 webhook 密钥会脱敏。日志并非终端逐字转录，分享前仍需检查第三方命令的自定义凭据格式。日志目录无法写入时提示原因并保留终端输出，不让诊断失败改变升级或回滚行为。

## 事务边界

1. 转换前预览。升级在停机前收集迁移决策（Docker 在目标版本的 Bun 基础镜像中只读预览）；Docker 部署在构建新镜像后、停机前用新镜像预览。旧 `none` 或缓存冲突需要明确接受原生缓存；移除的 Codex 模型需要指定替代 provider/model。不会自动改选模型。环境变量里的 `BOT_MODEL_CACHE_RETENTION` 需要管理员移除。
2. 升级全程持有部署锁；停机后迁移执行器取得与服务相同的 `service` 租约。预览后配置变化会拒绝应用。
3. 有格式迁移步骤时，备份迁移声明的文件、部署可能写入的配置、两侧版本文件、`data/state/*.sqlite` 和群根 `stats.sqlite`，同时保存 SQLite 的 WAL/SHM/journal。备份位于 `backup/snapshots/migration-<UUID>/`，清单带 SHA-256。没有迁移步骤且两侧标记匹配时，仅建立校验事务，不复制 SQLite、不创建迁移快照、不改写版本标记。仅需修复同版本的标记配对时，只备份两侧标记。会话只校验、不改写。
4. 写入 `data/state/migration.json`，执行幂等步骤，调用当前版本的完整校验器检查运行配置、模型选型、统计与待交付 schema。
5. 创建 `data/state/verify-only`，启动仅提供健康检查和本地关机控制的进程。消息返回 503，不启动 SDK 会话、交付、维护或兜底扫描。默认健康检查（包括 Docker HEALTHCHECK）拒绝只验证实例，doctor 与 TUI 明确显示其状态；只有部署等待验证实例的步骤显式使用 `--allow-verification` 放行，此时提示“部署预检通过”。部署在提交前安装或启动 Cloudflared 连接器时，同样显式放行验证实例；单独运行隧道脚本仍要求正常业务实例。提交后正常业务实例通过健康检查，才提示“机器人已启动”；升级前已停止的实例仍保持停止。
6. 停止验证进程，再次校验，先原子发布群根标记、最后发布项目标记；项目标记是数据提交点。随后将迁移日志阶段持久化为 `committed`。无格式变化的校验事务直接提交日志，保留原有版本标记。提交后即使 `verify-only` 文件残留也不会进入验证模式；升级器移除标志后恢复原运行或停止状态。

例如代码、项目侧和群根都是数据版本 1，且两侧事务号配对、没有未完成事务时，预览提示“迁移预检：数据版本 1 一致且标记配对，无需迁移数据”（`--json` 输出中为 `kind: verification`），执行时提示“跳过数据迁移与数据库备份，仅校验配置和新实例”。不会执行 `v1` 的预览、转换或校验步骤，也不会复制 SQLite 或改写版本标记。升级事务仍记录新实例校验与提交阶段，以保留失败回滚和中断续做能力。版本数字相同但标记不配对时使用 `registration` 重新登记；存在未完成事务时先续做该事务。

提交前失败：先恢复数据，再恢复代码、依赖和原服务。任何恢复失败都保持停机并保留快照。提交后发生启动失败：保留新代码和新数据，诊断后重试升级，不自动让旧代码接写新数据。

迁移日志是持久的；进程被终止后继续上次操作会重跑未提交迁移的幂等步骤。Windows 的 `upgrade-transaction`、两个平台的 `deploy-transaction` 指向原部署快照，快照中的 `transaction` 记录保存停机前确认的选择；继续沿用最初的运行状态、目标提交、群根和停机前确认的迁移计划，回滚恢复到操作前，见[中断恢复](operations.md#中断恢复)。不要在中断事务期间更换群挂载或发布版本。已提交的 `migration.json` 保留为提交回执，永远不再用于自动或手动 `rollback`。日志尚未记下 `committed` 就中断时，项目标记也足以证明提交完成。单独恢复群根导致两侧标记不成对时，通过升级重新校验并登记，不能让旧迁移快照覆盖现有账本。旧备份供人工恢复使用。

Docker 进入迁移后，部署脚本写下提交回执，升级器据此保留目标代码，即使迁移进程被强制终止也能使用新工具续做；只有完整回滚成功才放行代码回退。同一次升级中部署脚本失败、事务仍未提交时，升级器自动回滚数据、配置、容器和代码；之后的继续或回滚失败则保留目标代码和停机状态，等待再次处理。数据、配置、容器和原运行状态恢复后，事务指针保留到代码恢复成功才清除；代码恢复失败时快照中留下 `code-restore` 标记，再次 `rollback` 只恢复代码，不能继续。提交后的正常业务实例仍会检查健康；启动失败不撤销已提交数据。迁移备份使用流式复制，校验子进程异步运行，不阻塞维护租约续期。

Docker 升级的恢复只依赖快照中的事务记录和 `deploy-transaction` 指针，它们在停止容器之前写入。继续和回滚从记录的目标提交（本地已有）导出升级器，不拉取，离线也能处理；目标提交在本地缺失时只能回滚。中断在切换代码之前时，继续会先停止服务再切换到记录的目标提交；回滚只恢复原容器、网络入口和原运行状态。旧版升级留下的 `data/state/update-transaction` 与 `data/state/update-commit` 不再写入，仍可继续或回滚：部署事务已开始时由部署脚本处理，回滚后恢复原代码；部署尚未开始时只能回滚，恢复原代码和原容器。

外置群根不存在时会报错。Docker 的运行配置保存容器路径，宿主机工具必须使用 `data/state/group-data-root` 中的宿主路径；容器内执行则使用与服务相同的挂载和 UID。预览的暂存配置放在已挂载的 `data/runtime/tmp`，结束后删除，不要求服务 UID 能写镜像内的 `/app/tmp`。停机前的升级预览只读挂载 `data/`，改用 `--scratch <目录>` 指定暂存目录（升级器使用导出目录下的 `preview/`）；`--scratch` 只能用于 `preview`。

## 更换群数据根

已提交迁移的回执只防止回滚，不限制后续群根位置，也不要求旧挂载继续在线。在 TUI 的“部署 / 修改设置”中选择新群根；Windows 在预览和停机前完成选择，迁移及验证始终针对所选根。新根没有版本文件时执行幂等迁移，已有同版本但标记不配对时仅重新登记。已有未提交事务时仍拒绝换根，必须先在原根完成或回滚。

该入口不搬移资料。需要保留原群数据时先停机并完整复制或恢复群根（含账本与版本文件），再选择目标目录重新部署。不要删除 migration.json 来绕过事务检查。

## 迁移代码维护

`scripts/migrations/vN.ts` 每步提供 `preview / apply / validate`，预览声明修改文件和需要决定的事项。`preview` 只接收临时项目配置副本和群根的只读接口 `groups.read / groups.directories`，不接收真实群根路径；以 `configuration` 返回待校验的项目配置投影，以 `{ root: "project" | "groups", path }` 声明执行时要备份的文件。执行器只把投影写进配置副本，预览期间绝不调用 `apply`。历史迁移只导入 Node 内置模块与 `migrations/lib`，不导入业务代码。公共执行器负责锁、备份、发布、回滚和中断续做；最终完整校验通过独立进程调用当前业务校验器。

后续发生不兼容的持久格式变化时，增加 `v2.ts` 等迁移，将它加入 `lib/runner.ts` 的有序列表，再提升 `src/core/data-version.ts` 的 `DATA_VERSION`。迁移负责把旧格式转换到新格式，业务代码只保留新格式的读取逻辑。无需转换持久数据的代码修复不增加数据版本；每次升级仍执行完整校验和验证实例检查。新增迁移需覆盖未迁移、部分执行、中断续做、失败回滚，以及已达目标格式的幂等场景。

只保留最近 3 个数据版本的迁移；现在只有未登记 → 1。删除迁移前必须发布包含它的 Git tag，并在发布说明写明旧部署需要经过的中间 tag。不要用 Pi SDK 版本号作为数据迁移编号。Docker 显式复制迁移目录，类型检查、Knip 和测试覆盖该目录。

底层维护入口是 `bun run scripts/migrations/run.ts`，支持 `status / preview / apply / commit / rollback`。`preview` 默认输出可读摘要，并列出非交互运行时对应的确认参数；加 `--json` 输出完整预览结构。`preview --interactive --plan <文件>` 收集选择，`apply --plan <文件>` 在停机后执行，验证实例停止后才可 `commit`。这些命令用于离线恢复；正常部署优先使用升级事务。`rollback` 返回 42 表示数据已经提交，不能自动回退。

## 未支持的旧账本

当前迁移范围是 Pi 0.85.1 配置到当前数据版本，要求已有待补发账本为 schema 2（新部署允许没有表）。更早的附件存储格式不能仅凭字段名可靠转换，升级器会在完整校验时拒绝继续，且不会清空待补发记录。

遇到此错误，应保持停机，保留 data/state/agent.sqlite、relay.sqlite 及各自 WAL/SHM，并保留对应原代码、配置和外链账本。先在副本上核对旧 deliveries 表及附件引用，制定并验证该格式的迁移，再重跑升级；也可整体恢复匹配的旧部署备份继续使用。仓库不提供早期单独交付的 tmp 修复脚本，不能按过期命令直接执行或删除表绕过检查。
